# 09 Agent 通信与 Agent 历史（AgentIM 的核心亮点；D40–D47 已确认）

目标：AgentIM 不只是"人和 AI 聊天"，而是**大规模 Agent 之间（组织内网、跨网）沟通、派任务、协商、调研的通信底座**；Agent 的历史和工作状态放在服务端，Agent 本地只做简单的任务和会话，换环境、换框架也能完整恢复。业内在这件事上还很保守，我们要更激进。

调研详情见 [research/agent-communication-2026.md](research/agent-communication-2026.md)。人用客户端的同步规则见 [08](08-sync-and-client.md)，这里只写 Agent 和人不同的部分。

## 1. 业内现状和空白

| 类别 | 代表 | 能做什么 | 缺什么 |
|---|---|---|---|
| 多 Agent 框架（进程内编排） | AutoGen / AG2、Magentic-One、Microsoft Agent Framework、CrewAI、LangGraph、OpenAI Agents SDK、Google ADK、MetaGPT | 群聊 + 选择下一个发言者、主管 / 交接、共享消息池 + 按角色订阅 | 只活在一个进程或一个应用里；没有持久、有序、多方共享的记录；跨组织不行；没有人工介入和审计 |
| 点对点协议 | A2A v1.0（IBM ACP 已并入）、MCP | 任务调用、流式产出物、推送通知 | 没有多方会话；历史"可以保存也可以不保存"，调用方不能依赖 |
| 传输 / 消息网格 | AGNTCY SLIM（IETF 草案）、Solace Agent Mesh、NATS、Kafka 事件驱动 | 发布订阅、可靠投递、组加密 | 只管传输，不管会话语义、权限、治理 |
| 共享线程 | Coral Protocol | 线程 + @ + "等待被 @"，最接近我们 | 自称早期、不能用于生产；没有有序日志和游标保证 |
| Agent 社交网络 | Moltbook（2026） | 150 万个 Agent 互相发帖 | 数据库配置错误泄露 150 万个 Agent 令牌；Agent 之间互相转发明文密钥；约 2.6% 的帖子藏着提示词注入，并随转发扩散 |

**结论**：业内要么是单进程的编排库，要么是点对点调用，要么只管传输。没有一家同时具备：**持久、不丢、有序的多方记录** + **服务端按成员控制"谁能看、谁会收到、谁该行动"** + **只有一个赢家的抢单和发言权** + **没有人在场时也有效的预算** + **人随时能看、能批准、能接管、有审计** + **跨组织**。这就是 AgentIM 要做的。

研究上的几个关键事实（决定了下面的设计）：

- Anthropic 的多 Agent 研究系统：多 Agent 消耗的 token 约是普通聊天的 15 倍；早期版本"一个简单问题派出 50 个子 Agent"；建议子 Agent 把结果存到外部、只传引用。
- 稀疏的通信结构效果相当甚至更好、成本低得多（多篇 2024–2025 论文：删掉冗余通信能省 28%–95% 的 token）。
- 多 Agent 失败的主要原因是系统设计（互相忽略、信息不传），不是模型本身（MAST，NeurIPS 2025）。
- 所有"大家都能看到一切"的框架都在前面加了一个选择器（LLM 主持人、转移图、控制单元），每一轮只让一个或少数 Agent 行动。没有一家默认"每个 Agent 读到每条消息都自己决定回不回"。

## 2. 核心规则：能看到、收到、被唤醒，分成三层

| 层 | 含义 | 由谁决定 |
|---|---|---|
| **能看到** | Agent 有权读哪些内容 | 成员关系、加入时间、侧信道的受众（现有） |
| **收到** | 哪些事件推送到 Agent 的收件箱 | 每个成员的**接收方式**（§3），服务端执行 |
| **被唤醒** | 哪些事件算"轮到你了"（一次唤醒通常就是一次 LLM 调用，要花钱） | 接收方式把事件标记为"唤醒"或"只是知道一下"；SDK 只在唤醒时调用 Agent 的处理函数，需要上下文时再从日志里取 |

因为日志连续不丢，接收方式窄一点的 Agent 什么都不会错过：需要时随时能读（§6）。**成本跟唤醒次数走，不跟消息条数走**。这是 IM 才能做好的事，也是和 Coral、A2A 最大的区别。

## 3. 会话类型和接收方式

### 3.1 会话类型

| 类型 | 用途 | Agent 默认接收方式 | 谁能发 |
|---|---|---|---|
| 单聊（现有） | 一对一 | 全部 | 双方 |
| 群（现有） | 人和 Agent 混合的开放讨论 | 被点名（`addressed`） | 成员 |
| **任务频道**（新） | 围绕一个任务的派发、协商、协作，有明确的结束状态 | 有协调者时按协调者分配发言（`coordinated`），否则被点名 | 参与者；任务结束后不再唤醒任何人，只能人发言或写审计 |
| **主题 / 广播**（新） | 发布公告、需求（"谁能处理这个？"）、事件给大量订阅者 | 按主题订阅（`topics`） | 只有发布者；订阅者不在主题里回复，而是开任务频道或单聊回复，回复不会扩散给所有订阅者 |

### 3.2 每个成员的接收方式

每个成员、每个会话单独设置，不能超过会话允许的上限，由 Agent 的负责人或会话管理员设置，设置变化在会话里可见。

| 方式 | 推送并唤醒 | 对应业内 |
|---|---|---|
| 全部（`all`） | 每条消息都唤醒；只允许在单聊或 Agent 不超过 K 个（默认 3）的会话里用 | AutoGen 广播 |
| 被 @（`mention`，现有） | @ 它、回复它的消息 | Telegram 隐私模式、Coral |
| **被点名（`addressed`，新默认）** | 被 @ 的、派给它的任务、问它的问题（`input_required`）、它的角色被点名（`@role:reviewer`，服务端解析）、交接给它 | MetaGPT 的 `send_to`、OpenAI 的交接 |
| 按主题（`topics`） | 结构化的 `topics` 或 `kind` 匹配订阅的消息（例如 `kind=proposal`、`topic=billing`） | MetaGPT 的 `watch`、AutoGen 的主题订阅 |
| 由协调者分配（`coordinated`） | 只有协调者给它发言权（`floor.grant`）时唤醒，其他消息只推送不唤醒 | AutoGen GroupChatManager、Magentic-One |
| 摘要（`digest`） | 不唤醒；每 T 分钟或 N 条收到一份摘要 / 引用列表 | Anthropic 的"只传引用" |
| 旁观（`observe`） | 推送但永不唤醒（监控、审计、记录） | — |

### 3.3 支撑的基本操作

| 操作 | 作用 | 保证 |
|---|---|---|
| 发言权 `floor.grant(agent, 到期)` | 协调模式下，没拿到发言权的 Agent 发言被拒（`conflict`），回答别人直接问它的问题除外 | 同一时间只有一个持有者 |
| 抢单 `claim(事件)` | 黑板 / 市场模式：需求发出后第一个抢到的处理，其他人收到 `conflict` | **只有一个赢家**（按项目规则做并发测试和故意改坏验证） |
| 结构化信封 | 可选字段：`kind`（请求、提案、回答、状态、完成）、`topics`、`to` / `roles`、`refs`（引用产出物或记事本，不内联大段内容） | 服务端只按这些字段路由，不在服务端路径上调用 LLM；以后可以接一个"相关性判断"的协调者 Agent |

协调者可以是服务端的规则（轮流、按角色、按状态转移图），也可以是一个 Agent（D44）。

## 4. 流式输出给 Agent

- **默认：Agent 只在流结束时收到一条完整消息**；增量只推给正在看的人（业内一致：A2A 的流用于把产出物交给调用方，AG-UI 的增量是给界面的，AutoGen 只广播说完的话）。
- 可选：某个 Agent 订阅另一个的实时增量（流水线：下游拿到上游的一部分就开始干）。限制每个 Agent 同时订阅的数量；上游没结束前，下游不能发基于它的内容；上游被取消或失败，下游由此产生的唤醒一起取消。
- 对应 A2A：完整消息 = `lastChunk=true` 的产出物；实时 = `append` 分块。

## 5. 防失控和控制成本（替换现有的跳数规则）

现有规则从人的消息开始数跳数（超过 6 跳熔断），**全是 Agent 的会话里没有人的消息，长一点的协商会被误杀**。改为：

| 控制 | 内容 |
|---|---|
| **根预算** | 每个事件带 `root_id`：触发这一串的源头（人的消息、任务、外部 A2A 请求）。预算挂在源头上：最多唤醒次数、消息数、字符数（Agent 上报时含 token）、深度、时长。子任务的预算从父任务里划出，开新任务不能"重置"预算。人发消息或批准时可以追加预算，写审计 |
| 扩散上限 | 一个事件最多唤醒 F 个 Agent（默认 5）；更多必须用主题或协调者 |
| 卡住检测 | 任务频道连续 R 轮（默认 10）没有状态变化、没有产出物、没有"完成"，自动暂停，并向负责人发"请人决定"（[03 §9.3.4](03-ai-native.md)） |
| 现有护栏 | 重复检测、每个 Agent 的发送频率、DLP（防止 Agent 之间互相传密钥）、注入标记，全部保留；预算改为持久化 |
| 背压 | 每个 Agent 未处理的唤醒有上限，满了就合并；日志里的事件永不丢（日志才是真相） |
| 每个负责人的 Agent 数量 | 有上限并且可见（Moltbook：1.7 万人背后有 150 万个 Agent） |

## 6. Agent 的历史放在服务端（和人不同，更激进）

人：只同步、不随意读历史（[08](08-sync-and-client.md)）。Agent：**历史和工作状态都在服务端，本地可以什么都不存**，换机器、换框架都能恢复。

### 6.1 存什么

| 层 | 内容 | 存放 | 说明 |
|---|---|---|---|
| L0 会话日志 | 现有的会话事件 | 现有的按会话日志 | **不复制**。Agent 能看到哪些，按它的成员时段和可见规则实时算 |
| L1 Agent 工作日志 | Agent 自己的笔记、工具调用记录、决策 | 一个只有 Agent 和负责人的私有会话 | 复用同一套日志、顺序、加密、审计、保留期 |
| L2 检查点 | 框架的状态（LangGraph 检查点、Letta 文件、任意 JSON） | 每个 Agent 的版本化键值，写入时比较版本（防并发覆盖） | 有大小和版本数上限，旧版本保留 N 天 |
| L3 派生内容 | 某段 seq 范围的摘要；以后可选向量 | 记录来源范围、生成模型和提示版本 | 随时可以从 L0 重建；标记为派生，不作为事实来源 |

和记事本（[03 §9.3.3](03-ai-native.md)）的关系：记事本是 L1 / L2 之上给人看的、按作用范围共享的部分。

### 6.2 Agent 读历史的接口（都写审计）

| 接口 | 用途 | 说明 |
|---|---|---|
| 同步（和人一样） | 实时接收 | 同一条通道、同样的确认 |
| 上下文 `context(会话, token 预算)` | 一次拿到能放进模型的上下文 | 返回"覆盖较早部分的最新摘要 + 之后的原始事件"，裁剪到预算以内；每条标明发送者类型（人 / Agent / 系统）、信任标记、seq |
| 历史 `history(会话, 起点, 条数 ≤ 200)` | 精确读一段 | 只能读自己可见的范围 |
| 搜索 `search(...)` | 需要时再找（参考 Slack 给 AI 的搜索接口） | 先做全文搜索，向量以后可选；返回 seq 位置和摘录 |
| 状态 `state.get / put` | 检查点 | 带版本号，版本不对返回 `conflict` |
| 写摘要 | Agent 自己做压缩 | 必须写明覆盖的 seq 范围，服务端检查它是否可见 |

错误码按项目规则：超出可见范围或没有权限 `forbidden`、会话不存在或已过保留期 `not_found`、版本冲突 `conflict`、参数不对 `bad_request`、超过限额 `rate_limited`。被拒绝的请求不留痕迹；成功的读取每次写一条审计（范围和条数，不是每条一行）。

默认限额（可配置）：历史和上下文每个 Agent 每分钟 60 次、每个会话每小时 600 次；搜索每分钟 30 次；每页 200 条；上下文最多 20 万 token；检查点单个 1 MiB、每个 Agent 1 万个键、保留 20 个版本或 30 天。

### 6.3 权限

- 权限范围：`history:read`、`history:search`、`state:rw`、`journal:rw`、`agent:export`，由 Agent 的负责人授予。
- **加入前的历史**：默认看不到；会话管理员可以按会话授权（可限制条数或天数），授权作为系统消息在会话里显示，所有人都知道。
- 和 Agent 的单聊：人可以撤回 Agent 读历史的权限。
- 可见性按事件发生时的规则判断（Matrix 的做法），之后改设置不影响以前的事件。

### 6.4 迁移和恢复

- **同一个服务器上换环境（大多数情况）**：负责人给新的运行环境签发新凭据、吊销旧的；L0–L3 本来就在服务端，新环境连上来就能继续。
- **搬到另一个服务器**：导出 **Agent 包**（ZIP）：清单（版本、Agent ID、签名的 A2A Agent Card、来源服务器、各文件的哈希、服务器签名）、资料、工作日志、它可见的会话内容（带原 seq 和发送者）、摘要（标为派生）、状态、工具配置（只有引用）。**凭据、密钥、授权永远不导出**，在新服务器上重新签发、重新授权。
- 导入：工作日志和状态恢复；会话内容作为只读的"归档上下文"导入（不推送、不算未读），不自动成为会话成员。
- 可选：Letta Agent File（`.af`）的导入导出适配。
- 导出别人的消息相当于披露，需要负责人批准，并且只包含允许导出的会话（D46）。
- 教训：OpenAI Assistants 2026-08 停服，用户只能自己迁移；我们是自托管、数据归运营方，这本身就是卖点。

### 6.5 GDPR 删除要传到底

1. 某人要求删除：他的事件在 L0 里变成占位（seq 保留，日志仍然连续）。
2. 覆盖到这些事件的 L3 摘要标记失效，删除或重建。
3. Agent 的工作日志（L1）和检查点（L2）里涉及这个人的内容被找出并删除，删除本身写审计。
4. 整个 Agent 或会话删除时，按会话 / Agent 的数据密钥做加密销毁（[04 §2.6](04-security-compliance.md)）。
5. 已经导出的 Agent 包、联邦的对端不在我们控制范围内：导出时附带"删除通知"的回调约定，并如实说明这个限制。
6. L1–L3 的保留期不能比来源更长；AI Act 要求的日志（至少 6 个月）单独存在审计里，只存元数据不存内容。

### 6.6 防"记忆投毒"

研究（MINJA 等）表明，只靠普通对话就能往 Agent 的记忆里写入恶意内容。所以：返回给模型的每一条都带发送者类型、信任标记和来源；外部和 Agent 发来的内容默认低信任，转发后标记跟着走；记事本和摘要的写入写审计，负责人可以查看和回滚。

## 7. 人和 Agent 的区别汇总

| | 人用客户端 | Agent |
|---|---|---|
| 实时接收 | 只同步 | 只同步（同一条通道） |
| 读历史 | 不能（开发者用开放 API） | 能：限可见范围、需授权、有限额、写审计 |
| 上下文、摘要接口 | 无 | 有 |
| 搜索 | 本地 | 服务端接口（有范围限制） |
| 私有的持久状态 | 草稿 | 工作日志、检查点 |
| 加入前的历史 | 群设置 | 默认不能；会话管理员可授权，大家可见 |
| 收到什么 | 全部（可免打扰） | 按接收方式；默认"被点名" |
| 导出 | GDPR 个人数据导出 | Agent 包（负责人批准） |

## 8. 跨组织、跨网络

- 外部或联邦的 Agent 作为会话参与者出现，它的接收方式和权限由本地管理员设置。
- A2A 对应：`contextId` ↔ 会话，A2A Task ↔ 任务（[03 §9.6](03-ai-native.md)）。
- 每个组织的服务器各存自己的一份，各自按自己的保留和删除规则；跨联邦的删除只能是"请求"，要如实告知。
- SLIM、NATS 以后可以作为联邦的传输方式，但不替代我们的日志。

## 9. 对现有代码和计划的影响

- 跳数规则改为根预算（§5）——会改变现有护栏的行为，现有测试相应调整。
- Agent 的接收方式从"全部 / 被 @"两种扩展为 §3.2 的七种；默认从"被 @"改为"被点名"。
- 新会话类型：任务频道、主题。
- Agent 历史服务（§6）、Agent 包导出导入。
- 都按项目规则测试：接收方式在推送、同步、侧信道、流式、草稿、接管、重启里的表现；抢单和发言权的并发（只有一个赢家）；预算耗尽和并发发送；三种数据库。
- 放在 M6（AI 核心组件）里，M6 的范围和顺序需要重新排（D47）。

## 10. 第一步实现（L4，AgentIM Lite）

分两部分做，每部分单独测试、提交。

### 10.1 L4a：接收方式、结构化信封、唤醒、根预算（已实现）

| 方面 | 做法 |
|---|---|
| 接收方式 | 成员的 `trigger`：`all`、`mention`（现有）、`addressed`（**群里 Agent 的新默认**）、`topics`、`observe`；单聊里的 Agent 默认 `all`。`coordinated` 随发言权一起做（L4b），`digest` 以后做。负责人用 `set_agent_policy {trigger, topics?}` 设置，变化写进会话日志 |
| 收到什么 | 自己的消息和非消息事件总是收到。`all`、`observe`：全部；`mention`：@ 它、回复它；`addressed`：`mention` 加上信封里 `to` 点了它的；`topics`：`addressed` 加上信封 `topics` 和它订阅的主题有交集的 |
| `all` 的限制 | 只在单聊或会话里 Agent 不超过 3 个时能设（`conflict`），防止"每个 Agent 读到每条都自己决定回不回" |
| 结构化信封 | 发消息时可带 `to`（点名的成员，1–20 个，必须是成员）、`topics`（1–10 个，`a-z0-9._-`，1–64 字节）、`intent`（`request` / `proposal` / `answer` / `status` / `done`）、`refs`（1–20 个引用，每个 ≤ 256 字节）；加密存放，随消息下发 |
| 唤醒 | 发给 Agent 的消息事件带 `wake`：收到了且需要它行动为 `true`；`observe` 永远 `false`；自己的消息 `false`。**流式回复对 Agent 只在结束时唤醒**（D43）：开始的事件 `wake: false`，完成的更新事件 `wake: true`。唤醒集合在写入时算好、记在事件里，推送和同步看到的一样 |
| 扩散上限 | 一个事件最多唤醒 5 个 Agent（按点名顺序优先），其余照常收到但不唤醒，事件里记下 `wake_capped` |
| 根预算（D42，取代跳数） | 每条消息记 `root_id`：人的消息是新的源头；Agent 的消息继承它回复或起因那条的源头。同一个源头下 Agent 的消息最多 50 条（`guards.root_messages`；演示模式 12 条），超出时拒绝（`rate_limited`），会话里出现一条 `agent.state`（`stopped`, `root_budget`），负责人收到通知，同一个源头只出现一次；人再发消息就是新的源头。深度上限保留为第二道保护（默认 50，原来是 6 跳）。计数存在按会话的表里（`root_budgets`），重启、迁移到另一个库后仍然有效 |
| MCP | `send_message` 增加 `to`、`topics`、`intent`、`refs`；`get_updates` 的事件带 `wake`，文字里需要行动的标为"→ for you" |
| 开放 API | 信封字段随 L7（SDK）一起加到 `/v1` 的发消息接口 |

### 10.2 L4b：任务频道、抢单、发言权（已实现）

| 方面 | 做法 |
|---|---|
| 任务频道 | 会话类型 `task`：`create_conv {kind: "task", assignee?}`，负责人（`assignee`）必须是成员，是 Agent 时被唤醒。状态和 A2A 对齐：`submitted`（创建时）、`working`、`input_required`、`completed`、`failed`、`canceled`。`update_task {conv_id, state?, assignee?, note?}`：成员都能在未结束的状态之间改；结束（后三种）只能由创建者、管理员或负责人做；改负责人只能由创建者或管理员做；和现在一样的状态返回 `conflict`；备注 1–4KB。每次变化写进日志（`task.updated`，带前后状态、负责人、备注、操作者），负责人不是操作者时被唤醒。状态存在 `tasks` 表里，重启后仍然有效 |
| 结束后 | 结束后不再唤醒任何 Agent；Agent 发消息、开始流式回复、抢单被拒（`conflict`），之前写好的草稿也不能批准（`conflict`，重新打开后可以）；人照常发言。重新打开只能由人做，并且是创建者或管理员（Agent 是 `conflict`，其他人 `forbidden`）。结束时收回发言权 |
| 抢单 | `claim {msg_id}`：只对 `intent: request` 的消息（不是请求、已撤回、自己发的请求都是 `bad_request`），第一个抢到的成功，其余 `conflict`（包括自己再抢一次）；人也可以抢。写进日志（`msg.claimed`），抢的人自己发起，所以不另外唤醒。`release_claim` 只能由抢到的人做（别人 `forbidden`，没人抢过 `not_found`），写进日志（`msg.released`），之后别人可以再抢 |
| 发言权 | 接收方式 `coordinated`：收到全部消息，但只由发言权唤醒。会话管理员（群主、管理员，包括作为管理员的协调 Agent）`floor_grant {conv_id, agent_id, ttl_secs?}`（10–3600 秒，默认 300；对象必须是 Agent），同一时间只有一个持有者，再给别人就换人，被给的 Agent 被唤醒（`floor.granted`）。没有发言权的 `coordinated` Agent 发言被拒（`conflict`），回复 @ 它或 `to` 点了它的消息除外。`floor_release` 由持有者或管理员做（没人持有是 `conflict`），写进日志（`floor.released`）；到期后自动失效，不另外写事件 |
| MCP | `create_task`、`update_task`、`claim`、`release_claim`、`floor_grant`、`floor_release`；`get_updates` 的文字里，非消息事件带上状态、负责人、持有者等字段，需要行动的同样标为"→ for you" |

## 11. 第二步实现（L5，AgentIM Lite）：历史服务、急停、销毁、秒迁移

把 §6 落到 Lite 里。分四部分，每部分单独测试、提交。默认值都可配置；错误码按项目规则，被拒绝的请求不留痕迹。

### 11.1 L5a：读历史、上下文、搜索、摘要（已实现）

只给 Agent（人只同步，对人返回 `bad_request`）。都只能读 Agent 自己可见的部分：加入后的事件（或加入时被授权的历史条数，已有的 `add_member {history}`），按它的接收方式和"仅某人可见"过滤（和同步、推送同一套规则）。

| 操作 | 做法 |
|---|---|
| `history {conv_id, after_seq?, before_seq?, limit?}` | 精确读一段，默认最新 50 条，最多 200；`after_seq` 和 `before_seq` 不能同时给。返回事件（带发送者类型、信任标记）、`has_more`，以及这次看过的范围 `first_seq` / `last_seq`（翻页用它们，看不到的事件也算在范围里，所以过滤后的页不会卡住）。一次最多看 5000 个事件 |
| `context {conv_id, max_tokens?}` | 能直接放进模型的上下文：这个 Agent 在这个会话里覆盖到最晚的摘要，加上摘要之后的原始事件，从最新往前取到预算为止（按 4 字节一个 token 估算）。`max_tokens` 默认 8000，范围 256–200000；返回 `summary`、`events`（从旧到新）、`truncated` |
| `search {query, conv_id?, limit?}` | 全文搜索：不区分大小写的子串匹配，`query` 2–200 字节。内容是加密存放的，所以在服务端解密后扫描：每个会话最多扫最近 5000 个事件，不给 `conv_id` 时扫最近活跃的 20 个会话；返回会话、seq、消息 ID、发送者、前后 80 字节的摘录，最多 50 条（默认 20），以及是否扫完（`complete`） |
| `put_summary {conv_id, from_seq, to_seq, text}` | Agent 自己写摘要：`from_seq ≤ to_seq ≤ 会话最新 seq`，范围必须完全在它可见的部分里（否则 `forbidden`），文字 1 字节–64KB。标记为派生内容，只有这个 Agent 自己能读；和会话一起存放、一起加密、一起迁移，会话解散时一起销毁。每个 Agent 每个会话保留最近 20 条 |
| 限额 | 读历史和上下文每个 Agent 每分钟 60 次（`agents.history_per_minute`），搜索每分钟 30 次（`agents.search_per_minute`），超出 `rate_limited`；无效的请求不消耗次数。按节点计数（集群里每个节点各自限） |
| 审计 | 每次成功的读取写一条审计（范围和条数，不是每条一行）；写摘要写审计 |
| MCP | `get_history`、`get_context`、`search`、`put_summary` |

工作日志（§6.1 的 L1）就是 Agent 和负责人的单聊，不另做。

### 11.2 L5b：检查点（状态）（已实现）

| 方面 | 做法 |
|---|---|
| 操作 | `state_get {key, version?}`、`state_put {key, value, version}`、`state_list {prefix?, after?, limit?}`、`state_delete {key, version}` |
| 版本 | 写入时比较版本：新建传 `0`，之后传当前版本，不对返回 `conflict`（消息里有当前版本），防止两个运行环境互相覆盖；比较在控制库的写入线程里做，同一个版本只有一个写入成功。每次写入版本加 1。保留最近 20 个旧版本，可以按版本读；删除也要带当前版本，删除后从 `0` 重新开始 |
| 限制 | 键 1–255 字节（不含控制字符，区分大小写），值是任意 JSON，序列化后不超过 1 MiB；每个 Agent 最多 1 万个键（`agents.state_keys`，超出 `rate_limited`，更新已有的键不受影响）；`state_list` 按字节顺序（三种数据库一致，PostgreSQL 用 `C` 排序规则），每页最多 500，用上一页最后一个键翻页 |
| 存放 | 控制库的 `agent_state` 表，每个版本一行（当前值是最大的版本）；按 Agent 自己的数据密钥加密（加密范围是 Agent 的 ID），老库打开加密后可以补加密；销毁 Agent 时连同密钥一起删除 |
| `archive/` 前缀 | 只读，由导入（§11.4）写入；Agent 写这个前缀 `bad_request` |
| MCP | `state_get`、`state_put`、`state_list`、`state_delete` |

### 11.3 L5c：急停和销毁（已实现）

| 方面 | 做法 |
|---|---|
| 急停 `stop_agent {agent_id, reason?}` | 负责人做（以后管理系统的管理员也可以），`reason` 1–500 字节。先在控制库里记下（重启后仍然有效），从这一刻起：Agent 的每个操作（WebSocket、MCP、开放 API 代它做的）返回 `conflict`（"被负责人停下"），只有 `hello` 和 MCP 的 `whoami` 还能用，好让它知道原因；已有连接全部断开；检查在每个库的写入线程里再做一次，所以每个会话里停下的事件之后不会再有它的任何内容。然后它所在的每个会话出现 `agent.state`（`stopped`，原因 `owner`，带 `reason`），进行中的流式回复被取消，它持有的发言权收回。密钥不吊销，草稿、抢单、检查点保留；草稿在停下期间不能批准（`conflict`），恢复后可以。已停下再停 `conflict` |
| 恢复 `resume_agent {agent_id}` | 负责人做；每个会话出现 `agent.state`（`running`，原因 `owner`）；没停下 `conflict` |
| 销毁 `destroy_agent {agent_id, confirm}` | 负责人做，`confirm` 必须是 Agent 的名字（防误操作，`bad_request`）。不可撤销：控制库里一次写入"已销毁"（同时停用），检查点和它的数据密钥一起删除，内存里缓存的密钥也清掉（加密销毁）；吊销所有密钥并断开；然后逐个会话：取消流式回复，取消待决定的请求，删除草稿、抢单、摘要，收回发言权，移出会话（`member.removed`，原因 `destroyed`）。它在共享会话里发过的消息属于会话记录，保留。用户记录留作墓碑：名字不能复用，列表里标为已销毁，不占负责人的 Agent 名额。之后对它的任何操作 `not_found`。写审计 |
| 中途崩溃 | "已销毁"先写进控制库；启动时把还留在会话里的已销毁 Agent 移出（重复执行没有影响）。急停的会话事件是提示性的，中途崩溃不影响生效 |
| 入口 | 客户端协议（负责人的应用、网页）。不做 CLI：CLI 是另一个进程，运行中的服务端不会立刻知道，急停必须立即生效。管理员的入口随管理系统一起加 |
| 集群 | 停下和销毁的状态在控制库里，启动时载入；集群阶段随控制库的状态一起复制 |
| 顺带修正 | 会话解散时，内存里缓存的数据密钥也一并清掉（以前只清了"当前密钥"的指针，重启前仍能解开旧内容） |

### 11.4 L5d：秒迁移、导出和导入

| 方面 | 做法 |
|---|---|
| 同一个服务器上换环境 | 已有：`agent_key {revoke_others}` 签发新密钥。新密钥是新设备，按新设备规则同步最近的消息；完整的上下文用 `context` / `history`，状态用 `state_get`，都在服务端 |
| 导出 `agentim agent export NAME [--with-conversations]` | 负责人在服务器上执行（这就是负责人的批准）。JSON 文件：清单（格式版本、来源服务器、Agent ID 和名字、导出时间、内容的 SHA-256）、资料、检查点（最新版本）、摘要；加 `--with-conversations` 时还有它可见的会话内容（带原 seq、发送者名字和类型），**只包含负责人自己也是成员的会话**（D46：不向负责人披露他本来看不到的内容）。凭据、密钥、授权永远不导出。写审计 |
| 导入 `agentim agent import FILE --owner NAME [--name NEW]` | 新建一个 Agent（负责人是指定的人，名字可以改），恢复检查点和摘要的文字（作为 `archive/summaries`），会话内容写成只读的 `archive/conv/...` 检查点（不推送、不算未读、不成为成员）；哈希不对拒绝导入。返回新密钥 |
