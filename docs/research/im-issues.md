# 调研：开源 IM 踩过的坑，我们有没有

> 2026-10-12 至 10-16。读了 OpenIM、Matrix（Synapse、tuwunel / conduwuit、Conduit、Dendrite）、Zulip、Tinode、ejabberd / Prosody 的提交记录、变更日志和问题单，以及这些项目和 Rocket.Chat、Mattermost、Centrifugo 的 57 条安全公告，归成约 150 类问题，每一类都对照了 AgentIM 的代码和测试。
> 原始报告（含每一条的出处链接和代码行号）在调研时的临时目录里，这里是合并去重后的结论。Mattermost / Rocket.Chat 的普通问题单这一组因额度用完没有完成（它们的安全公告已包含在安全组里）。
> 2026-10-16：H1–H6、M1–M17 全部修复，D87–D96 按建议实现（D89 按确认后的「个人助理 / 团队 Agent」），测试见 [05 §5](../05-operations.md)（`tests/audit.rs`、`tests/sync.rs`、`tests/team_agents.rs` 等）。「低」一节还没处理。
> 判定：**已防住** = 有代码也有测试；**可能有** = 有防护但没测试、或需要你定规则；**有** = 能写出"什么输入 → 什么错误结果"。关键几条已人工复核过代码（标 ✔）。

## 1. 总体情况

- 大约一半的问题类我们**已经防住并有测试**：序号在事务里分配、提交后才回复、推送有界且只是提示、同步按设备记位置、已读只前进且不超过最新、未读每次现算、撤回清理主日志、单写者无死锁、去重和消息在同一事务、移出后不能读写、越权读、伪造发送者、API Key 权限、注入、超大请求和深层 JSON、无界分页等。
- 发现的问题集中在五个地方：**新成员和"入群前"的边界**、**重试和去重的顺序**、**撤回 / 保留期没有覆盖衍生数据**、**多库（企业版）两步提交**、**账号和凭据的边角**。
- 没有发现会丢失"已回复成功"的主日志消息的问题。

## 2. 确认有的问题（按严重程度）

### 高

| # | 问题 | 怎么触发 → 结果 | 同类问题出处 |
|---|---|---|---|

| H2 ✔ 已修 | **不登录就能把服务器内存耗尽** | 大量并发 `POST /api/auth/login`（名字随便填）→ 每次一个 19 MiB 的 Argon2 哈希，没有并发上限，最多 512 个阻塞线程同时跑 → 约 10 GB 内存、CPU 跑满 | Centrifugo GHSA-8w47、Rocket.Chat GHSA-7c6v |
| H3 已修 | **编辑入群前的旧消息，新内容推给了看不到它的新成员**（隐私） | carol 以"不看历史"加入 → alice 编辑一条 carol 入群前的消息 → carol 实时收到、同步里也拿到带全文的 `msg.updated`；`trigger=all` 的 Agent 也一样 | Zulip f81f38f0（同一个修复） |
| H4 已修 | **撤回、解散没有清理衍生副本** | ① 审批通过的 Agent 消息被撤回后，原文还在草稿表和侧信道的 `draft.created` 里，负责人和 Agent 同步时仍能读到；② Webhook 发件箱里还没送出的消息不随撤回清理，解散会话时也不随加密销毁清理，Webhook 恢复后把已撤回 / 已解散的原文发出去 | Synapse #6377（搜索返回已撤回事件）、Zulip e4918006（撤回时收回推送） |
| H5 已修 | **多库时成员操作分两步提交，没有补偿**（企业版） | 会话库提交后再写控制库的索引和离开记录：① 控制库返回 `overloaded` 或进程在两步之间崩溃 → 被移出的人在 `list_convs` 里**仍能看到群名、成员和最新序号**（`list_convs` 不检查成员关系）、离线设备收不到"已移出"；② 同一个人的移出和拉回并发 → 他是成员却再也收不到消息，直到重启 | OpenIM #3750 / #3785（报错了人却已进群）、Tinode 2f632ecc |
| H6 已修 | **借自己的 Agent 看到权限之外的内容** | ① bob 以"不看历史"入群 → 拉自己的 Agent 进群并给它 200 条历史 → 用 `observe` 读到自己入群前的消息；② bob 被移出但他的 Agent 没被移出 → 继续通过 `observe` 看、通过 `takeover` 以 Agent 身份说 | Zulip GHSA-87p9（借邀请绕过权限）、GHSA-c9wc（退出后还能访问） |

### 中

| # | 问题 | 怎么触发 → 结果 |
|---|---|---|
| M1 ✔ 已修 | **重试去重放在权限、护栏和发送前钩子之后** | 消息已经提交但回复丢了 → 期间被移出或拉黑 → 用同一个 `client_msg_id` 重发得到 `forbidden` / `blocked`，客户端标成"失败"，别人却已经看到；Agent 重发会再扣限流和每日预算，第三条相同文字还会误触发熔断；发送前钩子会被再调一次，钩子拒绝时已发出的消息被报失败；非成员的内容也会先发给外部钩子 |
| M2 已修 | 发给某个人的消息和审批草稿**重试不去重** | 重发后对方收到两条，负责人的待办里出现两份草稿 |
| M3 ✔ 已修 | **新成员的未读数和 @ 数包括他看不到的消息** | 500 条消息的群里以"不看历史"拉入 bob → 显示 500 条未读，一条也看不到；移出后再加回也一样 |
| M4 ✔ 已修 | **搜索和导出找的是一个根本不存在的事件类型 `msg.edited`** | 编辑后新文字搜不到、旧文字仍能搜到；Agent 的流式回复永远搜不到，Agent 导出包里流式回复是空的 |
| M5 已修 | 侧信道积压超过一批时**同步报"没有更多了"**；侧信道查询没有上限 | 离线期间收到 250 条悄悄话或进度 → 只拿到 200 条，剩下的要等会话里再有动静；会话越长每次同步越慢 |
| M6 已修 | **安静会话的设备位置被单独过期，之后静默跳过消息** | 设备天天在用，但某个会话 30 天没动静 → 这一行位置被清理 → 之后这个会话涌入 300 条 → 设备只拿到最后 200 条，**没有"有消息不可同步"的提示** |
| M7 已修 | 推送队列满时整条下发记录被删 → **合法的确认被拒**，同一批其他会话的确认也一起失败，事件重复下发（不丢） |
| M8 已修 | **已读位置、免打扰变化在推送队列满时被直接丢掉**，同步里也不带这些状态 → 其他设备补不回来 |
| M9 ✔ 已修 | **API Key 的 IP 白名单可以被伪造的 `X-Forwarded-For` 绕过**（取的是第一项，而常见代理会保留客户端自带的值） |
| M10 已修 | **运维用 CLI 重置密码后，正在运行的服务端里旧令牌仍然有效**（服务端只在启动时读令牌），直到重启 |
| M11 ✔ 已修 | **一条"长得像密文"的消息让整个会话无法读取** | 加密关闭（或有开启加密前的老数据）时，发一条文字为 `enc:v1:k_x:AAAA` 的消息 → 这个会话的同步、历史、导出全部报 `storage` 错误，这个库的 Webhook 投递永久卡住 |
| M12 已修 | **人类用户没有发送限流**；同步和信号的限流按连接算，每个用户的连接数没有上限 → 一个账号可以刷屏、压垮推送 |
| M13 已修 | **鉴权通过和连接登记之间吊销令牌，连接会活下来**（一次握手往返的窗口） |
| M14 已修 | **离线期间被移出又被拉回**：移出之前本来能看到、但设备还没同步的事件永远不再下发，也没有提示 |
| M15 已修 | **保留期清理不完整**：摘要、已决定的草稿、请求、反馈、Webhook 发件箱不受保留期影响；清理时 `created_at` 上没有索引、一次全删、挡住整个库的写入；系统时钟回拨时可能在日志中间删出空洞 |
| M16 已修 | **服务端没有 WebSocket 空闲超时**：半开连接一直占着资源，Agent 一直显示在线 |
| M17 已修 | 同步下发的 `msg.created` **不带 `client_msg_id`** → 确认丢失后重启，界面先显示两条，docs/08 写的"按 `client_msg_id` 合并"做不到 |

### 低

- @ 识别：编辑后不重新计算；没有词边界（`@bobcat`、`x@bob.io` 都会 @ 到 bob）；Agent 流式回复里的 @ 永远不提醒。
- 分页正好整页时 `has_more` 误报为真（不丢数据，多拉一次空页）。
- 已离开的设备在同步里看到的是当前最新序号（能看出离开后的活跃程度）。
- 离开和解散的记录 30 天后和设备位置一起过期，离线更久的设备不知道自己已离开。
- 令牌永不过期（docs/04 写的是有过期时间）。
- 用户枚举：对存在的账号连错 10 次返回 `rate_limited`，不存在的永远返回 `invalid_credentials`；锁定也能被用来把指定的人锁在外面。
- 已登录后，改密码时的当前密码错误、关闭两步验证时的验证码错误不计入失败次数。
- 令牌放在 `/ws` 的 URL 里，会出现在代理日志里。
- Agent 导出包只有不带密钥的哈希（docs/09 设计的是服务端签名）。
- WebSocket、MCP、登录接口返回数据库的原始报错（泄露表名和约束名）。
- 持续发送随机令牌，会让"运行中用 CLI 新建的 Agent 密钥"一直加载不进来。
- Webhook 签名的密钥格式和 Standard Webhooks 官方验签库不兼容（docs/02 说可以直接用官方库）。
- 拉黑在事务提交前就改了内存，提交失败时内存和数据库不一致。
- 性能：每次同步对用户的每个会话都查 5–6 次；只听 @ 的 Agent 几乎每条都触发一次重新同步；大群里"正在输入"和事件共用队列；大群推送在全局锁里遍历。

## 3. 需要你定规则的

| # | 问题 | 我的建议 |
|---|---|---|
| D87 | 编辑后 @ 怎么算 | 照 Zulip 和 Matrix：编辑后重新计算；新增的 @ 提醒并唤醒 Agent，去掉的不再计数 |
| D88 | 编辑要不要带"基于哪个版本" | 加可选的 `base_version`，不一致返回 `conflict`（Agent 和负责人同时改同一条时不会悄悄覆盖） |
| D89 | 人离开或被移出时，他的 Agent 怎么办 | 一起移出；至少让代看、接管、耳语、改 Agent 策略都要求负责人本人仍是成员 |
| D90 | 普通成员拉自己的 Agent 时能给多少历史 | 不超过拉人者自己能看到的范围 |
| D91 | 撤回、解散时 Webhook 发件箱里还没送出的内容 | 一起清理（或改为发墓碑），和 GDPR / DSA 要求一致 |
| D92 | 离线期间被移出又拉回，移出前那段要不要补发 | 补发到移出点为止（那段本来就有权看） |
| D93 | 自己发言是否算"已读到这里" | 算（Slack、Telegram 的做法） |
| D94 | 令牌过期 | 加可配置的空闲过期和绝对过期，默认 30 天空闲 / 1 年绝对 |
| D95 | 人类用户的限流默认值 | 每用户每秒 10 条、突发 30 条；每用户最多 10 个连接；建群成员列表最多 1000 人（都可配置） |
| D96 | MCP 的 `get_updates` 在同一次调用里确认 | 现在的取舍（响应丢了可以用历史接口再读到）已写在 docs/03-agents.md §2.2；建议改成"下一次调用时确认上一批"，彻底不丢 |

## 4. 建议的处理顺序

1. **高**（H1–H6）和 **M1、M3、M4、M9、M11**：影响安全、隐私或用户直接看得到，而且修起来都不大。建议在工具网关之前先修掉（[06 §3](../06-plan.md) 第 0 步）。
2. 其余"中"：随相关功能一起修（同步类随集群 C0，保留期类随 GDPR）。
3. "低"和性能：排进对应模块。

每一条修的时候都按 CLAUDE.md：先写一个能失败的测试复现，再修；三种数据库、Linux 和 Windows 都跑；竞争类的做变异检查；覆盖情况写进 05 §5。
