# 02 架构

> 版本 v0.3（2026-10-10）。§1–§5 已实现并通过测试（代码在 `server/`）；§4.8 的进一步优化是**待确认的方案**；§6、§7 是集群阶段的目标架构（§7 的方案待确认：D69）。

## 1. 设计原则

1. 按会话分片，只保证会话内有序。
2. seq 分配和持久化在同一个事务里完成；**持久化（fsync）之后才 ACK**。
3. 推送只是通知，拉取才是真相。推送可以丢，正确性由拉取保证。
4. 只有存储层是强一致的；路由、在线状态、流式缓冲都是软状态，丢失后可以重建。
5. Agent 在 IM 外部运行，模型的延迟和故障不会传导到消息核心。
6. 过载时拒绝请求，不排无界队列（稳定性优先于吞吐）。
7. 开源核心的边界落在 trait 上，企业功能以插件形式实现。

## 2. 消息模型

### 2.1 主日志：会话事件序号

每个会话一条事件日志。`conv_seq` 是**事件序号**，单调递增、没有空洞，所有成员看到的都一样。

| 事件 | 含义 |
|---|---|
| `conv.created`、`conv.updated` | 会话创建、属性变化 |
| `member.joined`、`member.left`、`member.policy` | 成员变更、Agent 策略变化 |
| `msg.created` | 新消息。流式消息在开始时创建，`state=streaming` |
| `msg.updated` | 编辑、流式结束、审核替换（`version+1`） |
| `msg.recalled` | 撤回（内容清空） |
| `agent.state` | 接管、交还、熔断、护栏重置（对全员可见，保证透明） |

消息另有一个不变的 `created_seq`，表示它在会话中的位置。**展示按 `created_seq` 排序，同步按事件 `conv_seq` 进行。** 客户端只维护一个 `last_seq`，增量拉取就能拿到"新消息 + 旧消息的变化"。

### 2.2 侧信道：定向可见内容

每个会话还有一条侧信道，序号是 `side_seq`。存放只有部分人可见的内容：耳语、仅某人可见的消息、审批草稿、护栏和过滤的私有通知。每条侧信道事件带两个字段：

- `audience`：可见者列表。
- `anchor_seq`：产生时主日志的最新 seq。

Agent 和审批人按 `(anchor_seq, side_seq)` 把两条日志归并，得到完整上下文。普通成员拿不到侧信道，所以**主日志对每个成员都没有空洞，也不泄露"这里有一条你看不到的消息"**。

### 2.3 消息字段

```
Message {
  tenant_id, conv_id, msg_id, created_seq,
  sender_id, sender_type,      // human | agent | system，由服务端按认证身份写入
  on_behalf_of,                // Agent 代表谁发言（只能是它的所有者或委托人）
  kind,                        // text | interactive | tool_call | tool_result | thinking | ...
  content, version,
  state,                       // committed | streaming | complete | cancelled | failed | recalled
  state_reason,                // timeout | disconnected | cancelled_by:<name> | policy:... | taken_over
  hop, causation_id,           // 由服务端计算，用于循环熔断
  reply_to, mentions,
  ai_generated,                // 机器可读的 AI 标记（EU AI Act 第 50 条）🔧
  created_at, updated_at       // 由写入方（单机为写线程，集群为 leader）赋值
}
```

### 2.4 成员生命周期与用户目录（D12，已实现）

参考 Slack（私有频道）、WhatsApp、Discord 的通行做法。测试见 [05 §5](05-operations.md)（`tests/membership.rs`）。

| 操作 | 谁能做 | 结果 |
|---|---|---|
| `remove_member` | 群主和管理员；成员可以移除自己拉进来的 Agent | 主日志写 `member.removed`；被移除的人立刻收不到推送，也不能再拉取（与 Slack 私有频道一致：离开后看不到这个会话） |
| `leave` | 任何成员（群主要先转让） | `member.left`；同上 |
| `set_role` | 群主 | 角色：群主、管理员、成员；管理员可以拉人、移除普通成员、撤回他人消息 |
| `transfer_owner` | 群主 | 群主变更事件 |
| `dissolve` | 群主 | `conv.dissolved`；所有成员失去访问；内容按保留策略处理（默认立即删除正文，保留"这个会话存在过"的审计记录；企业版的法律保全会阻止删除） |
| `block` / `unblock` | 任何人 | 被拉黑的人不能和你建单聊，不能给你发仅你可见的消息，@你不会通知你；共同群里的消息照常（由客户端选择折叠）。App Store 要求有拉黑功能 |
| 单聊 | — | 同一对用户只有一个单聊：再次创建会返回已有的单聊 |

**Agent 被移除时**：取消它进行中的流，丢弃它待审批的草稿，结束它的任务（标为取消，原因"已移除"）。

**用户目录**：`hello` 不再返回所有用户，只返回和你有共同会话的人、你的 Agent，以及同一单元里允许互相发现的人。找新的人用 `find_user`，按精确的用户名或邮箱查，并受单元的可见性策略限制（企业版的信息屏障在此基础上叠加）。

**并发不变量**（配套并发测试）：`member.removed` 的 seq 为 N 时，被移除者不会出现 seq 大于 N 的消息；移除与该成员的发送同时发生时，结果只有两种：消息在移除之前落库，或者发送被拒绝。这一点由单写者保证：移除和发送在同一个写线程里串行执行。

### 2.5 协议版本管理（D19，握手已实现）

**目标**：新服务端能服务老客户端；新功能在老客户端上不出错、不丢信息；破坏性改动有章法、有过渡期；客户端可以准确知道服务端支持什么。

**业内做法**：

| 系统 | 做法 |
|---|---|
| Matrix | `/versions` 列出服务端支持的全部规范版本；实验功能用带命名空间的 `unstable_features` 声明，列表里没有就表示不支持；事件类型带命名空间；富内容事件必须带纯文本 `body` 作为兜底 |
| Slack Block Kit | 带 `blocks` 的消息必须同时给 `text`，客户端渲染不了 blocks 时显示 `text`；手机通知只用 `text` |
| XMPP | 服务发现（XEP-0030）：每一端声明自己支持的功能，对方按此决定发什么 |
| A2A v1.0 | 版本只用"主版本.次版本"，补丁号不影响兼容；请求头 `A2A-Version` 协商版本 |
| Protocol Buffers | 新增字段不破坏老代码，老代码保留并忽略不认识的字段 |

**方案**：

| 方面 | 规则 |
|---|---|
| 版本号 | 协议用整数主版本（`v1`、`v2`）。主版本内只做向后兼容的新增；服务端软件版本用语义化版本号（`1.4.2`），和协议版本分开 |
| 握手 | 连接时客户端带上：协议主版本列表、客户端名称和版本、平台、支持的功能列表。服务端在 `welcome` 里回复：选定的协议版本、服务端版本、**服务端支持的功能列表**、要求的最低客户端版本 |
| 功能声明 | 新功能用带命名空间的功能名声明，例如 `files`、`reactions`、`tasks`；实验功能用 `x.<域名>.<名字>`。客户端只使用服务端声明过的功能。服务端也知道每个会话支持什么，据此决定怎么推送 |
| 太老的客户端 | 低于最低版本时，握手返回 `client_too_old`，带上升级说明；不会让它在半兼容的状态下运行 |
| 主版本内允许的改动 | 新增可选字段、新事件类型、新操作、新错误码、新的功能名 |
| 主版本内禁止的改动 | 删除或改名字段、改变字段含义或类型、把可选改成必填、改变已有错误码的含义 |
| 客户端必须遵守 | 忽略不认识的字段；不认识的事件类型或消息类型显示降级文本（见下）；不认识的错误码按通用错误处理。这些写进协议文档，SDK 默认就这样做 |
| 降级显示 | 每条消息都必须带纯文本的 `fallback`（服务端在缺失时拒绝）。新消息类型（卡片、投票、自定义类型）在老客户端上显示 `fallback`，例如"[投票] 午饭吃什么？请升级客户端查看" |
| 未知操作 | 返回专门的 `unknown_op`（而不是笼统的 `bad_request`），客户端能区分"服务端太老"和"请求写错了" |
| 弃用 | 宣布弃用后至少保留 12 个月，且至少跨一个主版本；服务端同时支持当前主版本和上一个主版本；弃用的用法会在响应里带提示，并计入指标，方便运营者知道还有多少老客户端 |
| 存储兼容 | 数据库表结构有版本号，启动时自动迁移；新版本服务端能读老版本写的数据；集群阶段支持滚动升级（新旧节点同时在线时读写都兼容） |
| 文档与测试 | 协议用 AsyncAPI（WebSocket 版的 OpenAPI）描述，并生成文档；CI 里保留**上一个版本的 SDK 和场景测试**，每次都用它们测新服务端，确认老客户端不被破坏 |

**已实现**（`server/crates/agentim-core/src/protocol.rs`，测试见 `tests/protocol.rs`）：

| 环节 | 行为 |
|---|---|
| 连接 | `GET /ws?token=…&v=2,1` 可选带上客户端支持的协议版本（最多 16 个）；没有共同版本时在升级前返回 HTTP 400 `unsupported_protocol`，格式错误返回 400 `bad_request`，两者都附带服务端支持的 `protocols` |
| `welcome` | `protocol`（选定版本）、`protocols`、`server {name, version}`、`features`、`limits {message_bytes, frame_bytes}`、`me` |
| `hello` | 可选 `protocol: [..]`、`client {name, version, platform}`、`features: [..]`；回复同样的服务端信息加上 `me`、`users`、`my_agents`。不带这些字段的老客户端照常工作（得到当前版本）。重复 `hello` 以最后一次为准；被拒绝的 `hello` 不改变连接的状态 |
| 最低版本 | 配置 `[clients.min_versions]`（如 `agentim-js = "1.2.0"`，启动时校验格式）；低于最低版本返回 `client_too_old`（带升级说明），随后服务端以关闭码 1008 断开。配置了最低版本的客户端必须带可比较的版本号，否则 `bad_request`；没配置的客户端名不检查 |
| 限制 | 名称、版本、平台各不超过 64 字节；功能最多 100 个，每个 1–64 字节 |
| 未知操作 | 服务端不认识的 `op` 返回 `unknown_op`；认识的操作缺字段或类型错误仍是 `bad_request`。`OPS` 列表和请求解析器由单元测试保证完全一致 |
| 未知字段 | 忽略（主版本内的向前兼容） |
| 指标 | `agentim_clients_total{protocol, client}`；客户端名只有小写字母、数字和 `._-`、不超过 32 字节时才原样作为标签，否则记为 `other` |

还没做：弃用提示、上一版 SDK 的兼容性测试（SDK 发布后加入 CI）、AsyncAPI 文档。

### 2.6 扩展机制（D20，MVP 1 部分已实现）

**目标**：开发者不改服务端代码，就能加入自己的消息类型和功能，而且不破坏顺序、权限、审计、加密这些核心保证。

| 扩展点 | 做法 | 业内参考 |
|---|---|---|
| **自定义消息类型** | `kind` 可以是内置类型（`text`、`file`、`image`、`card`……），也可以是带命名空间的自定义类型，例如 `com.acme.order`。内容是 JSON 对象（大小受限），**必须带 `fallback` 纯文本**。和普通消息一样进主日志、占 seq、能编辑撤回、受权限和审计约束 | Matrix 的命名空间事件类型、Slack 的 `text` 兜底 |
| 类型注册（可选） | 管理员可以为自定义类型注册 JSON Schema：服务端据此校验内容，并标注哪些字段要过 DLP、哪些字段 Agent 可见。可以配置"只允许已注册的类型"（企业常用） | |
| **自定义信号** | 不落库、不占 seq 的轻量事件，只推给在线的成员，例如"正在绘制""共享光标位置"。同样带命名空间，有频率限制 | Matrix 的 ephemeral 事件 |
| **交互消息** | 卡片带按钮或表单；用户点击后，服务端把动作发给发消息的 Agent 或 Webhook，结果作为新消息或更新回到会话 | Slack Block Kit 的交互 |
| **Webhook** | 订阅事件（新消息、成员变化、任务变化等），服务端用签名的 HTTP 请求推送，失败自动重试，按 seq 可以补拉。适合不想维持长连接的集成 | Slack Events API、GitHub Webhooks |
| **服务端插件** | MVP 1：Rust trait（编译进服务端，用于企业定制的过滤、审批、审计导出）。MVP 2：WASM 插件，在沙箱里运行，限制内存、CPU 时间和可调用的接口，运行时加载、不用重新编译。候选运行时是 Wasmtime，或者基于它的 Extism（多语言插件开发包） | Envoy 的 proxy-wasm、Extism |
| Agent | Agent 本身就是一种扩展：用 SDK 或 MCP 接入即可（[03 §9](03-ai-native.md)） | |

**已实现：自定义消息类型**（测试见 `tests/extensions.rs`）

| 环节 | 行为 |
|---|---|
| 发送 | `send` 可选 `kind` 和 `payload`。`kind` 缺省或为 `text` 时不能带 `payload`。自定义类型必须带命名空间：至少两段、以点分隔，每段以小写字母开头、只含 `a-z0-9_-`，总长不超过 64 字节，`agentim.` 保留给内置类型。`payload` 必须是 JSON 对象，序列化后不超过 32 KiB，也可以不带。`text` 照常必填，就是老客户端显示的降级文本 |
| 存储与读取 | `payload` 和消息写在同一个事务（表结构 v2 的 `messages.payload`），推送、同步、重启后都原样返回；去重、seq、权限和普通消息完全一样 |
| 编辑 | `edit` 可以带新的 `payload` 替换旧的；不带就保留。纯文本消息带 `payload` 返回 `bad_request` |
| 撤回 | 数据库里的 `payload` 清空，此前所有事件快照里的 `payload` 也清空 |
| 仅某人可见 | 侧信道事件里带上 `kind` 和 `payload` |
| 审批 | 草稿保存 `kind` 和 `payload`（`drafts.kind`、`drafts.payload`），批准后照原样发布；批准时改的只是降级文本 |
| 内容策略 | Agent 发送和编辑时的 DLP、Agent 读取时的注入检测，都同时检查文本和 `payload` |

**已实现：信号**

`signal {conv_id, kind, data?}`：`kind` 是内置的 `typing` 或带命名空间的自定义类型；`data` 是不超过 4 KiB 的 JSON 对象。只推给此刻在线的其他成员（同一用户的所有连接，包括 Agent），不推回发送者；不落库、不占 seq、不进侧信道，之后连上的人也收不到。非成员 `forbidden`，会话不存在 `not_found`，单聊里任一方拉黑了对方 `blocked`（群聊不受影响）。每个连接每秒最多 20 个，超出 `rate_limited`。推送帧：`{"type": "signal", "conv_id", "kind", "from", "data"}`。

**已实现：Webhook**（测试见 `tests/webhooks.rs`；业内参考：Standard Webhooks 规范、Stripe、Svix 的 outbox 做法）

| 方面 | 行为 |
|---|---|
| 配置 | `[[webhooks]]`：`name`、`url`、`secret`（至少 16 字节）、`events`（`msg.created` 这样的精确类型、`msg.*` 前缀或 `*`）、`max_attempts`（默认 8）、`timeout_ms`、`backoff_ms`。开放 API 做好后改为按应用管理 |
| 不丢 | 订阅的事件和事件本身在**同一个事务**里写进 `webhook_outbox`（每批一条多行 INSERT）。没提交的写入、被拒绝的请求都不会发出去 |
| 有序 | 每个 Webhook 在每个数据库上有一个投递任务，按提交顺序一条一条发；前一条没成功不会发下一条 |
| 至少一次 | 成功后通过写线程移动游标（`meta` 里的 `webhook:<name>`）。重启后从游标继续；接收方用 `webhook-id` 去重 |
| 签名 | 请求头 `webhook-id`、`webhook-timestamp`、`webhook-signature: v1,<base64(HMAC-SHA256(id.timestamp.body))>`，和 Standard Webhooks 一致，现成的验签库可以直接用 |
| 请求体 | `{"type", "timestamp", "database", "data": {"conv_id", "seq", "event"}}` |
| 重试 | 非 2xx 或超时就按指数退避重试（最长 5 分钟一次）；超过 `max_attempts` 次后放弃这一条，写审计 `webhook.dropped`，计入 `agentim_webhook_dropped_total`，然后继续发后面的。接收方可以用开放 API 的历史接口按 seq 补齐 |
| 清理 | 所有 Webhook 都处理过的行立即删除 |
| 新增 Webhook | 从当前位置开始，不重放历史 |
| 多库 | 每个库有自己的 outbox 和投递任务，`database` 字段标明来源 |

**已实现：发送前拦截**

`[before_send]`：`url`、`secret`、`timeout_ms`（默认 2000）、`on_error`（`allow` 或 `reject`）。每条 `send` 在进入写线程**之前**同步调用（不占写线程，组提交不受影响），请求带同样的签名头，内容为 `{"type": "message.before_send", "conv_id", "client_msg_id", "kind", "text", "payload", "reply_to", "to_user", "sender"}`。回复 `{"action": "allow"}`、`{"action": "reject", "reason"}`（返回 `policy_blocked` 和这个原因）或 `{"action": "replace", "text", "payload"}`（替换后照常校验，非法就 `bad_request`）。超时、非 2xx、不是 JSON、未知的 action 都按 `on_error` 处理。格式不对的请求先被拒绝，不会发给钩子；成员、拉黑等规则在钩子之后照常检查。编辑和流式消息不经过钩子。

**自定义字段**（M3 已实现）：用户和会话都可以挂一个不超过 4 KiB 的 JSON 对象，通过开放 API（`PUT/PATCH /v1/users/{id}`、`PATCH /v1/conversations/{id}`）或客户端的 `update_conv` 修改，会话的修改以 `conv.updated` 事件通知成员。

**扩展也要守住核心保证**：自定义消息走同一条写入路径（单写者、组提交），所以同样不丢、有序；内容大小和信号频率都有上限；端到端加密的会话里，自定义内容整体加密，服务端只校验大小；扩展类型的版本放在类型的内容里（例如 `schema_version`），兼容规则和 §2.5 相同。

### 2.7 文件和图片（M5，方案待确认：D27–D30）

**业内做法**

| 产品 | 上传 | 下载与权限 | 其他 |
|---|---|---|---|
| Slack | 两步：先申请上传地址并上传，再"完成上传"时指定频道 | 需要登录；对外分享另发链接 | 单文件上限 1 GB；EKM 下文件也用客户密钥加密 |
| Matrix | 先上传到媒体库拿到 `mxc://` 地址，再发消息引用 | 1.11 起下载也要认证（以前任何人拿到地址都能下载） | 服务端生成固定几档缩略图；E2EE 时文件由客户端加密 |
| Mattermost | 先上传（带频道 ID），再发帖引用 | 只有频道成员能下载 | 默认上限 100 MB；本地磁盘或 S3；服务端生成缩略图和预览图 |

结论：**先上传、再发消息引用**是通行做法；文件要绑定到会话，下载按会话成员权限判断；服务端生成缩略图。

**方案**

| 方面 | 做法 |
|---|---|
| 流程 | ① `POST /api/files?conv_id=…`（客户端令牌）或开放 API `POST /v1/files`（以某个用户的身份）流式上传，返回 `file_id`；② 发送 `kind = "file"` 或 `"image"` 的消息，payload 里带 `file_id`，服务端补上名字、大小、类型、宽高、缩略图信息，`fallback` 是 `[文件] 名字`。上传时就要指定会话，只有能在这个会话发言的人能上传 |
| 一个文件一条消息 | 文件只能被一条消息引用（转发是以后的功能，到时复制一份）。两条消息同时引用同一个文件，只有一条成功（`conflict`） |
| 存放位置 | 文件的元数据（`files` 表）放在会话所在的库，内容放在这个库配置的存储里：本地磁盘或 S3 兼容存储（AWS S3、MinIO、Cloudflare R2、阿里云 OSS 等，用 `object_store` 库，GCS / Azure 也能接）。专属库可以配专属的存储桶，和 §5.4 的物理隔离一致 |
| 加密 | 静态加密开启时文件内容也加密：用会话的 DEK，按 64 KiB 分块 AES-256-GCM，每块的 AAD 是（文件 ID、块序号、是否最后一块），块不能被调换、截断或拼接。存储桶里只有密文，下载时边解密边输出，支持 `Range` |
| 不丢 | 内容完整写入（本地 fsync 后改名，S3 完成分片上传）之后，才通过写入线程提交 `files` 记录；记录提交了内容一定在。只写了内容、记录没提交的残留由后台清理 |
| 删除 | 撤回消息、解散会话、删除账号时，`files` 记录和"待删除"任务在同一个事务里提交，存储里的内容由后台删除（失败重试，重启后继续）。解散会话本身已经删除 DEK，存储里残留的密文也解不开 |
| 未使用的上传 | 24 小时内没有被消息引用就删除（D28）。后台清理和"发消息引用它"同时发生时，只有一个成功 |
| 下载权限 | 上传者本人，或者引用它的消息对你可见（会话成员，且这条消息在你加入之后，或会话允许看历史）。权限按每次请求判断：被移出会话后立刻不能下载 |
| 下载链接 | 浏览器的 `<img>` 不能带令牌，所以用短期签名链接：客户端请求 `file_url {file_id}`，服务端检查权限后返回 5 分钟内有效、绑定用户和文件的链接（HMAC）。链接泄露的影响限于 5 分钟 |
| 类型判断 | 不相信客户端声明的类型，按文件头判断。只有 JPEG、PNG、WebP、GIF 算图片；SVG、HTML 等一律当普通文件，下载时 `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: sandbox`，防止在我们的域名下执行脚本 |
| 缩略图 | 图片上传时生成两档（长边 320 和 1280 像素，WebP），和原图一样加密存放。解码前先读尺寸，超过 4000 万像素或解码失败就不生成缩略图（防"解压炸弹"），文件照常可以下载。生成在写入线程之外进行 |
| 位置信息 | 默认去掉图片里的 EXIF / XMP（含 GPS 位置）（D29）：JPEG、PNG、WebP 都是无损去掉元数据段，不重新压缩 |
| 限制 | 单个文件默认 100 MB（D28，可配置）；每人每天上传总量、Agent 的上传频率都有上限（复用现有限流）；文件名最长 255 字节，去掉路径和控制字符 |
| AI 生成内容 | Agent 上传的文件在元数据里标记 `ai_generated: true`，客户端据此显示标记（EU AI Act 第 50 条要求 AI 生成内容可以被机器识别）；嵌入 C2PA 放到以后 |
| 病毒扫描 | 提供一个可选的扫描钩子（和发送前拦截一样的 HTTP 回调，可以接 ClamAV 等）；没有扫描结果之前文件不能被引用；扫描服务出错时按配置拒绝或放行（D30） |
| 断点续传 | M5 只支持一次请求传完（流式，不占内存）；tus 断点续传和手机端一起放到 MVP 2（D27） |
| 多库迁移 | 会话迁移到另一个库时，`files` 记录和 DEK 随会话走，内容复制到目标库的存储，复制完成后才切换，然后删除旧存储里的内容 |
| 集群 | 本地磁盘只适合单机；集群部署要求用 S3 兼容存储，所有节点共享 |

**测试要覆盖的逻辑节点**：上传（权限、大小上限、空文件、未知会话、被拉黑、已解散）；发消息引用（别人的文件、别的会话的文件、已被引用、已过期、扫描未通过）；拉取、推送、侧信道（仅某人可见的文件消息）、草稿（Agent 草稿带文件，批准后才可见）、编辑（不能改附件）、撤回（文件随之删除、下载立刻失败）；下载（成员、非成员、被移出、加入前的消息、签名过期、签名被改、Range 边界）；解散（加密销毁）；重启（未完成的删除继续）；多库迁移；审计；开放 API 上传；静态加密开和关；本地磁盘和 S3（CI 里用 MinIO）。并发：两条消息抢同一个文件、清理和引用、撤回和下载、解散和上传，各重复多轮后检查"只有一个成功、存储里没有孤儿"。

## 3. 可靠性与顺序（已实现）

| 机制 | 说明 |
|---|---|
| 持久化后 ACK | 写事务提交后才回 ACK |
| 去重 | `(conv_id, sender_id, client_msg_id)` 与消息写在同一个事务；重试返回原 seq |
| 推拉结合 | 推送携带 seq；客户端发现空洞就拉取；重连按 `last_seq` 补齐 |
| 发送方顺序 | 同一连接的请求按到达顺序串行处理 |
| 流式 | 开始即占位（分配 seq）；增量不占 seq，按 `(msg_id, idx)` 幂等追加；每秒写一次检查点；结束时 `msg.updated` |
| 崩溃恢复 | 启动时把残留的 `streaming` 消息标为 `failed(server_restart)`，内容保留到最后一个检查点 |
| 未读数 | 只统计别人发的、未撤回的新消息，不受编辑和系统事件影响 |

已验证：`kill -9` 后已 ACK 的消息全部保留；并发压测中 seq 连续、每条消息恰好一次、推送有序。详见 [05 运维](05-operations.md) §5。

## 4. 写入路径与组提交（已实现）

### 4.1 改造前的问题

改造前，每个操作都是一个独立事务，每个事务一次 fsync（SQLite WAL，`synchronous=FULL`），而且全部在一把全局锁里串行执行；扇出（给每个连接序列化并推送）也在锁里。CI 实测：200 个客户端时吞吐 284 条/秒，ACK p50 387ms、p99 1.03s。

### 4.2 业内做法

| 系统 | 做法 |
|---|---|
| PostgreSQL | 天然组提交：在一次 WAL flush 进行期间准备好的事务，会搭上同一次 flush。`commit_delay` 让领头者先等一小会儿再 flush，以凑更多事务，但会给每次 flush 增加延迟，官方建议默认设为 0 |
| MySQL / MariaDB | binlog 组提交：分 flush、sync、commit 三个阶段，第一个到达的事务做领头者，替整组执行 fsync。`innodb_flush_log_at_trx_commit=1` 加 `sync_binlog=1` 才是完整持久化 |
| SQLite | 单写者，引擎层没有组提交。业界做法是在应用层用单个写线程，把多个操作合并进一个物理事务 |
| Raft（openraft 等） | 把多个提案批量追加到日志，一次落盘 |

还有一个不能忽视的教训：PostgreSQL 的 "fsyncgate" 事件说明，**fsync 失败后不能重试**，因为内核可能已经丢弃了脏页。正确做法是让进程崩溃，再从日志恢复。

### 4.3 方案：单写者 + 组提交 + 锁外扇出

```
 连接（按到达顺序）                写线程（每个存储分片一个）
 ──cmd──▶ 有界命令队列 ──▶ ┌────────────────────────────────────────┐
                           │ 取出第 1 条，再取走队列里已有的命令      │
                           │ （最多 512 条或 1MB；默认不额外等待）    │
                           │ BEGIN                                  │
                           │   SAVEPOINT; cmd1; RELEASE（失败只回滚它）│
                           │   SAVEPOINT; cmd2; RELEASE              │
                           │   …                                     │
                           │ COMMIT  ← 整批一次 fsync                 │
                           └──────┬─────────────────────────────────┘
                                  │ 提交成功后：按顺序回 ACK + 已提交事件
                                  ▼
                          扇出任务：每个事件只序列化一次（共享字节）
                          → 每个连接一个有界发送队列
                          → 队列满：丢弃推送，发 resync 标记（客户端去拉取）

 读请求（pull、list）──▶ 读连接池（WAL 允许并发读，不经过写线程）
 流式增量 ──▶ 直接进扇出（不落盘）；检查点作为普通写命令批量提交
```

**批量策略（借鉴 PostgreSQL 的领头者模式）**：写线程取到第一条命令后，只拿走"此刻已经在队列里"的命令，不额外等待。所以低负载时延迟等于一次 fsync，不会因为批量而变慢；高负载时一批里的命令自然变多，吞吐约等于"批大小 / fsync 延迟"。`commit_delay_us` 作为可选参数，默认 0。

### 4.4 正确性论证（G2 不丢、G3 有序、G4 正确）

| 风险 | 处理 |
|---|---|
| ACK 早于落盘 | 只有在 `COMMIT` 返回之后才回 ACK，并推送事件 |
| 一条命令失败拖垮整批 | 每条命令一个 SAVEPOINT，失败只回滚它自己，返回错误 |
| 回滚的命令占用了 seq，留下空洞 | seq 计数器存在数据库行里，在 SAVEPOINT 内递增，回滚会一起撤销。内存里的缓存值也要随之回滚 |
| 批内重复的 `client_msg_id` | 命令按顺序执行，后一条能看到前一条写入的去重记录 |
| 整批提交失败（磁盘满、fsync 报错） | 整批命令都返回错误，客户端用同一个 `client_msg_id` 重试。fsync 报错视为致命错误：停止接受写入，`/readyz` 失败，进程退出后由 systemd 拉起，再从 WAL 恢复（吸取 fsyncgate 的教训） |
| 同一连接的消息乱序 | 每个连接串行把命令放进队列；写线程按 FIFO 执行；ACK 按顺序返回 |
| 推送乱序 | 扇出任务按提交顺序处理事件；每个连接的发送队列是 FIFO |
| 慢客户端拖垮内存（G1） | 发送队列有界；满了就丢弃推送，发 `resync`，让客户端走拉取补齐 |
| 写入过载（G1） | 命令队列有界；满了就返回 `overloaded`，客户端退避后重试（幂等） |

运行时状态（流式缓冲、护栏计数、成员缓存）由各自的写线程独占；在线连接注册表单独加锁，只在提交后的扇出时使用。

实现时补充的两条规则：

| 风险 | 处理 |
|---|---|
| 被拒绝的请求，有些记录必须保留（熔断事件、DLP 拦截的审计、流式过程中的内容替换） | 命令可以标记"出错也提交"：返回错误，但它的写入随批次一起提交 |
| 迁移切换前已经按旧路由排队的写请求，在切换后才执行，写进即将删除的旧副本（测试中发现的会丢消息的竞态） | 写线程执行任何会话操作前，先确认会话当前归属本库，否则返回 `conv_moved`，由 hub 按新目录重新路由。对应测试连续跑 30 轮无失败 |

### 4.5 不采用的方案

| 方案 | 不采用的原因 |
|---|---|
| `synchronous=NORMAL` | 断电后会丢失已 ACK 的事务，违反 G2 |
| 先 ACK 后 fsync | 违反 G2 |
| 多线程同时写 SQLite，靠 busy 重试 | SQLite 是单写者，增加线程不会提升写吞吐，只会带来锁竞争 |
| 固定等待 N 毫秒再提交 | 低负载时白白增加延迟。可以作为可选参数，默认关闭 |

### 4.6 与 PostgreSQL / MySQL、集群的关系

- **PostgreSQL / MySQL**：数据库本身就会做组提交，我们的批量还能额外减少网络往返。它们支持并发写，所以可以按会话哈希开 N 个写线程（同一会话永远落在同一个写线程，顺序不变）。SQLite 固定为 1 个。
- **集群**：一个写线程 = 一组会话分片的写入归属者（§7）。集群时只是把"哪个节点持有这个写线程"交给数据库锁和租约决定，命令接口不变。所以这次重构同时是集群化的前置工作。

### 4.7 验收结果

- 正确性：崩溃恢复（`kill -9`，Linux 和 Windows 同一份测试）、并发一致性、故障注入（提交失败时不发 ACK、不推送、该库停止写入、`/readyz` 失败、重启后恢复）全部通过，在 SQLite、PostgreSQL 16、MariaDB 10.11 上都跑了。
- 组提交生效：16 个并发发送方的测试中，提交次数明显少于命令数。
- 性能（开发容器，4 核，release 构建，SQLite；压测程序和服务端在同一台机器上）：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 10 客户端各自写入（无扇出） | 211 条/秒，p50 44ms | 1,114 条/秒，p50 7.6ms，p99 13ms |
| 50 客户端同群 + 10 路流式 | 573 条/秒，p99 153ms | 1,060 条/秒，p99 68ms |
| 200 客户端同群 + 20 路流式 | 127 条/秒，p99 2.5s | 536 条/秒，p99 1.1s |

改造过程中还找到一个与 fsync 无关的延迟来源：服务端和客户端都没有开启 `TCP_NODELAY`，Nagle 算法加上延迟确认，让每个请求往返多出约 40ms。已经修复。

### 4.8 剩余瓶颈与下一步（待确认）

**fsync 已经不是瓶颈**：本机 fsync 约 0.1ms，平均每批约 15 条命令，提交耗时约 1ms。现在的瓶颈有两个：

1. **每条 SQL 语句的固定开销**。实测通过 sqlx 访问时，SQLite 每条语句约 31µs，PostgreSQL 约 100µs，MySQL 约 66µs。一次发送大约要执行 9 条语句，再加上 SAVEPOINT，每条命令在写线程里约 0.7ms，所以单库上限大约是每秒 1,300 条命令。sqlx 的 SQLite 驱动在独立线程上执行语句，每条语句都要跨线程往返一次，这是它开销大的原因。
2. **大群扇出**：200 人的群里每条消息要推给 220 个连接。这个场景里压测程序占了约 2.3 个核，服务端约 0.9 个核，测到的主要是压测机本身的上限。要得到准确的数字，需要把压测程序和服务端放在不同的机器上。

可选的优化（需要你确认方向）：

| 方案 | 预期收益 | 代价 |
|---|---|---|
| A. 减少每条命令的语句数（`RETURNING` 取 seq、人类消息跳过因果推断查询、合并插入） | 约 1.3–1.5 倍 | 小 |
| B. SQLite 写线程改用原生驱动（rusqlite），每条语句约几微秒 | 约 5–10 倍（单 SQLite 库） | 要为 SQLite 单独维护一份写路径实现，三种数据库就不再共用同一套写入代码 |
| C. PostgreSQL / MySQL 按会话哈希开多个写线程（§4.6） | 随 CPU 核数线性增长 | 中；同一会话固定落在同一个写线程上，不影响顺序 |
| D. 扇出移出写线程，交给独立任务，并按网关聚合 | 降低大群场景的 ACK 延迟 | 中；集群阶段本来就要做 |

建议顺序：先做 A 和 D（风险低），生产环境推荐 PostgreSQL 并配合 C；B 等有明确的单机 SQLite 高吞吐需求时再做。

## 5. 存储抽象（已实现）

### 5.1 目标

SQLite 用于单机和小规模部署，PostgreSQL 推荐用于生产（Matrix Synapse 的官方建议也是生产环境用 PostgreSQL，SQLite 只用于测试或轻负载），MySQL 也要支持。三者的语义必须完全一致。

### 5.2 业内选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| Diesel | 成熟，编译期检查的 DSL，支持三种数据库 | 同步；多后端泛型写法繁琐 |
| SeaORM | 异步，换数据库只需改 feature | ORM 抽象偏重；对事务、SAVEPOINT 的精细控制不如直接写 SQL |
| sqlx | 异步、纯 Rust，直接写 SQL，支持三种数据库 | 方言差异（占位符、upsert、类型）要自己处理 |
| sqlx + sea-query | sea-query 负责生成各方言的 SQL，sqlx 负责驱动和连接池 | 多一个依赖 |

### 5.3 方案

```
hub（业务逻辑） ──▶ trait Storage（领域接口，不出现 SQL）
                     ├─ 写：begin_batch() → WriteTx
                     │      next_seq / append_event / insert_message / update_message /
                     │      append_side / dedup / drafts / takeovers / audit / savepoint / commit
                     └─ 读：pull / pull_side / members / convs_for / unread / ...
                            │
                 SqlStorage（一套实现：sea-query 生成方言 SQL + sqlx 连接池）
                     ├─ SQLite（默认，单二进制内嵌）
                     ├─ PostgreSQL（生产推荐）
                     └─ MySQL / MariaDB（InnoDB、utf8mb4）
```

**与确认时方案的差异**：没有引入 sea-query。业务 SQL 都很简单，三种数据库的差异只有占位符（PostgreSQL 用 `$n`）、列类型（MySQL 用 `LONGTEXT`，主键列用 `VARCHAR`）和建索引的写法（MySQL 不支持 `CREATE INDEX IF NOT EXISTS`，改为在建表语句里声明）。这些由 `storage.rs` 里一个很小的方言层处理；需要 upsert 的地方，在写线程里改成"先查后写"（写线程是单一的，不存在竞争）。业务 SQL 只有 `db.rs` 一份。

- **数据库层**：`storage.rs`（方言、连接、建表、持久化检查）和 `db.rs`（全部业务 SQL）。业务逻辑（`logic.rs`）只调用 `db.rs` 的函数，看不到 SQL。
- **表结构升级**：见下面的"表结构版本与自动迁移"。
- **持久化配置检查**（G2）：启动时检查。SQLite 要求 `synchronous=FULL`；PostgreSQL 要求 `fsync=on` 且 `synchronous_commit` 不为 `off`；MySQL 要求 `innodb_flush_log_at_trx_commit=1`，开启 binlog 时还要求 `sync_binlog=1`。不满足就拒绝启动，配置项 `unsafe_durability = true` 可以显式放行，并打印警告。
- **SQLite `secure_delete`**：删除的内容会被覆盖，而不是留在空闲页里。会话迁移到专属库之后，旧库文件里不会残留它的内容（测试会直接读数据库文件确认）。
- **一致性测试套件**：同一套 13 个验收测试分别跑三种后端（`tests/hub.rs`）。CI 在 Linux 上用服务容器跑 PostgreSQL 16 和 MySQL 8.4，并检查没有测试被跳过；SQLite 在 Linux 和 Windows 上都跑。
- **迁移工具**（后续）：SQLite → PostgreSQL 的导出导入工具，类似 Synapse 的 `synapse_port_db`。
- **加密字段**：消息内容等加密后以 BLOB / BYTEA / LONGBLOB 存储，见 [04](04-security-compliance.md) §2。

**表结构版本与自动迁移**（业内参考：Flyway、Liquibase、Synapse 的 schema delta 和 `SCHEMA_COMPAT_VERSION`）

| 方面 | 规则 |
|---|---|
| 版本 | `meta` 表记录 `schema_version`（库的版本）和 `schema_compat`（还能使用这个库的最老的程序所对应的版本）。程序里的 `TABLES` 永远描述最新的表结构，`MIGRATIONS` 按版本列出每一步的变化 |
| 新库 | 直接按最新结构建表，写入最新版本，不重放迁移 |
| 老库 | 启动时在一个事务里按顺序执行缺少的迁移，每做完一个就更新版本号。每个库（控制库和各单元库）各自迁移 |
| 可重入 | 每一步先检查再执行（例如加列前先查列是否已存在）。MySQL 的 DDL 会隐式提交，不能整体回滚，所以中途崩溃后重启必须能接着做完 |
| 并发启动 | 集群里多个节点同时启动时只能有一个在迁移：PostgreSQL 用事务级的 advisory lock，MySQL 用 `GET_LOCK`，SQLite 用 `BEGIN IMMEDIATE` 的写锁 |
| 只做加法 | 主版本内的迁移只能新增表、可为空的列和索引，所以老程序在新库上照样能读写（忽略新列）。这样的迁移不提高 `schema_compat`，滚动升级时新老节点可以同时在线 |
| 破坏性变化 | 删除或改名列、改类型、改含义时提高 `schema_compat`；老程序发现库的 `schema_compat` 比自己新就拒绝启动（`schema_mismatch`），不会写坏数据。这类变化要分两步发布：先发能同时处理新旧结构的版本，再发真正的变化 |
| 启动检查 | 库的版本比程序新、但 `schema_compat` 不比程序新：照常启动并打印警告；否则拒绝启动 |

### 5.4 多库路由：组织单元的物理隔离（方案 A，已实现）

背景：一个集团下有多个子公司（组织单元，见 [04 §5](04-security-compliance.md)）。其中高密级子公司要求数据与其他单元**物理分开存放**，而且不能等集群阶段才实现。

```
                 ┌─ 控制库：租户、单元、用户、Agent、信息屏障规则、
                 │          会话目录（conv_id → 所属单元 → 所在数据库）、成员索引
                 │          （只有 ID 和关系，没有消息内容和会话标题）
AgentIM 进程 ────┼─ 数据库 shared：普通单元的会话          ← 写线程 1
（单机即可）      ├─ 数据库 unit-b：子公司 B 的全部会话     ← 写线程 2（可以放在另一台服务器或另一个地区）
                 └─ 数据库 unit-c：……                     ← 写线程 3
```

**规则**

1. **一个会话只属于一个数据库**，由创建时的所属单元决定。该会话的全部事件（seq、元数据、正文、侧信道、草稿、审计里的内容快照）都写进这个库，由这个库的写线程按 §4 的组提交方式写入。
2. **不拆分单条消息。** 元数据和正文写进同一个库的同一个事务。拆开存放需要跨库的原子写入（两阶段提交），否则会出现"有 seq 没内容"，违反 G2 和 G3；而且元数据本身也是敏感信息。
3. **跨库查询走控制库。** 会话列表、未读汇总这类查询，先查控制库的会话目录和成员索引，再并发访问各个数据库，最后在服务端合并。控制库只存 ID 和关系。
4. **跨单元的会话**：会话属于发起人的单元，存放在该单元的数据库里。其他单元的成员可以加入，但必须先通过信息屏障检查。如果高密级单元的成员要加入低密级单元的会话，按策略二选一：禁止，或者把会话迁移到更严格的库。
5. **升级迁移**：单元从共享库升级到专属库时，按会话逐个迁移：会话先进入只读状态，把数据复制过去并校验内容哈希，再切换控制库里的目录，最后删除旧副本。迁移期间这个会话的写入返回 `conv_migrating`（客户端用同一个 `client_msg_id` 重试即可），其他会话不受影响。集群阶段迁移分片用的是同一套工具，所以从 A 方案可以平滑升级到集群（C 方案）。
   - 用法：修改配置，把单元指向新库，然后运行 `agentim migrate-unit --config agentim.toml --unit <名称>`。P1 要求先停服务再执行；在线迁移的能力已经在库里实现并有测试覆盖，但还没有开放管理接口。
   - 崩溃安全：目录只在新副本校验通过后才切换。任何一步中断，重启时的一致性修复都会把目录指回完整的副本，并删除残留的另一份。
6. **独立的运维边界**：每个库有各自的连接配置、备份策略、加密密钥（L2，见 [04 §5](04-security-compliance.md)）和数据库账号。共享库的数据库管理员没有专属库的访问权限。
7. **故障隔离**：一个库不可用时，只有它上面的会话写入失败（客户端用同一个 `client_msg_id` 重试，去重保证不会重复）。其他库照常工作。`/readyz` 和指标会按库分别报告状态。

**对核心保证的影响**

| 保证 | 影响 |
|---|---|
| G2 不丢 / G3 有序 | 不变：一个会话只在一个库里，用一个写线程，不存在跨库事务 |
| G4 正确 | 会话目录与成员索引在控制库里，读写都要先查目录；目录与数据库不一致时以目录为准并告警 |
| G1 稳定 | 增强：一个库出故障不影响其他库 |
| G5 并发 | 增强：每个库一个写线程，多个库可以并行写入 |
| G6 集群 | 对齐：一个库就相当于一组专属分片，迁移工具与集群共用 |

**不采用的做法**

| 做法 | 原因 |
|---|---|
| 元数据放共享库，正文放到另一个"内容服务" | 需要跨服务的原子写入；元数据同样敏感 |
| 每个子公司一个 PostgreSQL schema，放在同一个库里 | 备份、账号权限、物理位置都无法真正分开；schema 越来越多也难以管理。可以作为 L1 的一个可选实现，但满足不了 L3 |

## 6. 群聊扩散（集群阶段）

消息体一律读扩散（会话日志只存一份），只对"会话有更新"这个信号做有限写扩散，在线推送在网关层聚合。

| | 普通群（≤ 2000 人） | 大群（2000–10 万人） |
|---|---|---|
| 用户同步信号 | 写入成员的"用户收件箱"，同一会话合并为一条 | 不写；成员本地标记为大群 |
| 重连补齐 | 读自己的收件箱 | 批量查询所在大群的 `max_seq` |
| 在线推送 | 网关聚合，逐条推送 | 网关聚合，按时间窗口（如 200ms）合并 seq 通知 |
| 流式增量 | 只推给正在看该会话的人 | 同左 |

推送服务按"在线成员分布在哪些网关"每个网关只发一次 RPC，10 万人群约 50 次 RPC。用户收件箱放在同一套强一致存储里，按 `user_id` 分片，可以从会话提交事件流重放重建。

## 7. 集群（目标架构，所有版本免费；方案待确认：D69）

**集群解决什么**：① 高可用（一台机器宕机、升级时不停服务，这是大多数客户要集群的主要原因）；② 长连接多；③ 大群推送扩散；④ 滚动升级。它**不提高数据库的写入上限**：写入靠 §4.8 的优化和多个数据库分担。

**业内做法**：主流开源 IM 都是"无状态的应用节点 + 消息总线 + 共享的数据库"，没有自己写一致性协议的：Mattermost（多节点 + 共享 PostgreSQL，节点之间广播缓存失效）、Rocket.Chat（多实例 + MongoDB 副本集）、Matrix Synapse（worker 进程 + 共享 PostgreSQL + Redis）、OpenIM（Kafka + Redis + MongoDB）、Tinode（会话按哈希分到节点 + 共享数据库）。稳定性来自数据库自己的高可用（主从、副本集、托管数据库），已经被验证了十几年。

**建议方案（D69）**：

```
 客户端（人 / Agent SDK / MCP）
        │ WebSocket
 负载均衡
        │
 AgentIM 节点 × N（同一个程序，无状态：连接、本地扇出、业务逻辑）
   · 每个会话同一时间只由一个节点写（写入归属）：节点用数据库锁按会话哈希认领一批分片，
     认领者就是 §4 的"写线程"，序号、组提交、写完才 ACK 都不变；节点失联后租约到期，别的节点接手
        │ 消息总线（NATS 或 Redis）：新提交的事件、缓存失效（用户、令牌、拉黑、急停、销毁）
 PostgreSQL / MySQL（主从或托管服务；SQLite 只用于单机）
   · 更大的规模：多个数据库（§5.4 的多库路由）或 Citus / Vitess
```

- 要处理的"单进程假设"（清单，新功能不再增加）：在线连接表 → 节点之间经总线推送；内存缓存（用户、令牌、拉黑、停用、急停、销毁、目录）→ 改动经总线通知所有节点，急停和销毁必须立即生效；进程内的全局锁（如单聊唯一）→ 数据库唯一约束或交给写入归属节点；限流计数 → 按节点计算；护栏预算、熔断、流式状态 → 跟着会话的写入归属走。
- 测试重点：节点宕机、网络分区、写入归属切换时消息不丢、不乱、不重复（同一个 `client_msg_id` 只成功一次）；滚动升级时新旧节点同时在线。
- 原来设想的自研 Multi-Raft 放弃：Rust 的 Raft 库还不成熟（openraft 仍在 1.0 之前），开发和测试成本远高于收益；只有将来出现超出数据库方案上限的客户时再评估。
