# 02 架构设计

> 状态：草案 v0.1（2026-10-10）

## 1. 设计原则

1. **按会话分片，只保证会话内有序**，不做全局有序。
2. **seq 分配与持久化原子化**：在同一次 Raft 日志写入中完成。
3. **推送是通知，拉取是真相**：推送可以丢，正确性由拉取保证。
4. **只有一层强一致**：会话分片使用 Raft；路由等其他状态均为软状态。
5. **Agent 在 IM 外部运行**：IM 负责传输与治理，模型的延迟和故障不传导到消息核心。
6. **开源核心的边界落在 trait 上**：企业功能以插件实现接口，核心代码中不出现企业版分支。

## 2. 消息模型

### 2.1 标识

| 字段 | 生成方 | 用途 |
|---|---|---|
| `client_msg_id` | 客户端（UUID v7） | 重试去重 |
| `server_msg_id` | 服务端 | 全局唯一标识 |
| `conv_seq` | 会话分片 leader | 会话内排序的唯一依据，单调递增、无空洞 |

### 2.2 字段

```
Message {
  tenant_id,          // 多租户，单租户部署默认一个值
  conv_id,
  conv_seq,           // 草稿态消息没有 seq
  server_msg_id,
  client_msg_id,
  sender_id,
  sender_type,        // human | agent | system
  on_behalf_of,       // Agent 代表谁发言（可空）
  kind,               // text | stream | tool_call | tool_result | system | ...
  content,
  version,            // 流式结束、编辑、工具结果回填时递增
  visibility,         // all | agent_only（耳语） | supervisors
  state,              // draft（待审批） | committed | recalled
  created_at,
}
```

## 3. 可靠性与顺序

### 3.1 发送路径

```
客户端 ──send(client_msg_id)──▶ 网关 ──按 conv_id 路由──▶ 会话分片 leader
                                                        │ 1. 去重（client_msg_id）
                                                        │ 2. 策略钩子（如该会话启用）
                                                        │ 3. 分配 conv_seq
                                                        │ 4. 写入 Raft 日志（多数派提交）
客户端 ◀──ACK(conv_seq)── 网关 ◀────────────────────────┘
                                                        │ 5. 发出提交事件 → 推送服务
接收方 ◀──push(conv_id, seq)── 网关
接收方发现 seq 空洞 ──pull(conv_id, from_seq)──▶ 分片（补齐）
```

### 3.2 机制

- **持久化后才 ACK**：多数派提交后才返回 ACK，已 ACK 的消息不会丢。
- **去重**：分片维护 `client_msg_id → conv_seq` 的映射（带 TTL），重试返回原 seq。
- **推拉结合**：客户端为每个会话记录 `last_seq`，推送携带 seq，发现空洞即拉取；重连时按用户级同步点批量补齐。
- **不做逐条送达回执**：接收方只上报阅读游标（`read_seq`），避免百万连接下的回执风暴。
- **发送方顺序**：SDK 对每个会话维护发送队列，可小窗口流水线，但 ACK 必须按序；重试使用相同 `client_msg_id`。

### 3.3 故障场景

| 故障 | 结果 |
|---|---|
| 发送方未收到 ACK | 用同一 `client_msg_id` 重发，分片去重后返回原 seq |
| 网关宕机 | 客户端重连到其他网关，用 `last_seq` 拉取补齐 |
| 分片 leader 宕机 | Raft 重新选主，已提交消息和 seq 不丢；未提交的由客户端重试 |
| 推送丢失 | 下一条推送或心跳暴露空洞，触发拉取 |
| 接收方离线 | 上线后按同步点拉取，服务端无需维护待投递队列 |

### 3.4 为什么不用 Redis INCR 分配 seq

分配 seq 与写库分两步时，中间宕机会造成跳号（客户端等待不存在的 seq）；Redis 故障切换可能导致 seq 回退重复。合并为一次 Raft 写入可彻底避免。

## 4. 群聊扩散模型

**消息体一律读扩散（会话日志只存一份），只对"会话有更新"信号做有限写扩散，在线推送在网关层聚合。**

### 4.1 分档

| | 普通群（≤ 2000 人，默认 100–1000） | 大群（2000 – 10 万人） |
|---|---|---|
| 消息存储 | 会话日志一份 | 会话日志一份 |
| 用户同步信号 | 写入成员的"会话变更日志"，同一会话合并为一条 | 不写，成员本地标记为大群 |
| 重连补齐 | 读自己的变更日志，得到变化的会话列表 | 批量查询所在大群的 max_seq |
| 在线推送 | 网关层聚合，逐条推送 | 网关层聚合，按时间窗口（如 200ms）合并 seq 通知 |

阈值（2000）为配置项，群人数跨越阈值时迁移模式。

### 4.2 网关层聚合扇出

推送服务查询"该群在线成员分布在哪些网关"，每个网关只发一次 RPC，由网关本地扇出。10 万人群约 50 次 RPC，而非 10 万次。成员上线时，网关在路由层订阅其所在群；网关本地维护 `group_id → 本地连接列表`。

### 4.3 未读数

未读数 = 会话 `max_seq` − 用户 `read_seq`，不存计数器。唯一例外是 @ 提及，仅对被提及者写扩散。

### 4.4 成员变更

入群、退群作为系统消息写入会话日志并占用 seq。成员记录 `join_seq` / `leave_seq`，拉取时按范围做权限过滤。

## 5. 整体分层

```
                    客户端（人）            客户端（Agent SDK / MCP / Webhook）
                         │                              │
        ┌────────────────┴──────────────────────────────┴───────────────┐
 接入层 │  Gateway（WebSocket / QUIC）  长连接、鉴权、心跳、本地扇出、流式合并 │
        └───────┬─────────────────────────────┬─────────────────────────┘
                │                             │
 路由层   Router（软状态）                 Agent Gateway
          用户→网关、群→网关订阅            流式追加、取消、工具事件、MCP、
                │                           预算/限流/循环熔断、上下文 API
                │                             │
        ┌───────┴─────────────────────────────┴───────────────┐
 核心层 │  Conversation Shards（Multi-Raft）                    │
        │  分配 seq → 去重 → 策略钩子链 → 提交 → 成员/可见性    │
        │       ↑ 审批草稿区   ↑ 介入：观察/耳语/接管/打断       │
        └───────┬──────────────────────────────────────────────┘
                │ 提交事件流
     ┌──────────┼───────────────┬───────────────┬──────────────┐
 Push 服务   离线推送        审计/监控管道      搜索索引        冷存储归档
 （在线扇出） （APNs/FCM）   （指标、审计、告警）（Tantivy）     （S3 兼容）

 元数据：用户、认证、组织（Postgres）    文件媒体：对象存储，预签名直传
```

| 层 | 职责 | 状态 |
|---|---|---|
| Gateway | 长连接、鉴权、心跳、本地扇出、流式增量合并 | 仅连接状态 |
| Router | 用户→网关、群→网关订阅 | **软状态**，可从网关重建；丢失只影响推送，不影响正确性 |
| Conversation Shards | seq、去重、策略钩子、持久化、成员与可见性、历史读取 | 强一致（Raft） |
| Agent Gateway | Agent 接入、流式追加、取消、工具事件、MCP、安全护栏 | 会话级运行状态 |
| Push | 消费提交事件，按网关聚合扇出；离线走 APNs/FCM | 无状态 |
| 审计/监控管道 | 提交与 Agent 动作的事件流 → 指标、审计、告警、搜索 | 追加写 |
| 元数据 | 用户、认证、组织、Agent 注册（群成员**不在此**，在分片内） | Postgres |
| 文件媒体 | 上传下载，不经过 IM 链路 | 对象存储 |

### 5.1 部署模式

- **单机模式**：所有角色同进程，嵌入式存储，单节点 Raft。
- **集群模式**：同一二进制，`--role gateway | shard | push | agent-gw`。
- 单机也用 Raft（单节点），升级集群只需加节点。

### 5.2 开源核心接口

| 接口 | 社区版实现 | 企业版实现 |
|---|---|---|
| `AuthProvider` | 账号密码、OAuth、2FA | SAML、SCIM、LDAP |
| `PolicyHook` | 基础过滤、安全护栏 | 数据防泄漏、合规词库、多级审批 |
| `AuditSink` | 本地日志 | ClickHouse、SIEM |
| `SearchBackend` | Tantivy | OpenSearch |
| `Replication` | 单地域 | 多地域、跨机房容灾 |

## 6. 容量估算（粗估，待压测）

| 项目 | 假设 | 结果 |
|---|---|---|
| 网关节点 | 每连接 10–20KB，单节点 15 万连接 | 7 个，N+2 冗余部署 9–10 个 |

| 下行扇出 | 平均群 200 人，在线率 30% | ~300 万次/秒，每网关 ~30 万帧/秒 |

## 7. 主要风险

**Multi-Raft 的分片迁移与负载均衡是最难的部分。**

- 会话哈希到固定数量的**虚拟分片**（如 4096），虚拟分片再映射到 Raft 组；扩容时移动虚拟分片，不重新哈希。
- 首版先做手动迁移工具，再做自动均衡。
- 热点大群单独放一个 Raft 组。
