# 04 安全与合规

> 版本 v0.5（2026-10-18）。静态加密默认开启（D3）已确认；E2EE 暂缓（2026-10-18 决定）；其余是**待确认的方案**，已实现的部分会单独注明。主要用户在海外，所以合规是基础需求，不是附加功能。

## 1. 身份与访问

| 项目 | 方案 | 依据 |
|---|---|---|
| 人类账号 | 账号密码，用 argon2id 哈希（m=19MiB、t=2、p=1）；可选 TOTP 二次验证；登录失败限流 | OWASP Password Storage Cheat Sheet 的最低建议参数 |
| 第三方登录 | OIDC（Google、Microsoft、GitHub）；SAML、SCIM 不做（2026-10-18 决定），原因：聚焦开发者 | |
| Agent 凭据 | API Key，格式为"前缀 + 随机密钥"，可以设置权限范围、轮换和吊销；之后支持 OAuth client credentials | MCP 2025-11-25 授权规范 |
| 内置账号密码 | Argon2id（19 MiB、2 轮，OWASP 最低要求），10–128 个字符且不能等于用户名；`POST /api/auth/login` 登录成功签发一台设备的令牌；名字不存在、没有设置密码、密码错误返回同一个错误，且对不存在的用户也做一次哈希，避免通过时间差探测账号；连续失败 10 次锁定 15 分钟（可配置，重启后仍有效）；同时计算的密码哈希有上限（每核一个，排队超过 4 倍返回 `rate_limited`，H2）；修改密码后其他设备全部下线；自助注册默认关闭（`auth.open_registration`）；运维可用 `agentim user set-password --name …`（从标准输入读密码）重置 | ✅ 已实现 |
| 两步验证（TOTP） | RFC 6238（SHA1、6 位、30 秒、前后各容忍一步）；`totp_setup` 生成密钥和 `otpauth://` 链接，`totp_enable` 用一个验证码确认后才生效，`totp_disable` 也需要验证码；每个验证码只能用一次（并发登录也只成功一次） | ✅ 已实现 |
| Origin 校验 | 浏览器访问 `/ws` 和登录接口时，`Origin` 必须是本站或 `server.allowed_origins` 里的地址，防止跨站 WebSocket 劫持；App、SDK、Agent 不带 `Origin`，不受影响 | ✅ 已实现 |
| 内置 TLS | `[server.tls] cert/key`（PEM）后服务端直接提供 HTTPS 和 WSS（rustls + ring）；握手在接受循环之外进行、10 秒超时；也可以放在 TLS 反向代理之后（`open_api.behind_proxy`；客户端地址取 `X-Forwarded-For` 从右数第 `proxy_hops` 项，客户端自己写的前几项不算，M9） | ✅ 已实现 |
| 会话令牌 | 256 位随机数；数据库里**只存 SHA-256 哈希**；人的令牌 30 天不用或签发满 1 年失效（`auth.token_idle_days`、`token_max_days`，D94；Agent 密钥不过期）；可以吊销；CLI 在服务端运行时吊销、改密码、停用，服务端 1 秒内生效（M10）；握手和登记之间被吊销的连接也会关闭（M13） | ✅ 已实现（`atk_` 前缀，老库升级时转为哈希） |
| 开发者后端签发令牌 | 开发者的后端用开放 API 给自己的用户签发客户端令牌（[07 §3.4](07-open-api.md)）；内置账号密码是给独立部署用的另一种方式 | Stream、腾讯云 IM 都是这样做 |
| 演示登录 | 只在 `--demo` 下可用；默认关闭（现状已经如此） | |
| 授权 | 集中在一个策略检查函数里；角色分为成员、管理员、所有者、组织管理员 | |
| **设备**（D14） | 每次登录创建一条设备记录（`device_id`、名称、平台、最近活跃时间、IP 所在地区）；每台设备有自己的刷新令牌（只存哈希）和短期访问令牌；用户和管理员都能看到设备列表并让单台设备下线 | Slack、Google 账号的设备管理 |
| 新设备登录通知 | 新设备登录时，向该用户的其他设备发系统通知（时间、平台、地区），可一键下线 | 海外用户普遍期待的账号安全功能 |
| 多端已读同步 | 一台设备标记已读后，服务端向同一用户的其他在线会话推送 `read.updated`，各端未读数立即一致 | |

## 2. 加密

### 2.1 传输加密

- 内置 TLS（rustls），也可以放在反向代理之后；只用 WSS；开启 HSTS。
- WebSocket 握手时校验 `Origin`，防止跨站 WebSocket 劫持。
- 集群内部的 RPC 走 mTLS（集群阶段）。

### 2.2 静态加密：三种模式

| 模式 | 适用 | 密钥在哪里 |
|---|---|---|
| `off` | 开发、测试 | — |
| `managed` | **默认开启**（D3） | 主密钥（KEK）来自本地密钥文件、环境变量或操作系统密钥库 |
| `byok`（客户管理的密钥） | 不做（2026-10-18 决定），原因：聚焦开发者 | — |

### 2.3 密钥层级（信封加密，参考 Slack EKM）

```
KEK（主密钥，来自密钥文件或环境变量；永不落盘到数据库）
 └─ DEK（数据密钥）：每个会话、每个时间窗口（默认按月）一个
     · 用 KEK 包装后存进 keys 表
     · 在内存中缓存
     └─ 内容：AES-256-GCM，随机 96 位 nonce
        AAD = (tenant_id, conv_id, msg_id, version)，防止密文被挪到别的消息上
```

- **加密的内容**：消息正文、侧信道内容（耳语、草稿）、工具调用的参数和结果、审计日志里的内容快照。
- **保持明文的内容**：ID、seq、时间戳、成员关系、发送者 ID。路由、排序和权限检查需要这些字段，这和 Slack EKM 的划分一致（频道名、成员记录由 Slack 自己的密钥保护）。
- **轮换**：DEK 按时间窗口自动轮换；轮换 KEK 时只需要重新包装 DEK，不必重新加密全部内容。
- **搜索**：服务端搜索需要索引，加密模式下索引本身也要加密。放到搜索功能那个阶段再做。

### 2.4 性能

AES-GCM 在支持 AES-NI 的 CPU 上，每个核心每秒可以处理数 GB（AWS-LC 在 Zen 3 上实测，AES-128-GCM 约 4.6 GB/s；AES-256 大约慢 30–40%）。一条 1KB 的消息加密只需要微秒级时间，远小于一次 fsync。

**结论：已默认开启（D3）。** 实测（同一台机器、SQLite、写入路径，各跑两次）：关闭 818 条/秒，开启 800 条/秒，约慢 2%，延迟没有可见差别；数据在 README。

### 2.6 实现细节（M4）

| 方面 | 做法 |
|---|---|
| 算法 | AES-256-GCM（ring，已经是依赖），96 位随机 nonce。DEK 用 KEK 包装（同样 AES-256-GCM，AAD 是 DEK 的 ID） |
| 主密钥（KEK） | `[encryption] mode = "managed"`（默认）或 `"off"`。KEK 是 32 字节随机数（base64），来源依次是：`key_file`、环境变量 `AGENTIM_MASTER_KEY`；都没有时，单个 SQLite 库的部署在数据库旁自动生成 `<数据库>.key`（权限 0600，启动日志提醒备份），其他部署拒绝启动。库里记录 KEK 的指纹，换错了钥匙拒绝启动，不会写出用另一把钥匙加密的数据 |
| DEK | 每个会话每 30 天一个（`data_keys` 表，KEK 包装后存放），内存缓存。全库共用内容（审计、Webhook 待发队列）用库级的 DEK（每库每月一个）。新 DEK 和使用它的数据在同一个事务里提交，事务失败时缓存里的新 DEK 一起丢弃，不会出现找不到钥匙的数据 |
| 加密的列 | `messages.content`、`messages.payload`、`events.payload`（含消息快照）、`side_events.data`（耳语、仅某人可见、草稿通知）、`drafts.content`、`drafts.payload`、`audit.detail`、`webhook_outbox.body`。空字符串和 NULL 不加密 |
| 不加密的列 | ID、seq、时间、类型、成员关系、角色、发送者 ID、会话标题、用户名和资料（和 Slack EKM 的划分一致；标题和资料以后可以单独加密） |
| 存储格式 | 原来的文本列里存 `enc:v1:<key_id>:<base64(nonce‖密文‖tag)>`，不改列类型。AAD 是（表、列、行 ID），密文挪到别的行或别的列都会解密失败 |
| 读到异常 | 认得的钥匙但解不开（被篡改、挪动）就报错（fail closed），不会把密文当内容返回；不带前缀的值是加密开启之前写的明文，照常读取 |
| 解散会话 | 删除内容的同时删除这个会话的 DEK（加密销毁）：即使备份里还留着密文，也无法再解开 |
| 迁移会话到另一个库 | DEK 随会话一起复制过去，内容原样复制 |
| 老库升级 | 开启加密后新写入的内容立即加密，老的明文照常可读；`agentim encryption encrypt-existing`（停服务执行，可重复执行，按批提交）把老数据全部加密 |
| 轮换主密钥 | `agentim encryption rotate-key --new-key-file …`（停服务执行）：只重新包装 DEK，不重新加密内容 |
| 测试 | 三种数据库上：任何表里都找不到明文、重启后可读、错误或缺失的主密钥拒绝启动、篡改和挪动密文被发现、关闭模式和从关到开、老数据加密、轮换主密钥、解散后的加密销毁、多库迁移、并发新建会话时每个会话每月只有一个 DEK；加密开和关的性能对比写进 README |

### 2.5 端到端加密（E2EE）

暂缓（2026-10-18 决定）。原来的方案：用 MLS（RFC 9420，OpenMLS），每台设备是一个 MLS 成员，服务端只做凭据签发、KeyPackage 目录和按 epoch 的全序投递（会话主日志正好提供）；加解密放在以后的 Rust 核心 SDK 里（[05 §6.1](05-operations.md)，D104）。开启 E2EE 的会话里，服务端的内容过滤、审批、审核和搜索都不可用，到时必须在界面和文档里写明。

## 4. 合规（海外）

### 4.1 法规与功能对照

责任划分：部署 AgentIM 的客户通常是"控制者"或"平台提供方"，我们提供让他们能够合规的功能。托管云上线后，我们自己也会成为处理者。

| 法规 | 要求 | AgentIM 功能 | 状态 |
|---|---|---|---|
| **EU AI Act 第 50 条**（2026-08-02 起适用，Digital Omnibus 没有推迟这一条） | 与人交互的 AI 必须让人知道对方是 AI；生成内容需要机器可读标记 | 服务端写入 `sender_type`，客户端必须展示 AI 标识；首次与 AI 对话时显示提示；消息带 `ai_generated` 元数据；媒体内容预留 C2PA 清单字段。参考欧盟委员会 2026-06 发布的标记与标识行为准则和 EU 图标 | 披露 ✅；标记 🔧 |
| **GDPR** 第 15、20 条 | 访问权、可携带权，一个月内答复 | 用户自助导出自己的数据（机器可读的 JSON：消息、成员关系、审计记录） | 🔧 |
| GDPR 第 17 条 | 删除权 | 用户自助删除账号：清空其消息内容并留墓碑；删除会话：销毁 DEK（crypto-shredding） | 🔧 |
| GDPR 第 5 条 | 数据最小化、存储期限 | 部署级的基本保留期限，过期自动删除；日志默认不含内容 | 🔧 |
| GDPR 第 30 条、DPIA | 处理活动记录 | 导出"哪个 Agent（以及它背后的模型提供方）处理了哪些会话"；提供 DPIA 模板 | 🔧 |
| GDPR 告知 | 群内的 AI 处理需要告知成员 | Agent 加入时向全员发系统事件 | ✅ |
| **DSA** 第 16、17 条 | 举报通道（通知与处理）；限制内容时给出处置理由 | 举报 API；基本审核队列；处置记录（限制类型、依据的事实、法律或条款依据、是否用了自动化工具、申诉途径） | 🔧 |
| **UK Online Safety Act** | 违法内容的举报与处理；儿童保护 | 同上；预留年龄验证钩子 | 🔧 |
| **App Store 1.2 / Google Play 用户生成内容政策** | 用户协议、过滤、举报、拉黑；24 小时内处理举报 | 用户协议确认、内容过滤、举报、拉黑（被拉黑者的消息不再投递）、带处理时限的审核队列 | 🔧 |
| **CCPA / CPRA** | 访问、删除、不出售 | 复用 GDPR 的导出和删除工具 | 🔧 |
| **COPPA** | 13 岁以下儿童 | 年龄门槛钩子 | ⏳ |
| 数据驻留 | 数据存储在指定地域 | 自托管时由部署地决定；托管云按地域部署 | 自托管天然满足 |

### 4.2 删除与保留的设计要点

- **删除顺序**：清空内容、写墓碑事件（占 seq，客户端据此删除本地副本）→ 删除搜索索引和缓存 → 写一条审计记录（只记录"谁在何时删除了什么范围"，不记录内容）。
- **备份**：只追加的日志和备份都无法逐条删除。办法：备份同样加密，保留期有上限；会话级的删除通过销毁 DEK 实现。注意：业界对"销毁密钥是否等同于删除"没有明确判例，需要客户的法务确认。
- **法律保全（legal hold）、电子取证（eDiscovery）、DSA 透明度报告、组织级保留策略**：不做（2026-10-18 决定），原因：聚焦开发者。

### 4.3 审核与举报流程

```
用户举报（消息 / 用户 / 会话，附原因）
  → 审核队列（按严重程度排序，显示处理时限倒计时；App Store 要求 24 小时内处理）
  → 处置：无需处理 / 删除内容 / 限制用户 / 封禁
  → 生成处置记录（DSA 第 17 条要求的字段）；通知被处置人，告知申诉途径
  → 写审计
```

## 5. 组织单元与多库隔离（高级配置）

按 D101（待确认）：保留为免费的高级配置，不加许可证开关，不做信息屏障。现有代码和测试保留；大多数部署用不到这一节。

### 5.1 要防的对象

| 对象 | 场景 | 手段 |
|---|---|---|
| 其他子公司的员工 | A 公司的人看到 B 公司的群 | 授权：所有读写都按单元过滤（L1） |
| 法规或合同要求 | 必须单独存放，或者存在指定地区 | 物理隔离（L3，§5.3） |
| AI Agent | Agent 把 A 公司的信息带到 B 公司 | Agent 归属到单元（§5.6） |

### 5.2 组织层级

```
集团（tenant）
 ├─ 子公司 A（unit，L1）
 ├─ 子公司 B（unit，L3，存储位置：欧盟）
 │   └─ 并购项目组（unit，可以继续嵌套，继承上级的限制，只能更严、不能更松）
 └─ ……
```

用户、Agent、会话都归属于一个单元（`unit_id`）。

### 5.3 隔离等级

| 等级 | 做法 | 能防住 |
|---|---|---|
| **L1 逻辑隔离** | 与其他单元共用数据库。存储接口强制带"访问范围"参数，代码里没有不带范围的查询路径；PostgreSQL 上再加 RLS 兜底（`FORCE ROW LEVEL SECURITY`，用事务级的 `SET LOCAL` 设置租户上下文，避免连接池复用时串租户） | 其他单元的用户和 Agent |
| **L3 物理隔离** | 该单元的会话全部存进专属数据库（[02 §5.4](02-architecture.md)，方案 A），可以放在单独的服务器或地区 | 再加上：法规和合同要求、其他单元的负载影响 |

L2（每个单元独立密钥、BYOK）：不做（2026-10-18 决定），原因：聚焦开发者。要求更高时可以**独立部署一整套 AgentIM**（方案 B）；集群阶段再提供专属分片（方案 C）。

### 5.4 信息屏障

不做（2026-10-18 决定），原因：聚焦开发者。

### 5.5 管理权限分级

不做（2026-10-18 决定），原因：聚焦开发者。

### 5.6 Agent

- Agent 归属于某个单元；上下文接口按单元过滤。
- 工具网关的凭据按单元分别保管。

### 5.7 容易漏掉的地方

日志默认不含内容；指标标签不含用户和会话 ID；L3 单元的备份单独存放。

### 5.8 版本划分

不做（2026-10-18 决定），原因：聚焦开发者。只有一个产品、一个程序 `agentim`。
