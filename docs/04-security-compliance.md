# 04 安全与合规

> 静态加密默认开启（D3）；E2EE 暂缓。✅ 表示已实现，其余是计划。主要用户在海外，合规是基础需求。

## 1. 身份与访问

| 项目 | 做法 | 状态 |
|---|---|---|
| 内置账号密码 | Argon2id（m=19 MiB、t=2、p=1，OWASP 最低建议），10–128 个字符且不能等于用户名；`POST /api/auth/login` 登录成功签发一台设备的令牌；名字不存在、没有设置密码、密码错误返回同一个错误，且对不存在的用户也做一次哈希，避免通过时间差探测账号；连续失败 10 次锁定 15 分钟（可配置，重启后仍有效）；同时计算的密码哈希有上限（每核一个，排队超过 4 倍返回 `rate_limited`）；修改密码后其他设备全部下线；自助注册默认关闭（`auth.open_registration`）；运维可用 `agentim user set-password --name …`（从标准输入读密码）重置 | ✅ |

## 2. 加密

### 2.1 传输加密

内置 TLS（rustls）或反向代理；浏览器连接校验 `Origin`（§1）；集群节点之间的连接见 [11 §6](11-cluster.md)；HSTS 计划中。

### 2.2 静态加密：模式

`[encryption] mode = "managed"`（默认，D3）或 `"off"`（开发、测试、小团队）。先关后开：老的明文照常读，`agentim encryption encrypt-existing` 加密老数据。先开后关（B4）：主密钥仍要配着，已加密的内容照常读，新内容存明文；`agentim encryption decrypt-existing` 把老数据转回明文；库里有数据密钥但没配主密钥时拒绝启动并说明怎么做。客户管理的密钥（BYOK）不做。

### 2.3 密钥层级（信封加密）

```
KEK（主密钥，来自密钥文件或环境变量；永不写进数据库）
 └─ DEK（数据密钥）：每个会话每 30 天一个；全库共用的内容用库级 DEK
     · 用 KEK 包装后存进 data_keys 表，内存缓存
     └─ 内容：AES-256-GCM，随机 96 位 nonce，AAD 绑定位置（§2.6）
```

- **轮换**：DEK 按时间窗口自动轮换；轮换 KEK 时只重新包装 DEK，不重新加密内容。
- **搜索**（以后）：服务端搜索的索引在加密模式下本身也要加密。

### 2.4 性能

开启后写入吞吐约慢 2%（同机 SQLite 实测 818 → 800 条/秒），延迟没有可见差别；数据在 README。

### 2.5 端到端加密（E2EE）

暂缓。需要时用 MLS（RFC 9420，OpenMLS）：每台设备是一个 MLS 成员，服务端只做凭据签发、KeyPackage 目录和按 epoch 的全序投递（会话主日志正好提供），加解密放在客户端 Rust 核心里（D104）。E2EE 会话里服务端的内容过滤、审批、审核、搜索都不可用，开放 API 不能替用户发消息。

### 2.6 实现细节

| 方面 | 做法 |
|---|---|
| 算法 | AES-256-GCM（ring），96 位随机 nonce。DEK 用 KEK 包装（同样 AES-256-GCM，AAD 是 DEK 的 ID） |
| 主密钥（KEK） | 32 字节随机数（base64），来源依次是：`key_file`、环境变量 `AGENTIM_MASTER_KEY`；都没有时，单个 SQLite 库的部署在数据库旁自动生成 `<数据库>.key`（权限 0600，启动日志提醒备份），其他部署拒绝启动。库里记录 KEK 的指纹，换错了钥匙拒绝启动 |
| DEK | 每个会话每 30 天一个（`data_keys` 表），内存缓存。全库共用内容（审计、Webhook 待发队列）用库级 DEK（每库每月一个）。新 DEK 和使用它的数据在同一个事务里提交，事务失败时缓存里的新 DEK 一起丢弃 |
| 加密的列 | `messages.content`、`messages.payload`、`events.payload`（含消息快照）、`side_events.data`（耳语、仅某人可见、草稿通知）、`drafts.content`、`drafts.payload`、`audit.detail`、`webhook_outbox.body`。空字符串和 NULL 不加密 |
| 不加密的列 | ID、seq、时间、类型、成员关系、角色、发送者 ID、会话标题、用户名和资料（路由、排序、权限检查需要；标题和资料以后可以单独加密） |
| 存储格式 | 文本列里存 `enc:v1:<key_id>:<base64(nonce‖密文‖tag)>`。AAD 是（表、列、行 ID），密文挪到别的行或别的列都会解密失败 |
| 读到异常 | 认得的钥匙但解不开（被篡改、挪动）就报错（fail closed），不会把密文当内容返回；不带前缀的值是加密开启之前写的明文，照常读取 |
| 解散会话 | 删除内容的同时删除这个会话的 DEK（加密销毁）：备份里的密文也无法再解开 |
| 迁移会话到另一个库 | DEK 随会话一起复制，内容原样复制 |
| 从关到开 | 新写入的内容立即加密，老的明文照常可读；`agentim encryption encrypt-existing`（停服务执行，可重复执行，按批提交）把老数据全部加密 |
| 轮换主密钥 | `agentim encryption rotate-key --new-key-file …`（停服务执行）：只重新包装 DEK |
| 测试 | 三种数据库上：任何表里都找不到明文、重启后可读、错误或缺失的主密钥拒绝启动、篡改和挪动密文被发现、关闭模式、从关到开、从开到关再到开（关着时旧密文照常读、新内容是明文、转回明文可重复执行、关着时不能加密老数据、没配主密钥时拒绝启动）、老数据加密、轮换主密钥、解散后的加密销毁、多库迁移、并发新建会话时每个会话每个窗口只有一个 DEK |

## 4. 合规（海外）

### 4.1 法规与功能对照

使用 AgentIM 的开发者通常是"控制者"或"平台提供方"，我们提供让他们能合规的功能；托管云上线后我们自己也是处理者。

| 法规 | 要求 | AgentIM 功能 | 状态 |
|---|---|---|---|
| **EU AI Act 第 50 条**（2026-08-02 起适用） | 与人交互的 AI 必须让人知道对方是 AI；生成内容需要机器可读标记 | 服务端写入 `sender_type`，客户端必须展示 AI 标识；首次与 AI 对话时显示提示；消息带 `ai_generated`；媒体预留 C2PA 字段 | 披露 ✅；标记 🔧 |
| **GDPR** 第 15、20 条 | 访问权、可携带权，一个月内答复 | 用户自助导出自己的数据（机器可读 JSON：消息、成员关系、审计记录） | 🔧 |
| GDPR 第 17 条 | 删除权 | 用户自助删除账号：清空其消息内容并留墓碑；删除会话：销毁 DEK | 🔧 |
| GDPR 第 5 条 | 数据最小化、存储期限 | 部署级保留期，过期自动删除（[08 §2.5](08-sync-and-client.md)）；日志默认不含内容 | 保留期 ✅ |
| GDPR 第 30 条、DPIA | 处理活动记录 | 导出"哪个 Agent（及其模型提供方）处理了哪些会话"；DPIA 模板 | 🔧 |
| GDPR 告知 | 群内的 AI 处理需要告知成员 | Agent 加入时向全员发系统事件 | ✅ |
| **DSA** 第 16、17 条 | 举报通道；限制内容时给出处置理由 | 举报 API；审核队列；处置记录（限制类型、依据的事实、法律或条款依据、是否用了自动化工具、申诉途径） | 🔧 |
| **UK Online Safety Act** | 违法内容的举报与处理；儿童保护 | 同上；预留年龄验证钩子 | 🔧 |
| **App Store 1.2 / Google Play UGC 政策** | 用户协议、过滤、举报、拉黑；24 小时内处理举报 | 用户协议确认、内容过滤、举报、拉黑（[02 §2.4](02-architecture.md)）、带处理时限的审核队列 | 拉黑 ✅；其余 🔧 |
| **CCPA / CPRA** | 访问、删除、不出售 | 复用 GDPR 的导出和删除工具 | 🔧 |
| **COPPA** | 13 岁以下儿童 | 年龄门槛钩子 | ⏳ |
| 数据驻留 | 数据存储在指定地域 | 自托管由部署地决定；托管云按地域部署 | 自托管天然满足 |

### 4.2 删除与保留的设计要点

- **删除顺序**：清空内容、写墓碑事件（占 seq，客户端据此删除本地副本）→ 删除搜索索引和缓存 → 写一条审计记录（只记录"谁在何时删除了什么范围"，不记录内容）。
- **备份**：日志和备份无法逐条删除。备份同样加密、保留期有上限；会话级的删除通过销毁 DEK 实现（"销毁密钥是否等同于删除"没有明确判例，由使用者的法务确认）。
- 法律保全、电子取证、透明度报告、组织级保留策略不做。

### 4.3 审核与举报流程

```
用户举报（消息 / 用户 / 会话，附原因）
  → 审核队列（按严重程度排序，显示处理时限倒计时；App Store 要求 24 小时内处理）
  → 处置：无需处理 / 删除内容 / 限制用户 / 封禁
  → 生成处置记录（DSA 第 17 条要求的字段）；通知被处置人，告知申诉途径
  → 写审计
```

## 5. 组织单元与多库隔离（高级配置）

免费的高级配置，没有许可证开关（D101）；大多数部署用不到。

### 5.1 要防的对象

| 对象 | 场景 | 手段 |
|---|---|---|
| 其他单元的用户 | 单元 A 的人看到单元 B 的群 | 授权：所有读写都按单元过滤（L1） |
| 法规或合同要求 | 必须单独存放，或者存在指定地区 | 物理隔离（L3） |
| AI Agent | Agent 把单元 A 的信息带到单元 B | Agent 归属到单元（§5.6） |

### 5.2 组织层级

租户（tenant）下分单元（unit），单元可以嵌套，下级继承上级的限制，只能更严、不能更松。用户、Agent、会话都归属于一个单元（`unit_id`）。

### 5.3 隔离等级

| 等级 | 做法 | 能防住 |
|---|---|---|
| **L1 逻辑隔离** | 与其他单元共用数据库。存储接口强制带"访问范围"参数，没有不带范围的查询路径；PostgreSQL 上再加 RLS 兜底（`FORCE ROW LEVEL SECURITY`，事务级 `SET LOCAL` 设置租户上下文，避免连接池复用时串租户） | 其他单元的用户和 Agent |
| **L3 物理隔离** | 该单元的会话全部存进专属数据库（[02 §5.4](02-architecture.md)），可以放在单独的服务器或地区 | 再加上法规和合同要求、其他单元的负载影响 |

L2（每个单元独立密钥）不做；要求更高时独立部署一套 agentim。

### 5.4 信息屏障

不做。

### 5.5 管理权限分级

不做。

### 5.6 Agent

- Agent 归属于某个单元；上下文接口按单元过滤。
- 工具网关的凭据按单元分别保管。

### 5.7 容易漏掉的地方

日志默认不含内容；指标标签不含用户和会话 ID；L3 单元的备份单独存放。
