# 04 安全与合规

> 静态加密默认开启（D3）；E2EE 暂缓。✅ 表示已实现，其余是计划。主要用户在海外，合规是基础需求。

## 1. 身份与访问

| 项目 | 做法 | 状态 |
|---|---|---|
| 最终用户没有 IM 密码 | 账号在开发者自己的系统里，IM 只认开发者签名的客户端令牌（[13 §4.2](13-roles-and-entry-points.md)）；内置的密码登录、注册、改密码、TOTP、`user set-password` 已删除（D116）。Argon2id、锁定和 TOTP 的代码留给控制台的管理员登录（A5，[12 §4](12-developer-experience.md)） | ✅ |
| 客户端令牌（人） | 开发者后端用签名密钥离线签 JWT（HS256，必须有 `kid`、`sub`、`iat`、`exp`，最长 `auth.max_token_days` 天，默认 30），不调 IM；只接受 HS256，`none` 和其他算法一律拒绝；`iat` 最多比服务器时钟快 60 秒。签名密钥由部署者用 `agentim signing-key create/list/revoke` 管理，可以同时有多把以便轮换，用主密钥加密存放（静态加密关闭时明文），吊销后用它签的令牌立即失效、用它连上的设备立即断开（集群里每个节点）。第一次见到的用户 ID 自动建成人；已删除、已停用、Agent、`system` 的 ID 拒绝。被拒绝的令牌不建用户、不登记设备、不写审计 | ✅ |
| 第三方登录 | OIDC（Google、Microsoft、GitHub）；SAML、SCIM 不做 | 计划 |
| Agent 凭据 | Agent 密钥：`atk_` + 256 位随机数，数据库里**只存 SHA-256 哈希**；负责人在客户端、开发者用开放 API `POST /v1/agents/{id}/keys`（`agents:write`）签发、轮换、吊销；不过期（D94）；以后支持 OAuth client credentials（MCP 授权规范） | ✅ |
| 登出和吊销 | 下线一台设备（`logout_device`、开放 API）或全部（`DELETE /v1/users/{id}/tokens`）：断开、删掉同步位置，并记下时刻，这个用户（或这台设备）签发时间不晚于该秒的令牌从此被拒绝（Stream 的 `revoke_tokens_issued_before` 是同样做法）；令牌不是按设备签的，拿到令牌的人换个设备 ID 仍能连上直到过期，所以怀疑泄露时下线全部，令牌有效期要短。CLI 在服务端运行时吊销、停用，服务端 1 秒内生效；握手和登记之间被吊销的连接也会关闭 | ✅ |
| 设备 | 人的设备 ID 由 App 选定并保存（连接时 `device=`，1–64 个 `A-Z a-z 0-9 _ -`），服务端第一次见到时登记（名称、平台、最近使用时间），欢迎帧里带服务端的 `device_id`；30 天不用就忘掉（`auth.token_idle_days`，下次连接算新设备）。Agent 的每把密钥是一台设备。`list_devices`、`logout_device` 让单台设备下线并立即断开 | ✅ |
| 新设备登录通知 | 新设备登录时，该用户已在线的设备收到 `device.added`，可一键下线 | ✅ |
| 多端已读同步 | 一台设备标记已读后，同一用户的其他在线设备收到 `read`，未读数立即一致（[08 §2.6](08-sync-and-client.md)） | ✅ |
| 令牌不进地址 | 连 `/ws` 时令牌放在 `Authorization: Bearer` 头里，浏览器放在子协议 `agentim.bearer.<base64url>` 里，不放在 URL 里（代理和负载均衡的访问日志会记下 URL，D129，[02 §2.5](02-architecture.md)）；`?token=` 还接受一个版本 | ✅ |
| 认证失败按来源限制 | 同一个来源地址（直连的对端；`open_api.behind_proxy` 时取最外层可信代理加的 `X-Forwarded-For`）1 分钟内认证失败 30 次后拒绝 5 分钟（`rate_limited`，带 `Retry-After`），`/ws`、`/mcp`、开放 API 共用这个计数，指标 `agentim_auth_blocked_total`（D130）。GitLab 的默认是 1 分钟 10 次封 1 小时（[文档](https://docs.gitlab.com/rate_limits/abuse_bans/)），我们放宽，因为公司网络和移动运营商常常很多人共用一个地址。内存里没有的令牌或密钥去库里查之前：每个来源每秒最多一次，全部来源合计每秒最多 20 次，一个来源乱发令牌占不满别人的额度；新建、吊销的 Agent 密钥、签名密钥、开放 API 密钥都立刻通知集群里的其他节点，正常情况下用不着查库。很多地址一起来的随机令牌属于 DDoS，交给前面的负载均衡和 WAF | ✅ |
| Origin 校验 | 浏览器访问 `/ws`、`/mcp` 和演示接口时，`Origin` 必须是本站或 `server.allowed_origins` 里的地址，防止跨站 WebSocket 劫持；App、SDK、Agent 不带 `Origin`，不受影响 | ✅ |
| 内置 TLS | `[server.tls] cert/key`（PEM）后直接提供 HTTPS 和 WSS（rustls + ring）；握手在接受循环之外进行、10 秒超时；也可以放在 TLS 反向代理之后（`open_api.behind_proxy`；客户端地址取 `X-Forwarded-For` 从右数第 `proxy_hops` 项，客户端自己写的前几项不算） | ✅ |
| 演示登录 | 只在 `--demo` 下可用：演示自己有签名密钥，`/api/login` 返回签好的令牌；`--demo` 只监听本机地址（否则启动报错，除非加 `--demo-public`）；`/api/dev/users` 也校验 Origin | ✅ |
| 授权 | 集中在一个策略检查函数里；角色：成员、管理员、所有者 | ✅ |

## 2. 加密

### 2.1 传输加密

内置 TLS（rustls）或反向代理；浏览器连接校验 `Origin`（§1）；集群节点之间的连接见 [11 §6](11-cluster.md)；HSTS 计划中。

### 2.2 静态加密：模式

`[encryption] mode = "managed"`（默认，D3）或 `"off"`（开发、测试、小团队）。先关后开：老的明文照常读，`agentim encryption encrypt-existing` 加密老数据。先开后关（B4）：主密钥仍要配着，已加密的内容照常读，新内容存明文；`agentim encryption decrypt-existing` 把老数据转回明文；库里有数据密钥但没配主密钥时拒绝启动并说明怎么做。客户管理的密钥（BYOK）不做。

### 2.3 密钥层级（信封加密）

```
KEK（主密钥，来自密钥文件或环境变量；永不写进数据库）
 └─ DEK（数据密钥）：每个会话每 30 天一个；全库共用的内容用库级 DEK
     · 用 KEK 包装后存进 data_keys 表，内存缓存
     └─ 内容：AES-256-GCM，随机 96 位 nonce，AAD 绑定位置（§2.6）
```

- **轮换**：DEK 按时间窗口自动轮换；轮换 KEK 时只重新包装 DEK，不重新加密内容。
- **搜索**（以后）：服务端搜索的索引在加密模式下本身也要加密。

### 2.4 性能

开启后写入吞吐约慢 2%（同机 SQLite 实测 818 → 800 条/秒），延迟没有可见差别；数据在 README。

### 2.5 端到端加密（E2EE）

暂缓。需要时用 MLS（RFC 9420，OpenMLS）：每台设备是一个 MLS 成员，服务端只做凭据签发、KeyPackage 目录和按 epoch 的全序投递（会话主日志正好提供），加解密放在客户端 Rust 核心里（D104）。E2EE 会话里服务端的内容过滤、审批、审核、搜索都不可用，开放 API 不能替用户发消息。

### 2.6 实现细节

| 方面 | 做法 |
|---|---|
| 算法 | AES-256-GCM（ring），96 位随机 nonce。DEK 用 KEK 包装（同样 AES-256-GCM，AAD 是 DEK 的 ID） |
| 主密钥（KEK） | 32 字节随机数（base64），来源依次是：`key_file`、环境变量 `AGENTIM_MASTER_KEY`；都没有时，单个 SQLite 库的部署在数据库旁自动生成 `<数据库>.key`（权限 0600，启动日志提醒备份），其他部署拒绝启动。库里记录 KEK 的指纹，换错了钥匙拒绝启动 |
| DEK | 每个会话每 30 天一个（`data_keys` 表），内存缓存。全库共用内容（审计、Webhook 待发队列）用库级 DEK（每库每月一个）。新 DEK 和使用它的数据在同一个事务里提交，事务失败时缓存里的新 DEK 一起丢弃 |
| 加密的列 | `messages.content`、`messages.payload`、`events.payload`（含消息快照）、`side_events.data`（耳语、仅某人可见、草稿通知）、`drafts.content`、`drafts.payload`、`audit.detail`、`webhook_outbox.body`。空字符串和 NULL 不加密 |
| 不加密的列 | ID、seq、时间、类型、成员关系、角色、发送者 ID、会话标题、用户名和资料（路由、排序、权限检查需要；标题和资料以后可以单独加密） |
| 存储格式 | 文本列里存 `enc:v1:<key_id>:<base64(nonce‖密文‖tag)>`。AAD 是（表、列、行 ID），密文挪到别的行或别的列都会解密失败 |
| 读到异常 | 认得的钥匙但解不开（被篡改、挪动）就报错（fail closed），不会把密文当内容返回；不带前缀的值是加密开启之前写的明文，照常读取 |
| 解散会话 | 删除内容的同时删除这个会话的 DEK（加密销毁）：备份里的密文也无法再解开 |
| 迁移会话到另一个库 | DEK 随会话一起复制，内容原样复制 |
| 从关到开 | 新写入的内容立即加密，老的明文照常可读；`agentim encryption encrypt-existing`（停服务执行，可重复执行，按批提交）把老数据全部加密 |
| 轮换主密钥 | `agentim encryption rotate-key --new-key-file …`（停服务执行）：只重新包装 DEK |
| 测试 | 三种数据库上：任何表里都找不到明文、重启后可读、错误或缺失的主密钥拒绝启动、篡改和挪动密文被发现、关闭模式、从关到开、从开到关再到开（关着时旧密文照常读、新内容是明文、转回明文可重复执行、关着时不能加密老数据、没配主密钥时拒绝启动）、老数据加密、轮换主密钥、解散后的加密销毁、多库迁移、并发新建会话时每个会话每个窗口只有一个 DEK |

## 4. 合规（海外）

### 4.1 法规与功能对照

使用 AgentIM 的开发者通常是"控制者"或"平台提供方"，我们提供让他们能合规的功能；托管云上线后我们自己也是处理者。

| 法规 | 要求 | AgentIM 功能 | 状态 |
|---|---|---|---|
| **EU AI Act 第 50 条**（2026-08-02 起适用） | 与人交互的 AI 必须让人知道对方是 AI；生成内容需要机器可读标记 | 服务端写入 `sender_type`，客户端必须展示 AI 标识；首次与 AI 对话时显示提示；消息带 `ai_generated`；媒体预留 C2PA 字段 | 披露 ✅；标记 🔧 |
| **GDPR** 第 15、20 条 | 访问权、可携带权，一个月内答复 | 用户自助导出自己的数据（§4.2） | ✅ |
| GDPR 第 17 条 | 删除权 | 自助删除账号：清空其消息内容并留墓碑（§4.2） | ✅ |
| GDPR 第 5 条 | 数据最小化、存储期限 | 部署级保留期，过期自动删除（[08 §2.5](08-sync-and-client.md)）；日志默认不含内容 | 保留期 ✅ |
| GDPR 第 30 条、DPIA | 处理活动记录 | 导出"哪个 Agent（及其模型提供方）处理了哪些会话"；DPIA 模板 | 🔧 |
| GDPR 告知 | 群内的 AI 处理需要告知成员 | Agent 加入时向全员发系统事件 | ✅ |
| **DSA** 第 16、17 条 | 举报通道；限制内容时给出处置理由 | 举报、审核队列、处置记录（§4.2） | ✅ |
| **UK Online Safety Act** | 违法内容的举报与处理；儿童保护 | 同上；预留年龄验证钩子 | 🔧 |
| **App Store 1.2 / Google Play UGC 政策** | 用户协议、过滤、举报、拉黑；24 小时内处理举报 | 用户协议确认（应用做）、内容过滤、举报、拉黑（[02 §2.4](02-architecture.md)）、带处理时限的审核队列 | ✅ |
| **CCPA / CPRA** | 访问、删除、不出售 | 复用 GDPR 的导出和删除工具 | ✅ |
| **COPPA** | 13 岁以下儿童 | 年龄门槛钩子 | ⏳ |
| 数据驻留 | 数据存储在指定地域 | 自托管由部署地决定；托管云按地域部署 | 自托管天然满足 |

### 4.2 A4 合规基础（✅ 2026-10-20）

只做每个部署都必须有的（D7、D62）：导出自己的数据、删除账号、举报、审核队列；保留期已有（[08 §2.5](08-sync-and-client.md)）。**导出和删除只给开发者的后端**（开放 API，`compliance` 权限，D116）：账号属于开发者的产品，开发者是数据控制者，由它在自己的界面里提供入口、核实身份、把导出的文件交给用户（Sendbird、Stream 也只在服务端提供）。App Store 5.1.1(v) 要求的是应用里能删除账号，开发者的 App 调自己的后端、后端再调我们即可。举报是给最终用户的（DSA 第 16 条），在客户端。参照：Discord 和 Slack 的数据导出（只导出本人的数据）、Apple App Store 5.1.1(v)（支持创建账号的应用必须能在应用里删除账号）、Google Play 用户生成内容政策、DSA 第 16 条（举报）和第 17 条（处置理由）。

#### 导出自己的数据（GDPR 第 15、20 条）

- `GET /v1/users/{id}/export`（`compliance` 权限）。客户端令牌不能导出。
- **边读边发**（NDJSON，每行一个 JSON 对象），不生成文件、不需要文件存储，集群和多库都一样；大的导出可以用 `after` 续传（每行带游标）。
- 内容：资料、设备（名称、平台、最后活跃）、偏好、拉黑名单、所在的会话（ID、标题、角色、加入时间）、**本人发的消息**（会话、seq、时间、类型、内容、状态；撤回的只有撤回标记）、本人给出的反馈和卡片回应、本人提交的举报、拥有的 Agent（名称和创建时间）。别人发的消息不导出（它们是别人的个人数据，Discord、Slack 也只导出本人的）。
- 不按人限次（开发者分页续传时每页就是一次），只受开放 API 按 Key 的限流。每次导出写一条审计 `api.users.export`（哪个 Key、何时，不含内容）。

#### 删除账号（GDPR 第 17 条、App Store 5.1.1(v)）

- `DELETE /v1/users/{id}`（`compliance` 权限），返回 202 和进度，`GET /v1/users/{id}/erasure` 查进度；删除记录里写上是哪个 Key 发起的。确认和二次核实由开发者的界面做。Agent 不按账号删除（400），用销毁。
- **立即**：标记为已删除（不能再登录、不能再被拉进群、不能再发消息），吊销全部令牌并断开所有连接。
- **然后逐个会话**（在会话所在的库里，由会话的写者执行，和发消息串行）：
  1. 清空这个人在会话里的所有消息内容和附带数据（和撤回一样：内容、载荷、旧事件里嵌的内容、草稿、未送出的 Webhook、反馈、卡片回应、搜索索引），写一条 `user.erased {user_id, upto_seq}` 事件：客户端收到后把本地这个人 `upto_seq` 之前的消息内容清掉；
  2. 退出会话（`member.removed`，原因 `account_deleted`）；如果是群主，群主转给最早加入的管理员，没有管理员就转给最早加入的成员；没有其他成员就解散。
- **最后**：删掉资料（名称改成"已删除的用户"，头像、自定义字段、密码、两步验证、设备、同步位置、偏好、拉黑记录），删掉他拥有的 Agent（走 Agent 销毁流程），发 Webhook `user.deleted`（开发者自己的系统据此删除）。
- **可恢复、可重复**：进度记在控制库（`erasures` 表），服务重启后接着做完；重复请求返回同一个进度。
- **和并发发送赛跑**：会话写者在清除时先把这个人记为已删除，之后排到这个会话的发送一律被拒（`forbidden`），所以清除完成后这个会话里不会再有他的新内容。
- 用户 ID 不复用：对已删除的 ID 调 `PUT /v1/users/{id}` 返回 `conflict`。
- 审计记录保留（只有"谁在何时做了什么"，不含内容，是法定义务）；备份无法逐条删除，按备份的保留期自然过期（§4.3）。

#### 举报（DSA 第 16 条、App Store 1.2、Google Play UGC）

- 客户端：`report {target_kind, target_id, category, text?}`；`target_kind` 是 `message`、`user`、`conversation`。
- 类别：`spam`、`harassment`、`hate`、`sexual`、`violence`、`self_harm`、`child_safety`、`illegal`、`impersonation`、`other`。`child_safety`、`self_harm`、`violence`、`illegal` 是高严重度。
- 规则：举报消息要能看到这条消息（是会话成员，且在自己的可见范围内）；举报会话要是成员；举报用户要存在、不能是自己。同一个人对同一个对象还没处理的举报只算一个（重复提交返回同一个）。`text` 最多 1000 字。每个用户每小时最多 20 次。
- 举报时**保存证据快照**（消息内容、发送者、会话、时间），之后消息被撤回也能审核；快照和消息内容一样静态加密。
- 错误码：不是成员 `forbidden`；未知或看不到的对象 `not_found`；类别错误、举报自己、太长 `bad_request`；太频繁 `rate_limited`。被拒绝的举报不留痕迹。

#### 审核队列（开发者后端，`moderation` 权限；控制台 A5 建在它上面）

- `GET /v1/reports?state=open`：按严重度、再按截止时间排序；截止时间 = 提交后 24 小时（App Store 要求），可配置。
- `GET /v1/reports/{id}`：举报、证据快照、同一对象的其他举报。
- `POST /v1/reports/{id}:resolve {action, reason, ground?, automated?, days?}`：
  - `action`：`none`（无需处理）、`remove_content`（以系统身份撤回这条消息；只用于消息）、`suspend_user`（停用 `days` 天，到期自动恢复）、`ban_user`（永久停用）；
  - **同一对象所有未处理的举报一起处理**，返回处理了几条；
  - 已处理的再处理返回 `conflict`；两个审核员同时处理只有一个成功。
- **处置记录**（DSA 第 17 条要求的字段）：处置类型、依据的事实（`reason`）、法律或条款依据（`ground`）、是否用了自动化工具（`automated`）、申诉途径（配置 `moderation.appeal_url`）、时间和处理人；写审计。
- Webhook：`report.created`、`report.resolved`（开发者据此通知举报人和被处置人）。
- 已处理的举报和证据快照保留 `moderation.keep_days`（默认 180 天）后删除。

```toml
[moderation]
due_hours = 24
keep_days = 180
appeal_url = ""          # 写进处置记录；空表示由开发者自己告知
report_per_hour = 20
```

#### 测试

每个接口的正常路径和每个错误码；边界（空、最长、未知 ID、重复、自己）；删除和并发发送赛跑（多轮，清除完成后这个人在会话里没有任何内容，变异检查）；删除中途崩溃后重启接着做完；重复删除；两个审核员同时处理；导出和同时发生的发送、删除；三种数据库、集群多库；客户端收到 `user.erased` 后清掉本地内容。

### 4.3 删除与保留

- **删除顺序**：清空内容、写墓碑事件（占 seq，客户端据此删除本地副本）→ 删除搜索索引和缓存 → 写一条审计记录（只记录"谁在何时删除了什么范围"，不记录内容）。
- **备份**：日志和备份无法逐条删除。备份同样加密、保留期有上限；会话级的删除通过销毁 DEK 实现（"销毁密钥是否等同于删除"没有明确判例，由使用者的法务确认）。
- 法律保全、电子取证、透明度报告、组织级保留策略不做。

## 5. 组织单元与多库隔离（高级配置）

免费的高级配置，没有许可证开关（D101）；大多数部署用不到。

### 5.1 要防的对象

| 对象 | 场景 | 手段 |
|---|---|---|
| 其他单元的用户 | 单元 A 的人看到单元 B 的群 | 授权：所有读写都按单元过滤（L1） |
| 法规或合同要求 | 必须单独存放，或者存在指定地区 | 物理隔离（L3） |
| AI Agent | Agent 把单元 A 的信息带到单元 B | Agent 归属到单元（§5.6） |

### 5.2 组织层级

租户（tenant）下分单元（unit），单元可以嵌套，下级继承上级的限制，只能更严、不能更松。用户、Agent、会话都归属于一个单元（`unit_id`）。

### 5.3 隔离等级

| 等级 | 做法 | 能防住 |
|---|---|---|
| **L1 逻辑隔离** | 与其他单元共用数据库。存储接口强制带"访问范围"参数，没有不带范围的查询路径；PostgreSQL 上再加 RLS 兜底（`FORCE ROW LEVEL SECURITY`，事务级 `SET LOCAL` 设置租户上下文，避免连接池复用时串租户） | 其他单元的用户和 Agent |
| **L3 物理隔离** | 该单元的会话全部存进专属数据库（[02 §5.4](02-architecture.md)），可以放在单独的服务器或地区 | 再加上法规和合同要求、其他单元的负载影响 |

L2（每个单元独立密钥）不做；要求更高时独立部署一套 agentim。

### 5.4 信息屏障

不做。

### 5.5 管理权限分级

不做。

### 5.6 Agent

- Agent 归属于某个单元；上下文接口按单元过滤。
- 工具网关的凭据按单元分别保管。

### 5.7 容易漏掉的地方

日志默认不含内容；指标标签不含用户和会话 ID；L3 单元的备份单独存放。
