# 04 安全与合规

> 版本 v0.4（2026-10-10）。静态加密默认开启（D3）和 MVP 内的 E2EE（D4）已确认；其余是**待确认的方案**，已实现的部分会单独注明。主要用户在海外，所以合规是基础需求，不是附加功能。

## 1. 身份与访问

| 项目 | 方案 | 依据 |
|---|---|---|
| 人类账号 | 账号密码，用 argon2id 哈希（m=19MiB、t=2、p=1）；可选 TOTP 二次验证；登录失败限流 | OWASP Password Storage Cheat Sheet 的最低建议参数 |
| 第三方登录 | OIDC（Google、Microsoft、GitHub）放社区版；SAML、SCIM 放企业版 | |
| Agent 凭据 | API Key，格式为"前缀 + 随机密钥"，可以设置权限范围、轮换和吊销；之后支持 OAuth client credentials | MCP 2025-11-25 授权规范 |
| Origin 校验 | 浏览器访问 `/ws` 和登录接口时，`Origin` 必须是本站或 `server.allowed_origins` 里的地址，防止跨站 WebSocket 劫持；App、SDK、Agent 不带 `Origin`，不受影响 | ✅ 已实现 |
| 内置 TLS | `[server.tls] cert/key`（PEM）后服务端直接提供 HTTPS 和 WSS（rustls + ring）；握手在接受循环之外进行、10 秒超时；也可以放在 TLS 反向代理之后（`open_api.behind_proxy`） | ✅ 已实现 |
| 会话令牌 | 256 位随机数；数据库里**只存 SHA-256 哈希**；有过期时间，可以吊销 | ✅ 已实现（`atk_` 前缀，老库升级时转为哈希） |
| 开发者后端签发令牌 | 开发者的后端用开放 API 给自己的用户签发客户端令牌（[07 §3.4](07-open-api.md)）；内置账号密码是给独立部署用的另一种方式 | Stream、腾讯云 IM 都是这样做 |
| 演示登录 | 只在 `--demo` 下可用；默认关闭（现状已经如此） | |
| 授权 | 集中在一个策略检查函数里；角色分为成员、管理员、所有者、组织管理员 | |
| **设备**（D14） | 每次登录创建一条设备记录（`device_id`、名称、平台、最近活跃时间、IP 所在地区）；每台设备有自己的刷新令牌（只存哈希）和短期访问令牌；用户和管理员都能看到设备列表并让单台设备下线 | Slack、Google 账号的设备管理 |
| 新设备登录通知 | 新设备登录时，向该用户的其他设备发系统通知（时间、平台、地区），可一键下线 | 海外用户普遍期待的账号安全功能 |
| 多端已读同步 | 一台设备标记已读后，服务端向同一用户的其他在线会话推送 `read.updated`，各端未读数立即一致 | |
| E2EE 设备密钥 | 每台设备一套 MLS 凭据，由服务器签发、绑定到用户；用户可以在另一台设备上核对安全码 | 见 §2.5 |

## 2. 加密

### 2.1 传输加密

- 内置 TLS（rustls），也可以放在反向代理之后；只用 WSS；开启 HSTS。
- WebSocket 握手时校验 `Origin`，防止跨站 WebSocket 劫持。
- 集群内部的 RPC 走 mTLS（集群阶段）。

### 2.2 静态加密：三种模式

| 模式 | 适用 | 密钥在哪里 |
|---|---|---|
| `off` | 开发、测试 | — |
| `managed` | **社区版和企业版默认开启**（D3） | 主密钥（KEK）来自本地密钥文件、环境变量或操作系统密钥库 |
| `byok` | 企业版 | KEK 在客户的 KMS 里：AWS KMS、GCP KMS、Azure Key Vault、HashiCorp Vault Transit |

### 2.3 密钥层级（信封加密，参考 Slack EKM）

```
KEK（主密钥，本地或 KMS 中；永不落盘到数据库）
 └─ DEK（数据密钥）：每个会话、每个时间窗口（默认按月）一个
     · 用 KEK 包装后存进 keys 表
     · 在内存中缓存，TTL 5 分钟（Slack 也是 5 分钟，以减少 KMS 调用并避开限流）
     └─ 内容：AES-256-GCM，随机 96 位 nonce
        AAD = (tenant_id, conv_id, msg_id, version)，防止密文被挪到别的消息上
```

- **加密的内容**：消息正文、侧信道内容（耳语、草稿）、工具调用的参数和结果、审计日志里的内容快照。
- **保持明文的内容**：ID、seq、时间戳、成员关系、发送者 ID。路由、排序和权限检查需要这些字段，这和 Slack EKM 的划分一致（频道名、成员记录由 Slack 自己的密钥保护）。
- **BYOK 吊销**：客户在 KMS 里吊销访问后，最多 5 分钟内（缓存过期）所有相关内容都无法解密；写入操作也随之失败（fail closed）；`/readyz` 和告警都会反映出来。
- **轮换**：DEK 按时间窗口自动轮换；轮换 KEK 时只需要重新包装 DEK，不必重新加密全部内容。
- **搜索**：服务端搜索需要索引，加密模式下索引本身也要加密。放到搜索功能那个阶段再做。

### 2.4 性能

AES-GCM 在支持 AES-NI 的 CPU 上，每个核心每秒可以处理数 GB（AWS-LC 在 Zen 3 上实测，AES-128-GCM 约 4.6 GB/s；AES-256 大约慢 30–40%）。一条 1KB 的消息加密只需要微秒级时间，远小于一次 fsync。KMS 调用按 DEK 摊销，命中缓存时为零。

**结论：开启加密对 CPU 和吞吐的影响应该很小，已确定默认开启（D3）。** 实现时在 CI 里加一项"加密开 / 关"的对比基准测试，数据写进 README。

### 2.5 端到端加密（E2EE，MVP 必须有，D4）

**方案：MLS（RFC 9420），用 OpenMLS（Rust 实现，严格遵循 RFC 9420，Phoenix R&D 和 Cryspen 维护）。** Google 和 Apple 在 RCS 上推行的也是 MLS；它为群组设计，成员增减的代价是对数级，比逐对加密（Signal 协议）更适合大群和多设备。

| 方面 | 做法 |
|---|---|
| 开启方式 | 创建会话时选择 `e2ee: true`，之后不可关闭。社区版可用；企业管理员可以按单元禁止（有保留、电子取证要求的组织需要这样做） |
| 加密套件 | `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`（RFC 9420 规定必须实现的套件） |
| 成员单位 | **每台设备是一个 MLS 成员**；拉一个人进群 = 把他的所有设备加进来 |
| 服务端角色 | 认证服务：给设备签发凭据，绑定到用户；投递服务：**我们的会话主日志正好提供 MLS 需要的全序**——每个 epoch 只接受第一个提交（Commit），后到的返回冲突让客户端基于新状态重试；KeyPackage 目录：每台设备预先上传一批一次性 KeyPackage 和一个兜底 KeyPackage |
| 客户端 | 加解密全部在 Rust 核心 SDK 里（[05 §6](05-operations.md)），各语言绑定共用，避免七种语言各写一遍密码学代码 |
| 新设备 | 只能看到加入之后的消息（MLS 的前向保密）。跨设备的历史同步（类似 Matrix 的密钥备份）放到 MVP 之后 |
| 设备核对 | 在另一台设备上比对安全码；之后考虑密钥透明（key transparency），防止服务端偷偷加设备 |

**开启 E2EE 后服务端做不到的事，必须在界面和文档里写明：**

| 能力 | E2EE 会话里 |
|---|---|
| 服务端的内容过滤、DLP、审批、审核 | 不可用（看不到内容） |
| 速率、接管、成员管理、审计（谁、何时、发了多大的消息） | 照常可用 |
| Agent | 只能作为 MLS 成员、运行在客户自己的环境里（D18）；过滤在 Agent 那一侧做 |
| 撤回 | 服务端删除密文，各客户端删除本地明文 |
| 举报（D7） | 举报人提交解密后的内容；之后用 message franking（Facebook Messenger 的做法）让服务端能验证举报内容确实是那条消息 |
| 服务端搜索 | 不可用；客户端本地搜索 |
| 离线推送通知 | 只能显示"有新消息"，不显示内容 |

参考：WhatsApp 的 Private Processing 用机密计算（TEE、远程证明、OHTTP）在不破坏 E2EE 的前提下运行 AI，是长期可以借鉴的方向。

## 4. 合规（海外）

### 4.1 法规与功能对照

责任划分：部署 AgentIM 的客户通常是"控制者"或"平台提供方"，我们提供让他们能够合规的功能。托管云上线后，我们自己也会成为处理者。

| 法规 | 要求 | AgentIM 功能 | 状态 |
|---|---|---|---|
| **EU AI Act 第 50 条**（2026-08-02 起适用，Digital Omnibus 没有推迟这一条） | 与人交互的 AI 必须让人知道对方是 AI；生成内容需要机器可读标记 | 服务端写入 `sender_type`，客户端必须展示 AI 标识；首次与 AI 对话时显示提示；消息带 `ai_generated` 元数据；媒体内容预留 C2PA 清单字段。参考欧盟委员会 2026-06 发布的标记与标识行为准则和 EU 图标 | 披露 ✅；标记 🔧 |
| **GDPR** 第 15、20 条 | 访问权、可携带权，一个月内答复 | 按用户导出机器可读的 JSON：消息、成员关系、审计记录 | 🔧 |
| GDPR 第 17 条 | 删除权（有例外，例如法律保全） | 删除用户：清空其消息内容并留墓碑；删除会话：销毁 DEK（crypto-shredding）；先检查法律保全 | 🔧 |
| GDPR 第 5 条 | 数据最小化、存储期限 | 按组织和会话设置保留策略，过期自动删除；日志默认不含内容 | 🔧 |
| GDPR 第 30 条、DPIA | 处理活动记录 | 导出"哪个 Agent（以及它背后的模型提供方）处理了哪些会话"；提供 DPIA 模板 | 🔧 |
| GDPR 告知 | 群内的 AI 处理需要告知成员 | Agent 加入时向全员发系统事件 | ✅ |
| **DSA** 第 16、17 条 | 举报通道（通知与处理）；限制内容时给出处置理由 | 举报 API；审核队列；处置记录（限制类型、依据的事实、法律或条款依据、是否用了自动化工具、申诉途径） | 🔧 |
| **UK Online Safety Act** | 违法内容的举报与处理；儿童保护 | 同上；预留年龄验证钩子 | 🔧 |
| **App Store 1.2 / Google Play 用户生成内容政策** | 用户协议、过滤、举报、拉黑；24 小时内处理举报 | 用户协议确认、内容过滤、举报、拉黑（被拉黑者的消息不再投递）、带处理时限的审核队列 | 🔧 |
| **CCPA / CPRA** | 访问、删除、不出售 | 复用 GDPR 的导出和删除工具 | 🔧 |
| **COPPA** | 13 岁以下儿童 | 年龄门槛钩子 | ⏳ |
| **HIPAA**（企业版） | 审计、加密、访问控制 | 提供这些控制项；BAA 只对托管云有意义 | 🔧 |
| 数据驻留 | 数据存储在指定地域 | 自托管时由部署地决定；托管云按地域部署 | 自托管天然满足 |

### 4.2 删除与保留的设计要点

- **删除顺序**：检查法律保全 → 清空内容、写墓碑事件（占 seq，客户端据此删除本地副本）→ 删除搜索索引和缓存 → 写一条审计记录（只记录"谁在何时删除了什么范围"，不记录内容）。
- **备份**：只追加的日志和备份都无法逐条删除。办法：备份同样加密，保留期有上限；会话级的删除通过销毁 DEK 实现。注意：业界对"销毁密钥是否等同于删除"没有明确判例，需要客户的法务确认。
- **legal hold（法律保全）**：被保全的用户或会话不受保留策略和删除请求影响，直到解除保全。

### 4.3 审核与举报流程

```
用户举报（消息 / 用户 / 会话，附原因）
  → 审核队列（按严重程度排序，显示处理时限倒计时；App Store 要求 24 小时内处理）
  → 处置：无需处理 / 删除内容 / 限制用户 / 封禁
  → 生成处置记录（DSA 第 17 条要求的字段）；通知被处置人，告知申诉途径
  → 写审计；可导出透明度报告（企业版）
```

## 5. 集团内的私密性：组织单元、隔离等级、信息屏障

### 5.1 要防的对象

| 对象 | 场景 | 手段 |
|---|---|---|
| 其他子公司的员工 | A 公司的人看到 B 公司的群 | 授权：所有读写都按单元过滤（L1） |
| 集团总部的管理员 | 总部 IT 导出子公司的聊天记录 | 分级管理 + 双人控制（§5.5） |
| 数据库管理员、运维、备份 | 直接查库或拿走备份 | 每个单元独立密钥（L2） |
| 法规或合同要求 | 必须单独存放，或者存在指定地区 | 物理隔离（L3） |
| 本来就不该有往来的部门 | 投行与研究部门之间的防火墙、并购项目组 | 信息屏障（§5.4） |
| AI Agent | Agent 把 A 公司的信息带到 B 公司，或者把内容交给不合规的模型 | Agent 归属到单元，按单元限制可用模型（§5.6） |

### 5.2 组织层级

```
集团（tenant）
 ├─ 子公司 A（unit，L1）
 ├─ 子公司 B（unit，L3，存储位置：欧盟）
 │   └─ 并购项目组（unit，可以继续嵌套，继承上级的限制，只能更严、不能更松）
 └─ ……
```

用户、Agent、会话都归属于一个单元（`unit_id`）。

### 5.3 三档隔离等级

| 等级 | 做法 | 能防住 |
|---|---|---|
| **L1 逻辑隔离** | 与其他单元共用数据库。存储接口强制带"访问范围"参数，代码里没有不带范围的查询路径；PostgreSQL 上再加 RLS 兜底（`FORCE ROW LEVEL SECURITY`，用事务级的 `SET LOCAL` 设置租户上下文，避免连接池复用时串租户） | 其他单元的用户和 Agent |
| **L2 加密隔离** | 在 L1 的基础上，每个单元有自己的主密钥（KEK），可以放在子公司自己的 KMS 里（BYOK）。单元可以自行吊销密钥；撤销整个单元时销毁密钥 | 再加上：数据库管理员、运维、备份泄露、集团总部 |
| **L3 物理隔离** | 在 L2 的基础上，该单元的会话全部存进专属数据库（[02 §5.4](02-architecture.md)，方案 A），可以放在单独的服务器或地区 | 再加上：法规和合同要求、其他单元的负载影响 |

最高密级还可以选择**独立部署一整套 AgentIM**（方案 B）：服务器、管理员、密钥全部分开。近期两套系统之间不能互相通信，跨部署的联邦或桥接放到后续阶段。集群阶段再提供专属分片（方案 C）。

### 5.4 信息屏障（参考 Microsoft Teams）

- 管理员在单元之间配置"禁止通信"规则，规则是双向的。
- 被禁止的双方：不能单聊，不能被拉进同一个群，在通讯录里互相不可见。
- 规则生效时：已有的单聊变为只读；群里被禁止的一方被移出，并产生全员可见的系统事件，同时写入审计。
- 检查发生在服务端：建会话、加成员、发消息、通讯录查询这几处。

### 5.5 管理权限分级

- 集团管理员只能配置策略，看不到 L2、L3 单元的内容。
- 内容导出、电子取证必须由该单元自己的合规负责人发起，并经第二人审批（双人控制），全程审计。
- 紧急访问通道：可以用，但每次使用都会告警，并留下完整审计。

### 5.6 Agent

- Agent 归属于某个单元，只能加入信息屏障允许的会话；上下文接口按单元过滤。
- 工具网关的凭据按单元分别保管。
- 可用的大模型按单元限制：例如高密级单元只允许使用自建模型，其他单元的 Agent 不得进入它的会话。这一条同时满足数据驻留和 GDPR 对第三方处理者的要求。

### 5.7 容易漏掉的地方

日志默认不含内容；指标标签不含用户和会话 ID；搜索索引、缓存、备份都用该单元的密钥加密；L3 单元的备份单独存放。

### 5.8 版本划分

- 社区版：单租户、`managed` 静态加密、基础单元划分（L1）、多库路由（方案 A 的机制本身）。
- 企业版：多级单元、每个单元独立密钥与 BYOK（L2）、物理隔离与指定地区（L3）、信息屏障、管理权限分级、双人控制的取证导出。

## 6. 需要你确认的问题

1. **静态加密默认开启吗？** 建议社区版默认开启 `managed` 模式（先用基准测试确认开销）。
2. **E2EE 放到后续阶段做，并且只用于纯人类会话**，可以吗？
3. **审核队列和举报功能放进社区版**（App Store 上架必须有），可以吗？
4. **§5.8 的版本划分**：信息屏障、每个单元独立密钥、L3 放企业版；多库路由的机制本身放社区版。可以吗？
