# 11 集群

> 状态：**C0–C4 已实现**（2026-10-18）。没做的：§8.5 的数据倒退检测和恢复（D100，待确认）；单个分片的手动交接（加节点、下线节点时按首选节点自动再平衡已覆盖运维需要）。
> 原则：集群是 `agentim` 程序的一部分，免费；**除数据库外不依赖任何组件**；节点平等，没有主从；会话分片的归属由数据库租约决定，**没有选举**；节点之间全互连；实现在独立的 crate `agentim-cluster`；测试按 §12。调研见 [research/cluster.md](research/cluster.md)。

## 1. 目标和范围

| 解决 | 不解决 |
|---|---|
| 高可用：任意一个节点崩溃、升级、断网，服务不停，消息不丢、不乱、不重复 | 数据库自身的高可用（由客户的数据库或托管服务负责；我们负责"数据库切主时也不丢已确认的消息"，见 §8） |
| 连接扩展：长连接分散到多个节点 | 跨地域多活 |
| 推送扩展：大群的推送由各节点分担 | 单个数据库的写入上限（靠 [02 §4.8](02-architecture.md) 的优化和多库） |
| 滚动升级：逐个节点升级，用户无感 | |

- 集群只支持 PostgreSQL 和 MySQL。SQLite 只用于单机，集群模式下拒绝启动。
- 不开集群时代码路径不变；数据库调用超时、写连接超时这些保护单机同样生效。

## 2. 正确性规则

所有设计都服务于这几条，测试（§12）逐条证明：

| # | 规则 | 防住什么 |
|---|---|---|
| G1 | **写库成功（且从库确认，§8）才回复成功**，然后才推送 | 任何时刻崩溃，已回复成功的消息都在 |
| G2 | **同一个会话同一时刻只有一个写入者**；序号在事务里用行锁分配 | 顺序不乱、序号不重复 |
| G3 | **每批写入在同一事务里校验租约代号**，用会和接手互相等待的写法（§4.3） | 旧负责人卡顿后醒来写不进去 |
| G4 | **幂等落在数据库**：`client_msg_id` 唯一约束 | 结果不确定时重试不会产生两条 |
| G5 | **结果不确定的写一律当作"可能已提交"**（§4.5） | 不会因为误判"失败"而重复或丢失 |
| G6 | **节点之间只传通知和转发请求，不传数据**；通知丢了只影响实时性，客户端从数据库补齐 | 节点间网络出问题不影响正确性 |
| G7 | **读取只返回已确认复制的部分**（§8.3） | 别人看到的消息不会在数据库切主后消失 |
| G8 | 第二层保护：`(会话, 序号)` 唯一约束 | 即使分片保护有缺陷，也不会写出重复序号 |

## 3. 结构

```
                   负载均衡（可选；SDK 也可以配置多个地址）
                     │ WebSocket / HTTP
  ┌──────────────┬───┴──────────┬──────────────┐
  节点 A          节点 B          节点 C          ← 同一个程序，角色完全相同
  · 连接、推送     · 连接、推送     · 连接、推送
  · 持有分片 0–85  · 持有分片 86–170 · 持有分片 171–255（每个分片一个租约）
  · 每个库一个写线程，负责本节点持有的所有分片
  └──── 节点间全互连（TLS）：转发请求、事件和失效通知 ────┘
                     │
            PostgreSQL / MySQL（客户自己的主从或托管服务）
            · 业务数据 · 节点表 · 分片租约表 · 集群元数据
```

- **分片**：每个数据库的会话按 `hash(会话编号) mod V` 分到 V 个虚拟分片，V 在集群初始化时固定（默认 256，D80，之后不能改）。另有两个分片走同样的租约：**控制分片**（用户、令牌、Agent、API Key、目录）和**维护分片**（去重记录和设备位置的清理、Webhook 投递）。
- **写线程**：每个节点每个数据库一个写线程（单写者 + 批量提交），负责本节点持有的全部分片。数据库连接数 = 节点数 × 数据库数，不随分片数增长。
- **首选节点**：每个分片按会合哈希（rendezvous hashing）在当前存活节点里算出首选节点。首选只是建议；**能不能写只看数据库租约**。

## 4. 分片租约

### 4.1 表

```sql
cluster_meta(k PK, v)            -- 集群编号、分片数等，初始化时写入，之后只读
cluster_nodes(node_id PK, boot_id, addr, slot UNIQUE, version,
              state /* joining|active|leaving|draining */, heartbeat_at)
-- 初始化时为每个分片预先建好（不在抢的时候插入，避免 MySQL 间隙锁死锁）
shard_lease(db, shard_id, PRIMARY KEY (db, shard_id),
            owner /* node_id:boot_id，可空 */, epoch, expires_at, fence_count)
```

- 租约行和它保护的数据**在同一个数据库**（多库时每个库有自己的租约行），校验和写入在同一个事务里完成。
- 时间（毫秒）一律在 SQL 里取数据库时钟：PostgreSQL `clock_timestamp()`（不是事务开始时间 `now()`），MySQL `UTC_TIMESTAMP(6)`（和会话时区无关）。应用不把自己的时间传进去。
- 节点身份 = `node_id`（配置或首次启动生成，持久）+ `boot_id`（每次启动随机生成）。同一个 `node_id` 重启后算新的持有者；节点编号被另一个活着的进程占用时拒绝启动。

### 4.2 抢、续、交

| 操作 | SQL 要点 | 结果判断 |
|---|---|---|
| **接手**（租约过期或无人持有） | `UPDATE shard_lease SET owner=?, epoch=epoch+1, expires_at=<数据库时间>+租约时长 WHERE db=? AND shard_id=? AND (owner IS NULL OR expires_at < <数据库时间>)`，独立的短事务 | 影响行数必须**正好是 1**；0 表示没抢到 |
| **续约** | 一条语句续本节点持有的全部分片：`UPDATE … SET expires_at=… WHERE (db, shard_id, owner, epoch) IN (…) AND expires_at > <数据库时间>`，走专用连接 | 影响行数等于持有数才算全部续上；少了的分片立即自停 |
| **过期后自己续回** | `UPDATE … SET epoch=epoch+1, expires_at=… WHERE … AND owner=我 AND epoch=旧值` | 成功说明中间没人持有过；失败就是被接手了 |
| **计划内交接** | 旧负责人停收、排空、提交后：`UPDATE … SET owner=目标, epoch=epoch+1, expires_at=… WHERE … AND owner=我 AND epoch=当前`，并通知目标（`CHECK` 帧） | 目标节点立即可写，不用等租约到期 |
| **释放**（下线） | `UPDATE … SET owner=NULL, expires_at=<数据库时间> WHERE … AND owner=我 AND epoch=当前` | 别人立即可接手 |

- 每个续约间隔每个库一轮：续约、和租约表对比"该持有 / 实际持有"、接手空闲分片、把分片交给它的首选节点。
- 首选节点在租约到期后立即抢；非首选节点晚一个续约间隔才抢；刚失去某个分片的节点，一个租约时长内不抢回它。
- 每轮每库最多接手 10 个分片、最多交出 4 个给首选节点。新节点被看到两个续约间隔后才分给它分片。

### 4.3 每批写入的校验（核心）

批量事务里**提交之前的最后一条语句**（在各命令的保存点之后；之前的写都未提交，所以安全性和放在第一条相同，行锁只持有到提交前一瞬间，接手等得更短）：

```sql
UPDATE shard_lease SET fence_count = fence_count + 1
 WHERE db = ? AND (shard_id, owner, epoch) IN ((?, ?, ?), …)   -- 本批涉及的分片，按分片号升序
-- 影响行数必须等于本批涉及的分片数，否则整批回滚，这些分片立即自停
```

- 这条 `UPDATE` 拿到租约行的排他锁直到提交。接手者的 `UPDATE` 必须等它提交，之后 PostgreSQL 在新版本上重新判断条件，MySQL 的 `UPDATE` 读最新提交的版本。所以"旧负责人提交"和"新负责人接手"一定有先后，**不会两个代号都提交成功**。
- 计数加一让值一定改变，影响行数不依赖 MySQL 驱动的"匹配行数"设置。
- 代号用"等于"比较，不用"大于等于"：数据库切主后租约表可能回到旧代号，等值比较让节点自停后重新接手。
- 校验里不加"未过期"条件：安全性来自行锁加代号，时间条件只会在边界制造假失败。

### 4.4 时间参数

| 参数 | 默认 | 约束 |
|---|---|---|
| 租约时长 D | 15 秒（D73） | 最坏的接手时间约 D + 3 秒 |
| 续约间隔 R | 3 秒 | 一次失败还有多次重试机会 |
| 单次数据库操作超时 T | 2 秒 | 所有数据库调用都有 |
| 自停时间 F | 10 秒，从**发出续约请求之前**的本地单调时间算起 | `R + 2T ≤ F < D`，`D / F ≥ 1.5`（容忍 1.5 倍的时钟速率差）；启动时检查，不满足拒绝启动 |
| 写连接的锁等待 | PostgreSQL `lock_timeout` 2 秒；MySQL `innodb_lock_wait_timeout` 2 秒（默认 50 秒太长） | |
| 写连接的会话超时 | F：PostgreSQL `idle_in_transaction_session_timeout`，MySQL `wait_timeout`；空闲时每 F/4 检查一次连接 | 断开的写线程不会一直锁着租约行 |

到了自停时间还没续上，节点立刻停止写这个分片、停止为它推送，不等数据库通知。

### 4.5 结果不确定和错误分类

所有数据库错误在**一个函数**里分三类：

| 类别 | 例子 | 处理 |
|---|---|---|
| 明确没写进去 | 唯一约束冲突、校验失败、校验语句影响行数不对 | 返回业务错误码；校验失败时分片自停 |
| 失去归属 | 校验语句影响 0 行；接手、续约时发现别人持有 | 分片自停，回到待命；**不重试** |
| 结果不确定 | 超时、连接断开、提交时出错、序列化失败、未知错误 | 见下 |

结果不确定时：
1. 停止写这个分片，丢掉它的内存状态（流式状态、成员缓存等）。
2. 用"过期后自己续回"的写法把代号加一。这一步会等旧事务结束，所以之后读到的就是确定的结果。
3. 从数据库重新加载分片状态。
4. 本批所有请求返回可重试错误 `unavailable`（D78）。客户端用同一个 `client_msg_id` 重试，已经写进去的直接返回原来那条。
5. 本批不推送。

- MySQL 死锁（整个事务回滚、保存点随之消失，错误 1305）是**明确没写进去**：按可重试处理，下一批前换一条连接，不交出分片。
- 只有带**当前代号**的错误才改变分片状态，旧请求的迟到错误直接返回给调用方。
- **提交不能被取消**：写线程的提交不受客户端断开或请求超时影响；超时只用来判定"结果不确定"，不去取消正在等从库的提交（PostgreSQL 取消后数据已经本地可见）。

### 4.6 卡死保护

- 写线程一批超过 `F × 3/4` 还没完成就判定卡死。集群模式下卡死或写连接出错时，不像单机那样停止整个库：本节点放弃这个库的全部分片，丢掉并重建写连接，再用"过期后自己续回"的写法把代号加一后重新接手、重新加载（§4.5）。
- 续约由写线程的进展驱动：续约前先让写线程执行一个空命令，在 `F − R − T` 内没完成就不续约，别的节点会接手。租约循环对写线程的每次等待都有上限，写线程卡住不会拖住续约。
- 因对方租约过期而接手的分片，3 个租约时长内不按首选节点交还给它（防止交还给仍然卡住的节点后来回弹）。
- 连续 5 轮续约失败（`FAILED_ROUNDS`），节点报未就绪（`/readyz` 返回 503，原因写在 `cluster` 字段）并让所有客户端重连到别的节点；续约恢复后重新就绪。

## 5. 请求路由和转发

| 请求类型 | 在哪里执行 |
|---|---|
| 读（同步、历史、搜索、上下文、列表、未读） | 收到请求的节点直接读数据库（受 §8.3 的水位线限制） |
| 写某个会话 | 该会话分片的负责人 |
| 写控制库（用户、令牌、设备、Agent、API Key、拉黑） | 控制分片的负责人 |
| 跨多个分片的操作（建会话、解散、销毁 Agent 等） | 每一步发给对应分片的负责人；崩溃后的修复逻辑和单机相同 |

- `Hub` 调写线程都经过 `Router`：分片在本节点就交给本地写线程，否则转发给负责人；写线程命令（`Op`）可序列化。
- 负责人从本地缓存的"分片 → 持有者"取，缓存没有或需要重试时从租约表读当前未过期的持有者。分片不归对方时它回 `not_owner`。
- 分片正在移动（交接、下线、接手；`not_owner`、无人持有、请求没发出去）时，请求最多跟随 4 秒（`FORWARD_FOLLOW`），间隔从 25 ms 翻倍到 400 ms，之后返回 `unavailable` 并计入 `agentim_cluster_forward_exhausted_total`。
- 转发后等回复 5 秒（`FORWARD_WAIT`）。等不到就是结果不确定：对客户端返回 `unavailable`，**绝不返回"失败"，已经发出的请求绝不重发**；客户端用同一个 `client_msg_id` 重发。
- 被拒绝的请求（`forbidden`、`not_found`、`conflict`、`bad_request`、`blocked`、`rate_limited`）经过转发后错误码不变，不留痕迹。

## 6. 节点之间的通信

### 6.1 连接

- 节点从节点表发现彼此。每个节点向每个其他节点发起**一条** TLS 长连接，自己的转发请求和通知都走自己发起的那条（每对节点两条，每条只有一个方向的请求）。
- 集群自己的证书：第一个节点生成集群 CA，私钥用集群密钥派生的密钥加密存在数据库里；每个节点启动时给自己签发新证书，连接两端都必须出示这个 CA 签的证书。用户不用管证书。
- 握手（HELLO）双方都发：集群编号、节点编号、启动编号、协议版本范围、程序版本、能力列表。集群编号不同、节点编号和节点表不符、版本范围没有交集，都拒绝并告警。握手超时 5 秒。
- 对端的启动编号变了，说明它重启过：它之前转发中的请求全部按结果不确定处理，它的迟到帧全部丢弃。

### 6.2 存活和背压

| 项 | 做法 |
|---|---|
| 心跳 | 应用层 PING/PONG 每 2 秒；10 秒没**收到**任何帧就断开重连（每个方向单独判断，不靠 TCP 保活） |
| 重连 | 指数退避，100 毫秒起、上限 5 秒，加随机抖动 |
| 发送队列 | 每条连接最多 10 万帧，满了就断开该连接并告警（对端回来后让它的客户端重新同步）；**写线程只往队列里放，不等对端**，慢节点不会拖慢提交 |
| 单帧上限 | 8 MB，超了拒收并断开；要发的通知超过上限时不发，断开连接让对端的客户端重新同步 |
| 坏帧 | 魔数错误、长度超限、截断：断开；未知消息类型、未知字段：忽略并计数 |

### 6.3 帧

```
帧头 16 字节（字段位置固定，用测试锁住）：0..4 magic "AIMB" · 4..8 帧体长度（大端 u32）· 8 编码版本（1）· 9 消息类型 · 10..12 标志 · 12..16 保留
帧体：JSON（新字段可选、未知字段忽略；需要时再换二进制编码，编码版本字段就是为此留的）

HELLO          握手（§6.1）
FORWARD_REQ    转发的写命令：请求编号、库、分片号、命令
FORWARD_RESP   结果：ok | 业务错误码 | not_owner | unavailable | unsupported_op
PUBLISH        提交后的事件通知和失效通知（§6.4、§6.5）
CHECK          "现在看一下租约表"（分片刚交给你）
PING / PONG
```

- 能力协商（当前能力 `forward`、`publish`、`check`）：对端没声明某项能力，就不给它发依赖这项能力的帧或命令，改为本地处理或返回 `unsupported_op`。

### 6.4 事件通知和缺口

- 负责人提交后，把事件通知（PUBLISH）发给所有其他节点，**同一会话的通知按序号顺序发出**；收到的节点推给本机的相关连接。客户端的同步协议已经能处理：序号跳号就同步，旧序号丢弃。
- **尾部丢失**（最后一条通知丢了、之后没有新消息）：客户端用 `heads` 做位置校验（Agent SDK 每 30 秒一次），和服务端比对所在会话的最新序号，不一致就同步。
- 和某个节点的连接断开又重连：本节点上订阅了那个节点所负责会话的客户端，都收到"请同步"提示。

### 6.5 缓存失效（安全相关）

拉黑、吊销令牌、停用账号、急停和销毁 Agent、转交 Agent，这些改动必须在所有节点生效：

1. 写改动的同一个事务里，把数据库里的失效计数（`auth_epoch`）加一。
2. 提交后用 PUBLISH 通知所有节点重新加载；拉黑本身也作为通知发出（不等轮询）。
3. 每个节点每 2 秒读一次失效计数，变了就从数据库重新加载令牌、用户、拉黑和 Agent 状态，作为通知丢失时的兜底（也覆盖 CLI 等其他进程的改动）。
4. 和某个节点断连、或对端重启时，本节点从数据库重新加载安全相关的缓存。
5. 写入路径上，负责人在事务里再检查一次（急停、销毁、拉黑），写入不会因为缓存滞后而放行：会话和拉黑记录在同一个库时（单库部署）直接查拉黑表；多库时会话库的负责人用通知更新的缓存（毫秒级滞后，[06 §1.1](06-plan.md) D98）。

**保证**：改动提交后，最迟 3 秒内所有节点生效（推送、读取路径）；写入路径立即生效。测试证明（§12.4）。

## 7. 节点的生命周期

| 阶段 | 做法 |
|---|---|
| 启动 | 启动检查（§9）→ 写节点表（`joining`）→ 和其他节点建连 → 第一轮接手首选分片后开始服务；启动后两个续约间隔（默认 6 秒）内节点表状态是 `joining`、不分给它别人的分片，之后为 `active` |
| 运行 | 心跳 2 秒；节点表超过 10 秒（租约时长的 2/3）没更新视为离线（只影响路由和首选节点计算，不删数据） |
| 加入新节点 | 新节点成为部分分片的首选；现负责人对这些分片做**计划内交接**（§4.2），每轮每库最多 4 个 |
| 优雅下线（升级、缩容） | 收到 SIGTERM 或 Ctrl-C 时执行 `Node::leave`：节点表改为 `leaving`（仍可连接，但不再被选为首选）→ 对每个分片：先标为"排空中"，不收新命令，已进入写线程的批次仍按原租约提交，写线程处理完已排队的命令后，租约一步交给下一个首选节点并立即通知它 → `/readyz` 返回 503，WebSocket 客户端收到关闭码 1012（`server_restart`）后重连到别的节点 → 对迟到的转发请求回 `not_owner` 一小段时间 → **最后**停心跳和退出 |
| 崩溃 | 别的节点在租约到期后接手（约 15–18 秒）；客户端重连到别的节点并同步 |
| 管理员下线 | `agentim cluster drain --node <id>` 把节点表状态改为 `draining`（只对在服务的节点有效，否则报错、不改任何东西）；节点在下一次心跳发现后按优雅下线交出全部分片、`/readyz` 返回 503、让客户端重连，但进程不退出，由管理员停掉；再启动即重新加入 |
| 查看 | `agentim cluster status` 列出节点（状态、距上次心跳）和每个库各节点持有的分片数、无人持有的分片数。两个命令只读写集群表，不需要节点应答 |

**滚动升级**：支持相邻两个版本同时运行。
- 协议靠能力协商兼容：HELLO 带能力列表，旧节点不带时按空处理；对端发来本版本不认识的命令，回 `unsupported_op`；事件里有本版本不认识的种类，逐条跳过、其余照常生效，并让本机连接重新同步。
- 表结构变更"先加后删"：新版本加列且旧版本能忽略，下一个版本才删旧列。
- 分片移动期间的转发规则见 §5：没有发出去的请求可以换节点重发；已经发出、结果不确定的，绝不重发。

## 8. 数据库主从和"不丢已确认的消息"

### 8.1 三种模式（启动时自动识别）

| 模式 | 识别 | 提交后怎样才算已复制 |
|---|---|---|
| 无从库 | 看不到从库，或配置 `mode = "none"` 声明没有 | 提交即算 |
| 数据库端同步 | PostgreSQL 配了 `synchronous_standby_names` 且 `synchronous_commit` 至少为 `on`；MySQL 半同步、等待点 `AFTER_SYNC` | 提交返回即算；MySQL 每批提交后检查 `Rpl_semi_sync_source_status`，退回异步时按 §8.2 扣住、回复 `unavailable` |
| **应用等待**（异步从库，默认配置） | 看得到从库但没有同步配置 | 我们自己等（§8.2）：PostgreSQL 提交后在同一连接上取 `pg_current_wal_lsn()`（覆盖这次提交），比较 `pg_stat_replication` 里从库的 `flush_lsn`；MySQL 需要 GTID，取 `@@GLOBAL.gtid_executed`，逐台连 `replica_urls` 检查 `GTID_SUBSET`；MariaDB 用 `gtid_binlog_pos` 和 `MASTER_GTID_WAIT(…, 0)` |
| 托管同步（声明，D77） | 看不到从库，但管理员声明 `mode = "managed_sync"`（RDS Multi-AZ、Cloud SQL 高可用、Azure） | 提交即算；声明写审计并在 `/readyz` 显示 |

配置在每个库的 `[storage.databases.replication]` 下（`agentim_core::replication`）：`mode = "auto"`（默认）/ `"managed_sync"` / `"none"`；`wait_ms`（默认 5000）；`replicas_required`；`replica_urls`（MySQL 应用等待必填）。识别结果写日志，并在健康检查的写线程状态里显示（`replication`、`unconfirmed`）。识别失败时拒绝启动并给出原因：PostgreSQL 看得到从库但看不到位置时提示授予 `pg_monitor`；MySQL 有异步从库但没配 `replica_urls` 或没开 GTID 时提示。

### 8.2 应用等待的规则

- 等哪些从库：默认**所有正在复制的从库**（不知道切主工具会提升哪一台）；可用 `replicas_required` 配置为 N 台（D74）。`replica_urls` 里**当前主库自己**（切主后）不算从库；连不上或卡住的从库算"落后"，不会被悄悄跳过（修好、从配置里去掉，或设 `replicas_required`）。
- **0 台从库算"不满足"，不算"不用等"**：被隔离的旧主看不到从库，这一条让它无法回复成功。
- 写线程按顺序等（一个库一个写线程，等待期间新命令排队、自然合成更大的批次）；轮询间隔从 2 ms 翻倍到 50 ms。
- 等不到（`wait_ms`）：这批已在主库提交，标为"已提交未确认"，它的事件、推送、Webhook 唤醒都**扣住**，客户端收到 `unavailable`（用同一个 `client_msg_id` 重试会去重并等到确认）；**绝不悄悄降级**。写线程空闲时每 200 ms 再问一次从库，后面任何一批确认时，扣住的内容按顺序一起放出。
- 被拒绝的命令（例如没有权限）照常回复原来的错误，不受等待影响。
- 集群的续约屏障（`Barrier`）不写数据，提交后立即回复、不等从库，所以从库慢不会让节点丢掉租约。

### 8.3 读取水位线

应用等待模式下，提交一返回别人就能读到，但从库可能还没有。所以每个会话记录已确认复制的序号 `conversations.confirmed_seq`（结构版本 6）：
- 应用等待以外的模式：分配序号的同一条 `UPDATE` 同时推进它（没有额外语句），读取也不加限制。
- 应用等待模式：确认后对本批涉及的会话设 `confirmed_seq = 本批的最大序号`（只往前走；不会把别的节点刚提交、还没确认的序号一起放出）。读会话记录的路径（同步、历史、搜索、上下文、导出、Agent 拉取）只读 `seq <= confirmed_seq`，会话的 `last_seq` 读出来时取两者较小值。写线程自己读全部数据。
- 升级前的会话（`confirmed_seq` 为空）启动时按已复制处理。
- 成员列表、未读数这些读状态的路径，切主瞬间可能短暂显示未确认的状态；切主后客户端按同步协议的原因码修正（D75）。
- 限制：应用等待模式的集群里新旧版本混跑时，旧版本节点不推进水位线，新版本节点读到的会滞后，直到旧节点升级完成。

### 8.4 数据库切主的检测和处理

- 主库身份：PostgreSQL 取 `(system_identifier, 时间线)`，时间线从 `pg_walfile_name(pg_current_wal_insert_lsn())` 取；MySQL 取 `server_uuid`。写线程启动时记下，并拒绝连到从库或只读的服务器（PostgreSQL `pg_is_in_recovery()`、`transaction_read_only`；MySQL `read_only`、`super_read_only`）。
- 遇到只读类错误（PostgreSQL 25006、57P01；MySQL 1290、1836、1792）时整批放弃（不再逐条记错误、提交剩下的部分）。只读类错误或连接断开（PostgreSQL、MySQL；SQLite 照旧按存储故障处理）都按"结果不确定"回复 `unavailable`，丢掉扣住的内容和缓存的会话状态；集群模式下同时交出这个库的全部分片（§4.5）。
- 下一批先重连并确认连到的是可写的主库；身份变了就记日志和指标 `agentim_db_failovers_total`。
- 找新主依赖配置的地址（VIP、DNS 或代理）在切主后指向新主（sqlx 不支持多主机地址）。读连接池在取出时检查连接，断掉的重新连到同一地址。
- 旧主被隔离但还活着、地址还指向它时，读取可能是旧数据，但它没有从库确认，不能回复任何写入成功。

### 8.5 防线被绕过时：检测、恢复、告知（未实现，D100）

§8.1–§8.4 保证正常配置下已确认的消息不丢。防线可能被绕过：管理员关闭了从库等待、托管同步声明错了、有人手动切了库、数据库从备份恢复、误把旧主库接回来。这时**服务必须能起来，并且不能带着错乱的数据悄悄运行**。

**会是什么样**：PostgreSQL 物理复制和 MySQL（GTID + 按提交顺序回放）都按事务顺序复制，被提升的从库是旧主某一时刻的完整快照，**只是少了最后一段**：最后几条消息不见了；同一个序号对应两条不同的消息（新消息从较小的序号继续分配）；客户端的同步位置比服务端还大；成员、拉黑、设置回退；去重记录丢失。

**检测**

| 信号 | 说明 |
|---|---|
| 主库身份变了 | PostgreSQL 时间线、MySQL `server_uuid`（§8.4） |
| 数据倒退 | 每个节点在本地小文件里记住上次见到的主库身份、各分片的最大代号和已确认位置；启动时数据库比记住的还旧，说明少了一段或连到了更旧的库 |
| 客户端位置超前 | 客户端报上来的同步位置大于服务端最大序号 |
| 一致性检查 | `agentim db check`：会话序号连续、目录和会话对得上、设备位置不超过会话最大序号、引用的消息存在、多库之间的目录一致 |

**恢复**

1. 默认自动进入**恢复模式**启动：跑一致性检查，能安全修的自动修（把超前的设备位置调回、修复目录）；`/readyz` 和指标显示恢复模式。
2. 发现**接到了比上次更旧的库**（时间线或代号更小）时拒绝写入，提示"可能接错了库"；管理员确认后执行 `agentim cluster accept-rewind`（写审计），再按恢复模式启动。
3. 倒退的会话**更换会话纪元**，并告诉客户端**分叉点**（新主库上这个会话的最大序号）；游标大于服务端最大序号时返回明确的错误让客户端重建，不返回空结果。
4. 客户端**按消息编号对账，不删除本地记录**：

   | 本地消息 | 处理 |
   |---|---|
   | 分叉点之前 | 原样保留 |
   | 分叉点之后、服务端有同一个消息编号 | 保留，按服务端的新序号调整位置 |
   | 分叉点之后、自己发的、服务端没有 | 用原来的 `client_msg_id` **补交**，服务端去重；补回的消息标为"恢复的消息" |
   | 分叉点之后、别人发的、服务端没有 | **保留**，标记"服务器上已缺失"；发送者补交回来后按消息编号自动合并 |
   | 撤回、编辑操作丢失 | 消息重新出现时，撤回或编辑的人看到"操作未生效"，可以重做 |

   只有纪元变了的会话才对账；其他会话、草稿、设置、文件缓存都不动。
5. **彻底重建的会话**（分叉点为 0 或对不上）：**不清空本地记录**。客户端把这个会话的本地记录归档到只读的"旧记录"区（照常可查看和搜索），提示用户并提供导出到本机文件；用户确认前不覆盖任何本地内容；Agent 客户端自动导出并在日志里写明路径。归档受本机保留策略和用户删除请求约束（GDPR）。

**告知**：管理员——审计记录切主时间、倒退的会话及各自少了多少条、补交找回了多少，恢复模式在 `/readyz` 和告警里可见；用户——受影响的会话里一条系统事件（"服务器恢复了数据，这段时间的部分消息可能缺失"）。

检测和 `accept-rewind` 只在服务端；客户端的对账、补交、归档、导出放在客户端 SDK 的 Rust 核心里（[12 §2.2](12-developer-experience.md)）。

## 9. 启动检查（集群模式）

不满足就拒绝启动，并给出原因和修复命令（不悄悄降级）：

| 检查 | PostgreSQL | MySQL |
|---|---|---|
| 版本 | ≥ 14（D76） | ≥ 8.0，开启 GTID |
| 连的是主库 | `pg_is_in_recovery() = false` | `read_only = 0`、`super_read_only = 0` |
| 持久性配置 | `fsync = on`、`full_page_writes = on`；会话设 `synchronous_commit` 不低于 `local` | `innodb_flush_log_at_trx_commit = 1`、`sync_binlog = 1`、`binlog_format = ROW` |
| 权限 | 能看到 `pg_stat_replication` 的位置列（否则提示授予 `pg_monitor`） | 有 `REPLICATION CLIENT`；**没有** `SUPER`、`CONNECTION_ADMIN` |
| 从库模式 | 识别 §8.1 的模式；应用等待模式下至少能看到 1 台从库，或已声明托管同步 | 同左 |
| 集群 | 集群编号一致（集群密钥能解开 CA）；分片数和元数据一致；时间参数满足 §4.4 的约束；节点编号没有被另一个活着的进程使用 | 同左 |

## 10. 单进程假设的清单

只在一个进程内成立的东西，集群下的处理（新功能不再增加新的单进程假设，这张表随代码维护）：

| 单机 | 集群下 |
|---|---|
| 在线连接表（`Registry`） | 只管本机连接；跨节点推送走 §6.4 |
| 内存缓存：用户、令牌、拉黑、停用、急停、销毁、API Key（`Shared`） | 失效计数 + 通知 + 兜底轮询（§6.5） |
| 会话目录 | 每次改动发给所有节点；本节点没有的条目在请求和转发进来时从库里读（`Hub::dir_ensure`）；控制分片接手后的修复先从库里重新读整个目录，且不删除正在迁移的会话的副本 |
| 进程内的全局锁（单聊唯一的 `dm_lock` 等） | 数据库唯一约束，或由负责人在事务里判断 |
| 限流计数（MCP、同步、进度、建会话、未知令牌查库） | 按节点计算；集群下的实际上限是"每节点上限 × 节点数" |
| 写线程里的会话状态（流式回复、防循环预算、成员缓存） | 跟着分片走；接手时重新加载，进行中的流式回复按"中断"结束 |
| 定时任务（看门狗、过期处理、保留期清理） | 跑在写线程里，只处理本节点持有的分片；控制库的任务跟着控制分片走 |
| Webhook 投递、去重记录和设备位置的清理（每个库） | 只由该库维护分片的负责人运行 |
| 多设备通知（其他设备已读、新设备登录） | 走 §6.4 的通知 |

## 11. crate 结构和分步

### 11.1 crate

- `agentim-core`：`Router` 接口（本地实现即单机行为）、可序列化的写线程命令、批量事务的校验钩子、读取水位线和从库等待（`replication`）、数据库调用超时、故障点（`failpoint`）。
- `agentim-cluster`：集群的全部实现——租约（SQL 两套方言）、会合哈希和首选节点（`assign`）、节点表和心跳、节点间连接和 TLS（`peer`、`ca`）、帧编码和能力协商（`codec`）、转发、通知和失效、启动检查、错误分类、管理命令（`admin`）。
- 程序 `agentim` 带集群，配置里不开就是单机。
- 纯逻辑（租约判断、哈希、帧编码、错误分类、时间参数校验、水位线）不碰网络和数据库，时钟可注入，单元测试覆盖；有 I/O 的部分很薄，在真实的 PostgreSQL 和 MySQL 上测。

### 11.2 分步

C0（前置：超时、MySQL 死锁行为、Windows CI 的 PostgreSQL 和 MySQL、代码接缝、测试基础设施）、C1（基础集群）、C2（平滑运维）、C3（数据库主从）、C4（部署和观测）**已实现**。剩下：§8.5（D100）、单个分片的手动交接。

| 租约状态机 | 待命 → 接手中 → 持有 → 续约成功 / 失败 / 超时 → 自停 → 待命；结果不确定 → 重新接手；每个转移、每个非法转移；代号只增不减 |
| 自停截止时间 | 从发出续约前算起；时钟前跳、后跳、速率偏差 1.5 倍内外；正好等于截止时间 |
| 时间参数校验 | `R + 2T ≤ F < D`、`D / F ≥ 1.5`：相等、差 1、为 0、为负、超大值 |
| 错误分类 | PostgreSQL 和 MySQL 的每个错误码、连接断开、超时、未知错误各分到哪一类；只有"影响 0 行"立即失去归属 |
| 会合哈希 | 分布均匀；节点增减时只移动最少的分片；同样输入同样输出；1 个节点、节点编号相同前缀 |
| 防抖 | 非首选节点的延迟、刚失去的分片冷却期 |
| 帧编码 | 每种帧往返编解码；截断、超长、魔数错误、未知类型、未知字段、缺失可选字段的默认值；帧头字段位置固定 |
| 能力协商 | 版本范围交集为空、单点、包含；对端缺能力时不发对应帧 |
| 转发 | 跟随上限、归属缓存的刷新 |
| 水位线 | 只增不减；乱序确认时按顺序推进 |

### 12.3 模块逻辑测试（单节点 + 真实数据库）

| 用例 | 断言 |
|---|---|
| 接手：空闲、未过期、已过期、并发 N 个节点抢同一个分片（多轮） | 每轮正好一个成功，代号正好加一 |
| 续约：自己的、过期的、代号不对的、别人的 | 只有自己未过期的成功 |
| 抢分片 A 不影响分片 B | 变异：去掉分片条件时必须失败 |
| 校验：手动把代号改大后，旧代号的批 | 整批失败，消息、序号、游标、审计里没有任何痕迹 |
| 校验和接手赛跑：批在校验后暂停，另一个连接发起接手 | 接手等到批提交后才成功；提交记录里代号单调；PostgreSQL 读已提交、MySQL 可重复读和读已提交都测 |
| 影响行数语义 | MySQL 驱动返回匹配行数、会话时区为 UTC，用测试钉住 |
| 时间 | 毫秒精度；长事务里接手 SQL 用的是当前时间而不是事务开始时间（变异：换成 `now()` 必须失败） |
| 结果不确定（提交成功但报超时、提交前断开） | 重新接手、代号加一、重新加载；客户端重试同一 `client_msg_id` 后只有一条 |
| MySQL 死锁（批中途） | 整批报错、没有部分提交、按可重试处理、后续批正常 |
| 卡死的连接（黑洞） | 写线程在 F 内自停，连接被丢弃重建 |
| 启动检查 | 每一项不满足时拒绝启动并给出原因；全部满足时启动 |
| 从库等待 | 有从库、从库停止、0 台从库、权限不足、MySQL 半同步退回异步，各自的行为 |

### 12.5 异常测试（故障注入 + 并发负载，结束时跑总校验）

| 故障 | 用例 |
|---|---|
| **负责人暂停（最重要）** | 停在"校验之前"或"校验之后、提交之前"，超过租约时长；另一节点接手并写入；放开后旧负责人的提交必须失败、不留痕迹，并发现自己已失去分片。用故障点精确暂停（Linux 和 Windows 一样） |
| 负责人暂停在回复之前 | 已提交未回复；客户端超时后换节点重发，只有一条 |
| 负责人崩溃 | 在各个故障点崩溃；接手后已确认的都在 |
| 部分分区 A：连得上数据库、连不上其他节点 | 仍是合法负责人，不出现第二个负责人；经别的节点发来的请求得到明确的可重试错误 |
| 部分分区 B：连得上其他节点、连不上数据库 | 在 F 内自停；恢复后写不进去（已被接手） |
| 单向分区 | 只丢 A→B 方向：可重试错误；队列不超过上限 |
| 黑洞和重置 | 同一场景各测一次，切换时间都在预期内 |
| 写线程卡住但节点心跳正常 | 不再续约，分片被别的节点接手 |
| 慢节点 | 对端停止读取：发送方断开连接，提交延迟不受影响 |
| 本地时钟偏移和跳变 | 不会延长自认为持有的时间，任何时刻没有两个负责人 |
| 通知丢失 | 任意一条、最后一条、全部丢失：客户端最终补齐（最后一条在位置校验周期内） |
| 失效通知丢失 + 对端重启 | 拉黑、急停在 3 秒内仍然生效 |
| 数据库连接池被关闭 | 能恢复，不会悄悄卡住 |
| 数据库主从切换（`tests/replicas.rs`，Linux） | 写入中途杀主库、提升从库；从库停止应用；主库变为只读：已确认的消息全部在新主上，没有从库的新主不回复写入成功 |
| 数据库整体宕机后恢复 | 原负责人优先续回，没有接手风暴 |
| 防线被绕过（§8.5，随 D100） | 关闭从库等待后让从库少一段再提升：检测到倒退、进入恢复模式、会话纪元更换、客户端本地记录一条不少、自己的消息补交后去重、别人的消息补回后自动合并；误接回旧主库：拒绝写入，`accept-rewind` 后恢复；从旧备份恢复：会话被归档而不是清空 |

### 12.6 边界测试

| 用例 |
|---|
| 1 个节点的集群、2 个节点、上限节点数（32）；所有分片在一个节点上 |
| 租约时长取最小值；续约正好失败一次；代号连续快速递增；同一节点失去又重新得到同一分片 |
| 接手时正好有会话解散在提交：解散之后不能再有任何事件，跨负责人也成立 |
| 同一 `client_msg_id` 同时发到三个节点；在旧负责人暂停期间重发 |
| 全部节点同时重启；一个节点反复加入离开 |
| 同一节点编号的两个进程（不同启动编号）：不会都认为自己持有 |
| 两个集群误用同一个数据库：启动失败 |
| 帧正好等于上限、超出 1 字节；队列正好满 |
| 错误码：每种拒绝经转发后和单机一致，不留痕迹 |

### 12.7 总校验（每个多节点测试结束时都跑）

1. 每条"回复成功"的消息都在数据库里（**不丢**）。
2. 每个会话序号从 1 连续、唯一（**不乱**）。
3. 每个 `client_msg_id` 最多一条；"结果未知"的可能有也可能没有，但不能有两条（**不重**）。
4. 被拒绝的不落库；终止事件（解散等）之后没有任何事件。
5. 同一分片的提交代号单调不减，且等于当时租约表里的代号（**旧负责人从未提交**）。
6. 每台设备从任意节点同步到的序列，等于数据库日志的前缀；日志重放的结果等于当前状态。
7. 急停、拉黑之后超过 3 秒，任何节点都没有放行。

每个守护竞态的测试都多轮运行，并对 §12.1 的变异开关逐一验证测试会失败。
