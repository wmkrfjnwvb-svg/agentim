# 11 集群

> 状态：**C0、C1 已实现**（2026-10-16；D72–D84、D86 按 [06 §1.1](06-plan.md) 的建议执行）；C2–C4 未开始。实现和设计不同的地方在各节里写明（"实现："）。
> 依据：[调研：集群](research/cluster.md)（Temporal、Patroni、client-go、Quartz、Airflow、db-scheduler、ShedLock、Redis Cluster、Mattermost、Synapse、Centrifuge、PostgreSQL / MySQL 切主、Jepsen 等的源码和社区问题单）。下文的"〔调研 2.x〕"指那份文档的对应小节。
> 已确认的方向（2026-10-12）：所有版本免费；**除数据库外不依赖任何组件**；节点平等，没有主从；会话分片由数据库租约决定归属，**没有选举**；节点之间全互连；做成独立的 Rust crate；测试按 §12 做全。

## 1. 目标和范围

| 解决 | 不解决 |
|---|---|
| 高可用：任意一个节点崩溃、升级、断网，服务不停，消息不丢、不乱、不重复 | 数据库自身的高可用（由客户的数据库或托管服务负责；我们负责"数据库切主时也不丢已确认的消息"，见 §8） |
| 连接扩展：长连接分散到多个节点 | 跨地域多活 |
| 推送扩展：大群的推送由各节点分担 | 单个数据库的写入上限（靠 [02 §4.8](02-architecture.md) 的优化和多库，多库属企业版） |
| 滚动升级：逐个节点升级，用户无感 | |

- 集群只支持 PostgreSQL 和 MySQL。SQLite 只用于单机，集群模式下拒绝启动。
- 单机部署不受影响：不开集群时，代码路径和现在一样，只是多了 §11 C0 里的几项改进（超时保护等，单机也需要）。

## 2. 正确性规则

所有设计都服务于这几条，测试（§12）逐条证明：

| # | 规则 | 防住什么 |
|---|---|---|
| G1 | **写库成功（且从库确认，§8）才回复成功**，然后才推送 | 任何时刻崩溃，已回复成功的消息都在 |
| G2 | **同一个会话同一时刻只有一个写入者**；序号在事务里用行锁分配（现有做法） | 顺序不乱、序号不重复 |
| G3 | **每批写入在同一事务里校验租约代号**，用会和接手互相等待的写法（§4.3） | 旧负责人卡顿后醒来写不进去 |
| G4 | **幂等落在数据库**：`client_msg_id` 唯一约束（现有） | 结果不确定时重试不会产生两条 |
| G5 | **结果不确定的写一律当作"可能已提交"**（§4.5） | 不会因为误判"失败"而重复或丢失 |
| G6 | **节点之间只传通知和转发请求，不传数据**；通知丢了只影响实时性，客户端从数据库补齐 | 节点间网络出问题不影响正确性 |
| G7 | **读取只返回已确认复制的部分**（§8.3） | 别人看到的消息不会在数据库切主后消失 |
| G8 | 第二层保护：`(会话, 序号)` 唯一约束 | 即使分片保护有缺陷，也不会写出重复序号 |

## 3. 结构

```
                   负载均衡（可选；SDK 也可以配置多个地址）
                     │ WebSocket / HTTP
  ┌──────────────┬───┴──────────┬──────────────┐
  节点 A          节点 B          节点 C          ← 同一个程序，角色完全相同
  · 连接、推送     · 连接、推送     · 连接、推送
  · 持有分片 0–85  · 持有分片 86–170 · 持有分片 171–255（每个分片一个租约）
  · 每个库一个写线程，负责本节点持有的所有分片
  └──── 节点间全互连（TLS）：转发请求、事件通知、失效通知 ────┘
                     │
            PostgreSQL / MySQL（客户自己的主从或托管服务）
            · 业务数据 · 节点表 · 分片租约表 · 失效日志 · 集群元数据
```

- **分片**：每个数据库的会话按 `hash(会话编号) mod V` 分到 V 个虚拟分片，V 在集群初始化时固定（默认 256，D80，之后不能改；Temporal 同样如此〔调研 2.1〕）。控制库（用户、令牌、Agent、API Key）是一个单独的"控制分片"，走同样的租约。
- **写线程**：每个节点每个数据库一个写线程（沿用现有的单写者 + 批量提交），负责本节点持有的全部分片。数据库连接数 = 节点数 × 数据库数，不会随分片数增长。
- **首选节点**：每个分片按会合哈希（rendezvous hashing）在当前存活节点里算出首选节点。首选只是建议；**能不能写只看数据库租约**。

## 4. 分片租约

### 4.1 表

```sql
-- 集群元数据：初始化时写入，之后只读
cluster_meta(cluster_id, shards_per_db, created_at, ...)

-- 节点表：每个节点一行
cluster_nodes(node_id PK, boot_id, addr, proto_min, proto_max, version,
              capabilities, state /* joining|active|leaving */, heartbeat_at)

-- 分片租约：初始化时为每个分片预先建好（不在抢的时候插入，避免 MySQL 间隙锁死锁〔调研 2.3〕）
shard_lease(db, shard_id, PRIMARY KEY (db, shard_id),
            owner /* node_id:boot_id，可空 */, epoch BIGINT NOT NULL,
            expires_at /* PG: timestamptz(6)；MySQL: DATETIME(6) UTC */,
            fence_count BIGINT NOT NULL, handover_to)
```

- 租约行和它保护的数据**在同一个数据库**（多库时每个库有自己的租约行），这样校验和写入能在同一个事务里完成。
- 时间一律在 SQL 里取数据库时钟：PostgreSQL `clock_timestamp()`（不能用 `now()`，那是事务开始时间），MySQL `UTC_TIMESTAMP(6)`〔调研 2.2〕。应用不把自己的时间作为参数传进去。
- 节点身份 = `node_id`（配置或首次启动生成，持久）+ `boot_id`（每次启动随机生成）。同一个 `node_id` 重启后算新的持有者〔调研 2.2 patroni#1804〕。

### 4.2 抢、续、交

| 操作 | SQL 要点 | 结果判断 |
|---|---|---|
| **接手**（租约过期或无人持有） | `UPDATE shard_lease SET owner=?, epoch=epoch+1, expires_at=<数据库时间>+租约时长 WHERE db=? AND shard_id=? AND (owner IS NULL OR expires_at < <数据库时间>)`，独立的短事务 | 影响行数必须**正好是 1**；0 表示没抢到 |
| **续约** | 一条语句续本节点持有的全部分片：`UPDATE … SET expires_at=… WHERE (db, shard_id, owner, epoch) IN (…) AND expires_at > <数据库时间>`，走专用连接 | 影响行数等于持有数才算全部续上；少了的分片立即自停 |
| **过期后自己续回** | `UPDATE … SET epoch=epoch+1, expires_at=… WHERE … AND owner=我 AND epoch=旧值` | 成功说明中间没人持有过，内存状态可以保留；失败就是被接手了 |
| **计划内交接** | 旧负责人停收、排空、提交后：`UPDATE … SET owner=目标, epoch=epoch+1, expires_at=… WHERE … AND owner=我 AND epoch=当前` | 目标节点立即可写，不用等租约到期 |
| **释放**（下线） | `UPDATE … SET owner=NULL, expires_at=<数据库时间> WHERE … AND owner=我 AND epoch=当前` | 别人立即可接手 |

- 只有首选节点在租约到期后立即抢；非首选节点再晚一个续约间隔才抢；刚因故障失去某个分片的节点，一个租约时长内不抢回这个分片〔调研 2.2 防抖〕。
- 接手有并发上限（每次 10 个分片，从随机位置开始）〔调研 2.1〕。
- 每分钟全量对账一次："我该持有哪些、实际持有哪些"〔调研 2.1〕。

### 4.3 每批写入的校验（核心）

批量事务里、**提交之前的最后一步**，在所有按命令的保存点之外（实现：放在最后而不是第一条，安全性相同——之前的写都未提交；行锁只持有到提交前的一瞬间，接手等得更短）：

```sql
UPDATE shard_lease SET fence_count = fence_count + 1
 WHERE db = ? AND (shard_id, owner, epoch) IN ((?, ?, ?), …)   -- 本批涉及的分片，按分片号升序
-- 影响行数必须等于本批涉及的分片数，否则整批回滚，这些分片立即自停
```

- 这条 `UPDATE` 拿到租约行的排他锁，一直持有到提交。接手者的 `UPDATE` 必须等它提交；等到后，PostgreSQL 会在新版本上重新判断条件，MySQL 的 `UPDATE` 读最新提交的版本〔调研 2.3〕。所以"旧负责人提交"和"新负责人接手"一定有先后，**不会出现两个代号都提交成功**。
- 让值一定改变（计数加一），影响行数不依赖 MySQL 驱动的"匹配行数"设置〔调研 2.3〕。
- 比较代号用"等于"，不用"大于等于"：数据库切主后租约表可能回到旧代号，等值比较会让节点自停后重新接手〔调研 2.2〕。
- 不在校验里加"未过期"条件：安全性来自行锁加代号，时间条件只会在边界制造假失败〔调研 2.3〕。

### 4.4 时间参数

| 参数 | 默认 | 约束和理由 |
|---|---|---|
| 租约时长 D | 15 秒（D73） | 最坏的接手时间约 D + 3 秒 |
| 续约间隔 R | 3 秒 | 一次失败还有多次重试机会 |
| 单次数据库操作超时 T | 2 秒 | 所有数据库调用都有，由 D 推导 |
| 自停时间 F | 10 秒，从**发出续约请求之前**的本地单调时间算起 | 约束 `R + 2T ≤ F < D`，`D / F ≥ 1.5`（容忍 1.5 倍的时钟速率差）；启动时检查，不满足拒绝启动〔调研 2.2〕 |
| 写连接的锁等待 | PostgreSQL `lock_timeout` 2 秒、`idle_in_transaction_session_timeout` = F；MySQL `innodb_lock_wait_timeout` 2 秒 | MySQL 默认 50 秒太长 |

到了自停时间还没续上，节点立刻停止写这个分片、停止为它推送，不等数据库通知。

### 4.5 结果不确定和错误分类

所有数据库错误在**一个函数**里分三类〔调研 2.1、2.2〕：

| 类别 | 例子 | 处理 |
|---|---|---|
| 明确没写进去 | 唯一约束冲突、校验失败、校验语句影响行数不对 | 返回业务错误码；校验失败时分片自停 |
| 失去归属 | 校验语句影响 0 行；接手、续约时发现别人持有 | 分片自停，回到待命；**不重试** |
| 结果不确定 | 超时、连接断开、提交时出错、死锁、序列化失败、未知错误 | 见下 |

结果不确定时（照 Temporal）：
1. 停止写这个分片，丢掉它的内存状态（流式状态、成员缓存等）。
2. 用"过期后自己续回"的写法把代号加一。这一步会等旧事务结束，所以之后读到的就是确定的结果。
3. 从数据库重新加载分片状态。
4. 本批所有请求返回可重试错误（D78：新增可重试错误码 `unavailable`）。客户端用同一个 `client_msg_id` 重试，已经写进去的会直接返回原来那条。
5. 本批不推送。

只有带**当前代号**的错误才会改变分片状态，旧请求的迟到错误直接返回给调用方〔调研 2.1〕。

**提交不能被取消**：写线程的提交不受客户端断开或请求超时影响；超时只用来判定"结果不确定"，不会去取消正在等从库的提交（PostgreSQL 取消后数据已经本地可见〔调研 2.5〕）。

### 4.6 卡死保护

- 写线程超过 `F − 余量` 还没完成一批，就判定卡死：自停所有分片，丢掉这条数据库连接，重建连接后重新接手〔调研 2.1 #12246〕。
- 续约由写线程的进展驱动：写线程卡住就不续约，别的节点会接手〔调研 2.3 Airflow 的教训〕。
- 连续 K 次（默认 5 次）续约失败，节点退出集群（报不健康、断开客户端），而不是只打日志〔调研 2.1 #11691〕。

## 5. 请求路由和转发

| 请求类型 | 在哪里执行 |
|---|---|
| 读（同步、历史、搜索、上下文、列表、未读） | 收到请求的节点直接读数据库（受 §8.3 的水位线限制） |
| 写某个会话 | 该会话分片的负责人 |
| 写控制库（用户、令牌、设备、Agent、API Key、拉黑） | 控制分片的负责人 |
| 跨多个分片的操作（建会话、解散、销毁 Agent 等） | 现在就是按步骤分别发给各个写线程，并有崩溃后的修复逻辑；集群下每一步发给对应分片的负责人，修复逻辑不变 |

- 现在代码里调用写线程的地方（`Hub` 中的 `shard.call(op)`），改为通过一个 `Router` 接口：分片在本节点就直接交给本地写线程，否则转发给负责人。所以要求写线程的命令（`Op`）可以序列化（§11 C0）。
- 转发请求带：请求编号、幂等编号、剩余时限、分片号、调用方认为的代号、身份、命令。负责人校验后执行；分片不归它时返回 `not_owner{负责人提示}`。
- 收到 `not_owner` 后按提示重发，**最多 2 次**，之后返回可重试错误，防止两个节点看法不一致时来回弹〔调研 2.1〕。
- 调用方缓存"分片 → 节点"，成员变化后 30 秒过期，连接出错时立即删除。
- 转发超时 = 客户端剩余时限减余量（默认 5 秒）。超时就是结果不确定：对客户端返回可重试错误，**绝不返回"失败"**，客户端用同一个 `client_msg_id` 重发〔调研 2.4〕。
- 被拒绝的请求（forbidden、not_found、conflict、bad_request、blocked、rate_limited）经过转发后错误码不变，不留痕迹。

## 6. 节点之间的通信

### 6.1 连接

- 节点从节点表发现彼此。实现：每个节点向每个其他节点发起**一条** TLS 长连接，自己的转发请求和事件通知都走自己发起的那条（每对节点两条，每条只有一个方向的请求），省掉"同时互连保留哪条"的判断。
- 集群自己的证书：第一次初始化时生成集群 CA，用主密钥加密存在数据库里；各节点启动时自动签发自己的证书并定期轮换。用户不用管证书。
- 握手（HELLO）双方都发：集群编号、节点编号、启动编号、协议版本范围、程序版本、能力列表。集群编号不同、节点编号和节点表不符、版本范围没有交集，都拒绝并告警。
- 对端的启动编号变了，说明它重启过：它之前转发中的请求全部按不确定处理，它的迟到帧全部丢弃。

### 6.2 存活和背压

| 项 | 做法 |
|---|---|
| 心跳 | 应用层 PING/PONG 每 2 秒；10 秒没**收到**任何帧就断开重连。每个方向单独判断，不能只靠 TCP 保活〔调研 2.4 redis#9688〕 |
| 重连 | 指数退避，100 毫秒起、上限 5 秒，加随机抖动 |
| 发送队列 | 每条连接上限 64 MB 或 10 万帧，超了就断开该连接并告警；**写线程只往队列里放，不等对端**，所以慢节点不会拖慢提交 |
| 单帧上限 | 8 MB，超了拒收并断开 |
| 坏帧 | 魔数错误、长度超限、截断：断开；未知消息类型、未知字段：忽略并计数〔调研 2.4〕 |

### 6.3 帧

```
帧头（字段位置固定，用测试锁住）：magic "AIMB" · 长度 · 编码版本 · 消息类型 · 标志 · 保留字段
帧体：JSON（实现：先用 JSON，字段可选、未知字段忽略；需要时再换二进制编码，帧头的编码版本字段就是为此留的）

HELLO          握手
POSITIONS      本节点持有的分片和代号；握手后先发，之后每次变化都发
FORWARD_REQ    转发的写请求
FORWARD_RESP   结果：ok | 业务错误码 | not_owner{提示} | unavailable | unsupported_op
EVENT_HINT     提交后的事件通知：会话、会话纪元、序号、上一个序号、（小的）事件内容
INVALIDATE     失效通知：失效日志编号
PING / PONG
```

- 能力协商：对端没声明某项能力，就不给它发依赖这项能力的帧或命令，改为本地处理或返回 `unsupported_op`〔调研 2.4 Redis 扩展机制〕。

### 6.4 事件通知和缺口

- 负责人提交后，按会话把事件通知发给其他节点（一开始广播给所有节点，节点多了以后只发给有相关连接的节点）。**同一会话的通知按序号顺序发出**〔调研 2.4 Centrifuge〕。
- 收到通知的节点推给本机的相关连接。客户端现有的同步协议已经能处理：序号跳号就同步，旧序号丢弃。
- **尾部丢失**（最后一条通知丢了、之后没有新消息）：客户端协议加"位置校验"，每 30 秒（或随心跳）和服务端比对相关会话的最新序号，不一致就同步〔调研 2.4〕。
- 和某个节点的连接断开又重连：本节点上订阅了那个节点所负责会话的客户端，都收到"请同步"提示。
- 客户端游标带会话纪元；游标大于服务端最大序号（数据库从备份恢复等情况），返回明确的错误让客户端重建，不能返回空结果〔调研 2.4〕。

### 6.5 缓存失效（安全相关）

拉黑、吊销令牌、停用账号、急停和销毁 Agent，这些改动必须在所有节点生效：

1. 写改动的同一个事务里，向数据库的**失效日志**表追加一行（递增编号、类型、对象）。
2. 提交后用 INVALIDATE 通知所有节点；节点按编号顺序处理，发现编号跳了就从数据库补拉〔调研 2.4 Synapse〕。
3. 每个节点每 2 秒查一次失效日志的最新编号，作为通知丢失时的兜底。
4. 和某个节点断连、或对端重启时，本节点清空安全相关的缓存，从数据库重新加载。
5. 写入路径上，负责人在事务里再检查一次（急停、销毁、拉黑），所以写入不会因为缓存滞后而放行。实现：拉黑在提交后作为通知发给所有节点（不等轮询）；会话和拉黑记录在同一个库时（单库部署），负责人在事务里直接查拉黑表；多库时会话库的负责人用通知更新的缓存（毫秒级滞后，记在 [06 §1.1](06-plan.md) D98）。

**保证**：改动提交后，最迟 3 秒内所有节点生效（推送、读取路径）；写入路径立即生效。测试证明（§12.4）。

## 7. 节点的生命周期

| 阶段 | 做法 |
|---|---|
| 启动 | 启动检查（§9）→ 写节点表（`joining`）→ 和其他节点建连 → 接手首选分片 → 全部接手完、再稳定 5 秒才报就绪（`active`）〔调研 2.1〕 |
| 运行 | 心跳 2 秒；节点表超过 10 秒没更新视为离线（只影响路由和首选节点计算，不删数据） |
| 加入新节点 | 新节点成为部分分片的首选；现负责人对这些分片做**计划内交接**（§4.2），一次只交接一小批 |
| 优雅下线（升级、缩容） | 节点表改为 `leaving` → 不再接受新连接 → 对每个分片：停收、排空、提交、交给首选节点 → 让客户端重连到别的节点 → 继续对迟到的转发请求回 `not_owner` 一小段时间 → **最后**停心跳和退出〔调研 2.1、2.3〕 |
| 崩溃 | 别的节点在租约到期后接手（约 15–18 秒）；客户端重连到别的节点并同步 |
| 退役 | 节点表留墓碑，防止被重新加入〔调研 2.4〕 |

**滚动升级**：支持新旧两个相邻版本同时运行。协议靠能力协商兼容；数据库表结构变更按"先加后删"两步走（新版本加列且旧版本能忽略，再下一个版本才删旧列）。

## 8. 数据库主从和"不丢已确认的消息"

### 8.1 三种模式（启动时自动识别）

| 模式 | 识别 | 提交后怎样才算已复制 |
|---|---|---|
| 无从库 | 单个数据库，看不到从库 | 提交即算（切主不存在） |
| 数据库端同步 | PostgreSQL 配了 `synchronous_standby_names` 且 `synchronous_commit` 至少为 `on`；MySQL 半同步、等待点 `AFTER_SYNC` | 提交返回即算；每批前后检查没有退回异步（MySQL `Rpl_semi_sync_source_status`）〔调研 2.5〕 |
| **应用等待**（异步从库，默认配置） | 看得到从库但没有同步配置 | 我们自己等：PostgreSQL 提交后在同一连接取 `pg_current_wal_insert_lsn()`，后台任务轮询 `pg_stat_replication` 等从库的落盘位置超过它；MySQL 需要 GTID，取 `@@GLOBAL.gtid_executed`，直连各从库检查已收到的 GTID 集合 |
| 托管同步（声明，D77） | 看不到从库，但管理员在配置里声明 `durability = "managed_sync"`（RDS Multi-AZ、Cloud SQL 高可用、Azure） | 提交即算；声明写审计并在 `/readyz` 显示 |

### 8.2 应用等待的规则

- 等哪些从库：默认**所有正在复制的从库**（最安全，因为不知道切主工具会提升哪一台）；可配置为 N 台（D74）。
- **0 台从库算"不满足"，不算"不用等"**。异步复制下，被隔离的旧主看不到从库，这一条会让它无法回复成功。
- 等不到（默认 5 秒）：本批返回可重试错误、不推送；**绝不悄悄降级**。这批数据已经在主库提交，标记为"已提交未确认"，后面的批排在它后面，等它确认后一起回复。
- 一个后台任务合并轮询，所有等待中的批次共用同一次查询。

### 8.3 读取水位线

应用等待模式下，提交一返回别人就能读到，但从库可能还没有〔调研 2.5〕。所以：
- 每个会话记录"已确认复制的序号"。负责人在确认复制后推进它（无从库、数据库端同步、托管同步三种模式下，和数据在同一个事务里推进，没有额外开销）。
- 同步、历史、搜索、上下文这些**读会话记录的路径**，只返回不超过这个序号的部分。
- 成员列表、未读数这些读状态的路径，切主瞬间可能短暂显示未确认的状态；切主后客户端按同步协议的原因码修正（D75）。

### 8.4 数据库切主的检测和处理

- 记住"主库身份"：PostgreSQL 取 `(system_identifier, 时间线)`，时间线从 `pg_walfile_name(pg_current_wal_insert_lsn())` 取；MySQL 取 `server_uuid`，并检查 `read_only`、`super_read_only` 都为 0〔调研 2.5〕。
- 每次取连接、每批提交后、每次轮询复制状态时比对；身份变了，或者遇到只读类错误（PostgreSQL 25006、57P01；MySQL 1290、1836、1792），或者 `pg_is_in_recovery()` 为真：
  1. 所有分片自停，未确认的批次全部按"结果不确定"返回；
  2. 关闭整个连接池（被提升的从库上的老连接会从只读变成可写，不能继续用）；
  3. 按配置的地址逐个连接，找到新主；
  4. 重新接手（代号加一），从新主重新加载状态。
- sqlx 不支持多个主机地址和 TCP 保活〔调研 2.5〕，所以找主库、超时都由我们自己做；连接取出时检查是不是主库。

### 8.5 防线被绕过时：检测、恢复、告知

§8.1–§8.4 保证正常情况下已确认的消息不丢。但防线可能被绕过：管理员关闭了从库等待、托管同步声明错了、有人手动切了库、数据库从备份恢复、误把旧主库接回来。这时**服务必须能起来，并且不能带着错乱的数据悄悄运行**。

**会是什么样**：PostgreSQL 物理复制和 MySQL（GTID + 按提交顺序回放）都按事务顺序复制，被提升的从库是旧主库某一时刻的完整快照，**数据不会只有半个事务，只是少了最后一段**。表现为：最后几条消息不见了；同一个序号对应了两条不同的消息（新消息从较小的序号继续分配）；客户端的同步位置比服务端还大；成员、拉黑、设置回退；去重记录丢失。

**检测**

| 信号 | 说明 |
|---|---|
| 主库身份变了 | PostgreSQL 时间线、MySQL `server_uuid`（§8.4） |
| 数据倒退 | 每个节点在本地一个小文件里记住上次见到的主库身份、各分片的最大代号和已确认位置；启动时数据库里的比记住的还旧，说明少了一段，或者连到了更旧的库 |
| 客户端位置超前 | 客户端报上来的同步位置大于服务端最大序号（客户端是最好的证人） |
| 一致性检查 | `agentim db check`：会话序号连续、目录和会话对得上、设备位置不超过会话最大序号、引用的消息存在、多库之间的目录一致 |

**恢复**

1. 默认自动进入**恢复模式**启动：跑一致性检查，能安全修的自动修（把超前的设备位置调回、修复目录，现有代码已会修目录）；`/readyz` 和指标显示恢复模式。
2. 发现**接到了比上次更旧的库**（时间线或代号更小）时拒绝写入，提示"可能接错了库"；管理员确认要用这个库，执行 `agentim cluster accept-rewind`（写审计），再按恢复模式启动。
3. 倒退的会话**更换会话纪元**，并告诉客户端**分叉点**（新主库上这个会话的最大序号）。
4. 客户端**按消息编号对账，不删除本地记录**：

   | 本地消息 | 处理 |
   |---|---|
   | 分叉点之前 | 原样保留 |
   | 分叉点之后、服务端有同一个消息编号 | 保留，按服务端的新序号调整位置 |
   | 分叉点之后、自己发的、服务端没有 | 用原来的 `client_msg_id` **补交**，服务端去重；补回的消息标为"恢复的消息" |
   | 分叉点之后、别人发的、服务端没有 | **保留**，标记"服务器上已缺失"；发送者补交回来后按消息编号自动合并 |
   | 撤回、编辑操作丢失 | 消息重新出现时，撤回或编辑的人看到"操作未生效"，可以重做 |

   只有纪元变了的会话才对账；其他会话、草稿、设置、文件缓存都不动。端到端加密会话的本地记录照样能解密。
5. **彻底重建的会话**（分叉点为 0 或对不上，例如数据库从很久以前的备份恢复）：**不清空本地记录**。
   - 客户端先把这个会话的本地记录**归档**：移到应用里一个只读的"旧记录"区，照常可以查看和搜索，和新记录分开显示。
   - 弹出提示，说明发生了什么、旧记录保存在哪里，并提供**导出到本机文件**（加密的归档文件，以及可直接阅读的 HTML / JSON）。
   - 用户确认前，不在这个会话里覆盖任何本地内容。
   - Agent 客户端没有界面：自动导出归档文件，并在日志里写明路径。
   - 归档受本机的保留策略和用户的删除请求约束（GDPR）：用户删除账号或会话时一并删除。

**告知**

- 管理员：审计记录切主时间、倒退的会话及各自少了多少条、补交找回了多少；恢复模式在 `/readyz` 和告警里可见。
- 用户：受影响的会话里出现一条系统事件（"服务器恢复了数据，这段时间的部分消息可能缺失"）。

客户端的对账、补交、归档、导出放在客户端 Rust 核心 SDK 里（[05 §6](05-operations.md)），所有语言共用。

## 9. 启动检查（集群模式）

不满足就拒绝启动，并给出原因和修复命令（不悄悄降级）：

| 检查 | PostgreSQL | MySQL |
|---|---|---|
| 版本 | ≥ 14（D76） | ≥ 8.0，开启 GTID |
| 连的是主库 | `pg_is_in_recovery() = false` | `read_only = 0`、`super_read_only = 0` |
| 持久性配置 | `fsync = on`、`full_page_writes = on`；会话设 `synchronous_commit` 不低于 `local` | `innodb_flush_log_at_trx_commit = 1`、`sync_binlog = 1`、`binlog_format = ROW` |

| 从库模式 | 识别 §8.1 的模式；应用等待模式下至少能看到 1 台从库，或已声明托管同步 | 同左 |
| 集群 | 集群编号一致；分片数和元数据一致；时间参数满足 §4.4 的约束；节点编号没有被另一个活着的进程使用 | 同左 |

## 10. 单进程假设的清单和改法

现在代码里只在一个进程内成立的东西，集群时逐项处理（新功能不再增加新的单进程假设，这张表随代码维护）：

| 现状 | 集群下 |
|---|---|
| 在线连接表（`Registry`） | 只管本机连接；跨节点推送走 §6.4 |
| 内存缓存：用户、令牌、拉黑、停用、急停、销毁、目录、API Key（`Shared`） | 失效日志 + 通知 + 兜底轮询（§6.5）。实现：会话目录的每次改动发给所有节点；本节点没有的条目在请求和转发进来时从库里读（`Hub::dir_ensure`）；控制分片接手后的修复先从库里重新读整个目录，且不删除正在迁移的会话的副本 |
| 进程内的全局锁（单聊唯一的 `dm_lock` 等） | 改为数据库唯一约束，或交给负责人在事务里判断 |
| 限流计数（MCP、同步、进度、建会话、未知令牌查库） | 按节点计算；文档写明集群下的实际上限是"每节点上限 × 节点数" |
| 写线程里的会话状态（流式回复、防循环预算、成员缓存） | 跟着分片走；接手时重新加载，进行中的流式回复按"中断"结束 |
| 定时任务（看门狗、过期处理、保留期清理） | 跑在写线程里，只处理本节点持有的分片；控制库的任务跟着控制分片走 |
| Webhook 投递循环（每个库一个） | 只由该库控制分片的负责人运行 |
| 多设备通知（其他设备已读、新设备登录） | 走 §6.4 的通知 |

| 自停截止时间 | 从发出续约前算起；时钟前跳、后跳、速率偏差 1.5 倍内、外；边界值（正好等于截止时间） |
| 时间参数校验 | `R + 2T ≤ F < D`、`D / F ≥ 1.5`：相等、差 1、为 0、为负、超大值 |
| 错误分类 | PostgreSQL 和 MySQL 的每个错误码、连接断开、超时、未知错误各分到哪一类；只有"影响 0 行"立即失去归属 |
| 会合哈希 | 分布均匀；节点增减时只移动最少的分片；同样输入同样输出；1 个节点、节点编号相同前缀等边界 |
| 防抖 | 非首选节点的延迟、刚失去的分片冷却期 |
| 帧编码 | 每种帧往返编解码；截断、超长、魔数错误、未知类型、未知字段、缺失可选字段的默认值；帧头字段位置固定 |
| 能力协商 | 版本范围交集为空、单点、包含；对端缺能力时不发对应帧 |
| 转发 | 重发上限、归属缓存的过期和删除、剩余时限的计算 |
| 水位线 | 推进只增不减；乱序确认时按顺序推进 |
| 失效日志处理 | 编号连续、跳号补拉、重复丢弃 |

### 12.5 异常测试（故障注入 + 并发负载，结束时跑总校验）

| 故障 | 用例 |
|---|---|
| **负责人暂停（最重要）** | 停在"校验之后、提交之前"，超过租约时长；另一节点接手并写入；放开后旧负责人的提交必须失败、不留痕迹，并发现自己已失去分片。用故障点精确暂停（Linux 和 Windows 一样）；Linux 再用 SIGSTOP、Windows 用 NtSuspendProcess 做黑盒补充 |
| 负责人暂停在回复之前 | 已提交未回复；客户端超时后换节点重发，只有一条 |
| 负责人崩溃 | 在每个故障点崩溃（接手后、校验后、提交前、提交后、回复前、通知前）；接手后已确认的都在 |
| 部分分区 A：连得上数据库、连不上其他节点 | 仍是合法负责人，不出现第二个负责人；经别的节点发来的请求得到明确的可重试错误 |
| 部分分区 B：连得上其他节点、连不上数据库 | 在 F 内自停；恢复后写不进去（已被接手） |
| 单向分区 | 只丢 A→B 方向：A 在超时内断开该方向；队列不超过上限 |
| 黑洞和重置 | 同一场景各测一次，切换时间都在预期内 |
| 写线程死锁但节点心跳正常 | 分片被别的节点接手（CockroachDB 的"死锁"场景） |
| 慢节点 | 对端停止读取：发送方断开连接，提交延迟不受影响 |
| 本地时钟偏移和跳变 | 不会延长自认为持有的时间 |
| 通知丢失 | 任意一条、最后一条、全部丢失：客户端最终补齐（最后一条在位置校验周期内） |
| 失效通知丢失 + 对端重启 | 拉黑、急停在 3 秒内仍然生效 |
| 数据库连接池被关闭 | 能恢复，不会悄悄卡住（Temporal #11691） |
| 数据库主从切换（C3，Linux 上用 docker 搭 PostgreSQL 和 MySQL 主从） | 写入中途杀主库、提升从库；主库在"提交后、回复前"被杀；半同步退回异步后再切；旧主被隔离但还活着：已确认的消息全部在新主上，旧主上的写入无法回复成功 |
| 数据库整体宕机后恢复 | 原负责人优先续回，没有接手风暴 |
| 防线被绕过（§8.5） | 关闭从库等待后让从库少一段再提升：检测到倒退、进入恢复模式、会话纪元更换、客户端本地记录一条不少、自己的消息补交后去重、别人的消息补回后自动合并、撤回丢失有提示、其他会话不受影响；误接回旧主库：拒绝写入，`accept-rewind` 后恢复；从旧备份恢复：会话被归档而不是清空，导出文件可读；多库之间进度不一致：一致性检查发现并修复目录 |

### 12.6 边界测试

| 用例 |
|---|
| 1 个节点的集群、2 个节点、上限节点数（32）；所有分片在一个节点上 |
| 租约时长取最小值；续约正好失败一次；代号连续快速递增；同一节点失去又重新得到同一分片 |
| 接手时正好有会话解散在提交：解散之后不能再有任何事件，跨负责人也成立 |
| 同一 `client_msg_id` 同时发到三个节点；在旧负责人暂停期间重发 |
| 全部节点同时重启；一个节点反复加入离开 |
| 同一节点编号的两个进程（不同启动编号）：不会都认为自己持有 |
| 两个集群误用同一个数据库：启动失败 |
| 帧正好等于上限、超出 1 字节；队列正好满 |
| 错误码：每种拒绝经转发后和单机一致，不留痕迹 |

### 12.7 总校验（每个多节点测试结束时都跑）

1. 每条"回复成功"的消息都在数据库里（**不丢**）。
2. 每个会话序号从 1 连续、唯一（**不乱**）。
3. 每个 `client_msg_id` 最多一条；"结果未知"的可能有也可能没有，但不能有两条（**不重**）。
4. 终止事件（解散等）之后没有任何事件。
5. 每条消息记录写入时的代号；同一分片的提交代号单调不减，且等于当时租约表里的代号（**旧负责人从未提交**）。
6. 每台设备从任意节点同步到的序列，等于数据库日志的前缀；日志重放的结果等于当前状态。
7. 急停、拉黑之后超过 3 秒，任何节点都没有放行。

每个守护竞态的测试都多轮运行，并对 §12.1 的变异开关逐一验证测试会失败。
