# 05 运维、测试与客户端

> 一个程序 `agentim`（单机到集群，集群见 [11](11-cluster.md)）。§1–§5、§7 已实现（标 ⏳ 的除外）；§6 是客户端 SDK 必须做到的行为，计划见 [12 §2](12-developer-experience.md)；§8 见 [12 §4](12-developer-experience.md)。

## 1. 部署

- **服务端只运行在 Linux 上**（x86_64、aarch64），以单个二进制发布。Windows 上的服务端只用于开发和测试，测试套件在 Windows 上同样通过（§5）。
- 配置：命令行参数 + 配置文件（`--config agentim.toml`，示例见 `server/agentim.example.toml`）。只用一个 SQLite 文件时，用 `--db` 即可。
- 存储故障时进程主动退出（退出码 70），由 systemd（`Restart=always`）拉起后从日志恢复，见 [02 §4.4](02-architecture.md)。调试时可以用 `--no-exit-on-storage-failure` 关闭这个行为。
- ⏳ systemd unit 文件、Docker 镜像、发布流水线。

## 2. 日志规范

| 规则 | 说明 |
|---|---|
| 格式 | `--log-format json` 输出 JSON 行（生产环境），默认是易读格式。写到 stderr（命令的结果写到 stdout，脚本可以直接解析），由 journald 或 Docker 收集。级别用 `RUST_LOG` 控制，默认 `info` |
| 字段 | 请求日志带 `conn_id`、`user_id`、`op`、`rid`、`result`、`latency_ms`；出错时带 `error.code`、`error` |
| 级别 | ERROR：需要人处理（存储故障、启动失败）；WARN：存储类请求错误、一致性修复、迁移问题；INFO：启动、写线程启动、迁移完成；DEBUG：逐请求日志、连接建立 |
| 隐私 | **日志里不记录消息内容、令牌、耳语正文**，只记录 ID 和错误码 |
| 审计与日志分离 | 审计记录（谁对什么做了什么）存在数据库里，A5 的管理 API 和控制台里查看。⏳ 导出为 JSONL 或发送到 SIEM |
| ⏳ | 按天滚动的日志文件；OpenTelemetry trace |

## 4. 健康检查、告警、面板

- `/healthz`：进程存活。
- `/readyz`：每个数据库都可写（没有处于存储故障状态），写入队列没有超过容量的 90%。返回每个库的状态；不就绪时返回 503。
- ⏳ 开发者控制台（§8）展示健康状态；随仓库提供 Prometheus 告警规则（提交耗时 p99 > 50ms、写入队列持续饱和、推送丢弃率过高、熔断突增、待审批草稿超过 SLA、存储错误）和 Grafana 面板 JSON。

## 5. 测试

**测试规则**（每个业务功能都必须做到，见仓库根目录的 `CLAUDE.md`）：
- 覆盖这个功能影响到的每个逻辑节点，不只是功能自己的操作；
- 覆盖边界：上限、空值、未知 ID、重复调用、对自己操作；
- 错误码符合业务含义且前后一致：`forbidden`（不允许或不是成员）、`not_found`（不存在或已删除）、`conflict`（当前状态不允许）、`bad_request`（输入无效或不适用）、`blocked`、`rate_limited`；被拒绝的请求不能在日志里留下任何痕迹；
- 和所有可能冲突的操作做并发竞争，多轮重复后检查不变量；守护竞争的测试要做"故意改坏能否抓到"的验证。

PostgreSQL 的测试库用 ICU `en-US` 排序规则建（大多数安装是按语言排序，不是按字节），这样依赖字节顺序的代码会被测出来；ICU 不可用时退回服务器默认。

所有测试都在 GitHub Actions 中运行：每次推送跑 `.github/workflows/server.yml`；规模测试在 `.github/workflows/scale.yml`，每晚跑一次，也可以手动触发（§5.4）。

| 并发竞争 | 建 450 人的大群时 12 个成员一看到会话就退出或发言（5 轮）：批次连续、退出和发言都在批次之后、日志重放等于成员列表；发送和移除（移除之后不会有被移除者的消息）；多端同时建单聊（只有一个）；移除和退出同时发生（只成功一次）；同时转让给不同的人（只有一个群主）；发送和解散；加人、移人、改角色同时发生（日志重放等于状态）；解散和加人、移人、改角色同时发生（解散总会成功，之后谁都看不到） |

故意改坏验证：去掉"移除后刷新成员缓存"这一行，有 4 个测试失败（包括发送与移除的竞争测试）。建大群：每批 1 人（`chunks(1)`）让两个建大群测试失败，去掉批内排序让顺序检查失败；客户端核心去掉 `members.joined` 分支让成员列表测试失败。

场景测试发现并已修复的问题：

1. **撤回后原文仍在历史里**。日志的每个事件都带着消息快照，撤回只改了最新状态，从头拉取还能看到原文和编辑过的版本。现在撤回会清空这条消息在所有事件里的内容。
2. **任何拥有 Agent 的人都能往任意会话写事件**（`reset_guard` 没检查 Agent 是否在会话里）。现在必须是成员。
3. 重复撤回会再加一个事件；现在返回冲突。
4. 已读游标可以设到末尾之后，导致之后的新消息都不算未读；现在收回到末尾。
5. 单聊可以没有对方或有多个对方；成员列表里有重复或包含自己时整个创建失败。
6. 流式消息存下来的内容可能超过大小上限；现在超限的那一块不保留。
7. 中途打开会话的人会看到一段文字出现两次。
8. `@bob` 会把 `@bobby` 也算成提到 bob；现在取最长匹配。
9. 文本里的 NUL 字节在 PostgreSQL 上导致存储错误；现在直接拒绝。

**本次排查发现并修复的问题**：

1. **任何登录用户都能看全站统计**（审计日志、在线用户、计数），WebSocket 的 `stats` 和 `/api/stats` 都是。现在只在演示模式下开放，正式环境由之后的管理 API 提供。
2. **接管期间所有者可以批准 Agent 的草稿**，于是会在"已被人接管"时冒出一条 Agent 消息，和接管的含义矛盾。现在返回 `conflict`，要先释放。并发测试证明这个竞争原来确实存在。
3. **没有熔断时也能"重置护栏"**，每次都往日志里写一条无意义的事件。现在返回 `conflict`。
4. **SQLite 上，别的连接正在写时，服务端的写入会直接失败**（`database is locked`），而不是等待。原因是批量事务先读后写，读完以后别的连接提交了，升级为写锁时 SQLite 直接报错、不等待。重启时旧进程还没完全退出就会遇到（CI 上偶发了一次）。现在 SQLite 的批量事务和启动建表都在开始时就拿写锁（`BEGIN IMMEDIATE`），遇到锁会按忙等待超时排队。新增的测试能稳定复现原来的问题；改动后单库写入吞吐不变（约 1,150 条/秒）。

**故意改坏验证**：分别撤掉上面前三处修复；第 4 项的测试在修复前稳定失败，对应的测试都会失败（第 2 项有两个测试失败，包括并发测试）。

**暂时无法自动测试的项**：MySQL 的持久性设置（`innodb_flush_log_at_trx_commit`、`sync_binlog`）只能全局修改，会影响同时运行的其他测试，所以只测了 PostgreSQL；MySQL 这部分靠代码审查和启动日志。

- 2026-10-24 补：compose 三节点任务停掉一个节点后，Caddy 要等下一次健康检查（2 秒）才不再把请求发给它，期间 `/readyz` 可能拿到 502。Caddyfile 加了 `lb_try_duration 5s` 和 `fail_duration 10s`：连不上的节点立刻跳过、请求换一个节点（[Caddy reverse_proxy 文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)），滚动重启时真实客户端也不会看到 502。
- 2026-10-25 补（B12）：各封装收到带 `reset` 的 messages 事件时先把视图清空发布一次、再应用变化发布一次，界面会闪一下空列表。现在浏览器（React Native 用同一个视图）、C#、Kotlin、Swift、Dart 都在一次更新里清空并应用；每个封装各有一条检查（浏览器 `test/messages.test.mjs`，其他在各自的一致性场景开头），浏览器、C#、Kotlin 做过变异检查（改回两次发布时失败，Kotlin 能看到中间那个空列表）。
- 2026-10-24 补：客户端核心里，发送的答复先于消息的推送到达时，消息从视图里消失，推送到了才回来（Kotlin 的 W2 偶尔失败就是它，所有封装都受影响）。现在答复到了仍显示本地这份（状态 sent、带服务端 ID），推送到了在一个事件里换成存下的那条；`a_send_answered_before_its_message_arrives_stays_shown` 修复前失败，Kotlin 一致性场景修复前 85 次失败 6 次、修复后 60 次全过。
- 2026-10-24 补：集群里一个节点被排空后写下 `left`，其他节点看到就立刻断开到它的连接，把还在等答复的转发一起丢了，这些请求被答成"结果未知"（`an_operator_drains_a_node_under_traffic` 偶尔失败，本地 165 次失败 2 次）。现在它立刻从路由里拿掉（不再往那儿发），连接等到在途的答复回来（最多 `FORWARD_WAIT`）再关。
- 2026-10-24 补：令牌缓存刷新（M10）只按读到的快照删令牌，快照之后才登记的设备令牌会被误删，这台设备随后连接被拒、已连上的被断开（B10 的一个原因）。现在快照里没有的令牌再到库里查一次，确实没了才删；`race_new_devices_and_auth_refresh` 三种数据库都测，修复前每次失败。
- 2026-10-24 补：一个新集群的几个节点同时对着空库启动（`docker compose up`）时，都去建系统用户，后建的报 `name taken` 退出。现在冲突说明别的节点已建好，照常启动；`race_servers_starting_together_on_an_empty_database` 四个服务同时打开三个新库（三种数据库都测），修复前 SQLite 和 PostgreSQL 都会失败。同一测试在 CI 上又暴露两处启动竞争，已修：主密钥指纹和 webhook 游标是"先查后插"，同时启动时后插的撞主键（`UNIQUE meta.k`），现在插入失败就读回别人写的值（指纹不同仍拒绝启动）；SQLite 新文件切到 WAL 要独占锁，几个进程同时打开时 SQLite 不等 `busy_timeout` 直接报 `database is locked`，现在这条 PRAGMA 在 5 秒内重试（本地 40 轮失败 3 次，修复后 60 轮全过）。

### 5.4 规模测试

压测程序和服务端在同一台 runner 上（4 核），所以这里的数字用来发现退化，不代表容量上限。万级消息/秒和百万连接要用独立的压测机器验证（多节点压测见 [11 §12.8](11-cluster.md)）。

| 场景 | Linux 规模 | Windows 规模 | 校验什么 |
|---|---|---|---|
| `connections --storm` 海量长连接 + 重连风暴 | 2 万连接（4 个本地源地址），每组 100 人，1% 的人在发，200 条/秒；中途全部连接同时断开再重连 | 5000 连接，100 条/秒 | 每个连接的服务端内存；重连风暴期间发送不失败；重连的客户端靠拉取补齐，数据不丢 |
| `biggroup` 大群 | 2000 人一个群，50 条/秒 | 1000 人 | 端到端投递延迟（发送时间戳到每个接收端） |
| `slow` 慢消费者 | 500 人一个群，10% 的人停止读取，300 条/秒，每条 2KB | 200 人 | 慢的人收到 resync 并能拉取补齐；其他人一条不缺、延迟不受影响 |

每个场景都检查：每个接收端最终拿到所在会话的全部事件（推送收到，或在 resync 通知、重连之后拉取补齐）；同一连接上的推送按 seq 顺序到达。**客户端没被通知就缺事件**、拉取也补不齐、推送乱序，都会让测试失败。性能门槛只在 Linux 上设了宽松的 p99 ≤ 2 秒，用来发现严重退化。

GitHub Actions 结果（标准 runner，release，SQLite，每个场景发送 120 秒）：

| 场景 | Linux | Windows |
|---|---|---|
| 海量长连接 + 重连风暴 | 2 万连接 2.5 秒建好，每个连接约 13KB 服务端内存；2 万连接同时断开，2.3 秒内全部重连，期间发送零失败；端到端 p50 3ms、p99 7ms；240 万次投递无丢失、无乱序 | 5000 连接，重连 1.6 秒；p99 37ms；无丢失、无乱序 |
| 2000 人大群，50 条/秒（每秒 10 万次推送） | 1204 万次投递全部按序到达；端到端 p50 14ms、p99 43ms；服务端内存 54MB | 通过 |
| 慢消费者（500 人，50 人不读，300 条/秒、每条 2KB） | 50 个慢客户端全部收到 resync 并拉取补齐；其余 450 人一条不缺，p99 30ms；服务端内存 34MB，丢弃的 169 万次推送没有占用内存 | 通过 |

规模测试发现并已修复的问题：

1. **慢消费者可能不知道自己漏了消息**。推送队列满时欠下的 resync 通知，原来要等下一次推送才会发出；如果之后没有新消息，客户端永远不知道有缺口。现在队列一排空就补发。
2. **每个空闲连接占约 140KB 内存**（WebSocket 库默认 128KB 读缓冲 + 128KB 写缓冲），2 万连接就是 2.7GB。改小缓冲后约 14KB，降到原来的十分之一。
3. **大群的推送接收列表按事件重复构建**。建一个 2000 人的群会产生 2000 个成员事件，每个事件都复制一份 2000 人的接收列表，服务端内存涨到 600MB 以上。现在接收列表按成员列表缓存、各事件共享，只有群里有 Agent 时才按事件复制。同一场景下 2000 连接加 2000 人群的服务端内存从 619MB 降到 46MB。

本地跑 PostgreSQL 和 MySQL 的测试：设置 `AGENTIM_TEST_PG=postgres://user@host` 和 `AGENTIM_TEST_MYSQL=mysql://user:pass@host`（URL 里不带库名），每个测试会自动新建一个库。

**客户端核心没覆盖的行**（2026-10-24，`cargo llvm-cov`，37 行，行覆盖 98.4%）：
- 防御：内部函数收到不认识的会话时直接返回（`history.rs` 29、43、256，`view.rs` 38、79、178、182，`sync.rs` 14、123、150、321、347，`queue.rs` 553、655），调用方已经先确认过会话存在、操作还在；服务端数据缺 `conv_id`（`sync.rs` 37、304）；关闭后排的重试（`conn.rs` 182）；已移除的请求超时（`conn.rs` 564）；发送永远没拿到 ID 时排在它后面的修改（`queue.rs` 453–461、478）：发送被拒时后面的修改已经带着同一个错误码失败，拿到 ID 时已经改指向 ID，所以走不到。
- 没测的边角（行为简单，暂不补测试）：离线后才到的连接失败直接挂起（`conn.rs` 185–186）；往回翻到头时找不到对应的段（`history.rs` 147）；跳转时锚点之后没有消息（`history.rs` 233）；会话还没建立基准时同步回来的确认位置（`sync.rs` 94）；账号被删时缓存里没有这个人的消息（`sync.rs` 237）；在线请求不带 `args`（`view.rs` 239）。

## 6. 客户端 SDK

计划、包、平台和发布见 [12 §2](12-developer-experience.md)（所有平台共用一个 Rust 核心，浏览器用 wasm，D104；实现情况见 12 §2.14）；同步协议和异常场景见 [08](08-sync-and-client.md)。本节只写**每个客户端 SDK（任何语言）都必须做到的行为**，SDK 的协议一致性测试逐条检查。

### 6.1 顺序和投递

- 同一会话的事件按 seq 顺序交付，每个（会话，seq，版本）**恰好一次**；SDK 缓存乱序到达的推送、自动补缺口，收到 `resync` 时按原因码重置，每 30 秒用 `heads` 校验位置（补上最后一条丢失的推送）。不同会话之间不保证顺序。
- 只靠 `sync` + `ack` 同步，存好后才确认（[08](08-sync-and-client.md)）。

### 6.2 发送和本地数据

- **乐观发送**：`send` 立即返回一条 `pending` 的本地消息，之后变为 `sent(seq)` 或 `failed`。每条带 `client_msg_id`；`unavailable`、`overloaded`、断线时用**同一个** id 一直重试（服务端去重），频率按退避；只有业务拒绝才标为失败（D113）；重发、取消按 `client_msg_id`，幂等。
- **本地存储按业内做法**：设备上用 SQLite（Stream 的 React Native SDK、matrix-rust-sdk、Telegram、WhatsApp、微信都是），浏览器用 IndexedDB（Sendbird、matrix-js-sdk）。TypeScript SDK：浏览器 `IndexedDBStore`；React Native、Electron、Node 用 `SqliteStore`，通过一个很小的驱动接口接 expo-sqlite、op-sqlite、better-sqlite3 或 `node:sqlite`；测试和一次性程序用 `MemoryStore`。按消息写入（一批一个事务），不整段重写会话。以后的 Rust 核心同样用 SQLite。
- 本地缓存只是缓存：损坏或迁移失败时删除重建、从服务端重新同步；待发送队列和草稿单独保存、不被淘汰。要求的存储打不开时报错，不悄悄退回内存。`logout()` 默认清除本地数据（GDPR）。

### 6.3 错误

`{code, message, retryable, retry_after, request_id}`。`code` 和服务端完全一致：`forbidden`、`not_found`、`conflict`、`bad_request`、`blocked`、`rate_limited`、`unavailable`、`overloaded`、`taken_over`、`unknown_op`、`unsupported_protocol`、`client_too_old`、`logged_out`、`storage`；另加客户端自己的 `unauthenticated`、`network`、`timeout`、`cancelled`、`expired`、`unsupported_version`、`storage_locked`。TypeScript 里是字符串联合类型。

### 6.4 兼容、事件和 hook

- **未知分支**：事件和枚举都留"未知"分支，不认识的事件逐条跳过，未知消息类型显示 `fallback`，老客户端连新服务端不会崩溃；连接时协商协议版本（[02 §2.5](02-architecture.md)）。语义化版本，弃用至少保留一个小版本。
- **事件**：带类型，订阅返回取消函数。类别：连接（状态、令牌将过期、本设备被下线、需要升级）、同步、会话和成员、消息（含发送状态、已读、信号）、流式（开始、带偏移的增量、结束原因）、介入（草稿、耳语、接管、熔断）。React 的 hooks 见 [12 §3](12-developer-experience.md)。
- **hook**：取令牌（必须；首次连接、将过期、被拒时调用）、发送前（链式，可修改或拒绝）、显示转换（不改本地存储）、发送结果、限流通知、传输和日志。客户端 hook 能被绕过，**业务规则和合规检查只放在服务端**。

### 6.5 Agent SDK

Agent 用 `sdk/agent-node`、`sdk/agent-python`（和客户端 SDK 共用协议）。除 §6.1–§6.4 外还有：流式回复（按偏移续上）、读上下文（每条带发送者类型和信任标记）、进度和状态信号、卡片、来源、请人决定、检查点、转人工；处理器抛错时同一条消息重新交给它，被服务端按业务规则拒绝的不重给。测试见 §5 "Agent SDK 端到端"。

### 6.6 测试工具包

⏳ `agentim-test`：进程内服务端（SQLite、可控时钟）、故障注入（丢推送、乱序、发送失败、令牌过期）、事件记录和断言；SDK 一致性测试和开发者自己的应用测试都用它（[08](08-sync-and-client.md) 的随机故障测试）。

### 7.1 协议摘要（JSON over WebSocket）

连接：`GET /ws?token=<token>[&v=<协议版本列表>]`，服务端先发 `welcome`（选定的协议版本、服务端版本、功能列表、限制），版本规则见 [02 §2.5](02-architecture.md)。客户端帧：`{"op": "...", "rid": 1, ...}`；服务端对请求回 `{"type": "res", "rid": 1, "ok": true | false, ...}`。

| op | 用途 |
|---|---|
| `hello {protocol?, client?, features?}`、`list_convs`、`create_conv`、`add_member` | 基础；`hello` 协商协议并检查最低客户端版本，只返回和你有共同会话的人和你的 Agent；单聊每对用户只有一个，重复创建返回已有的（`existing: true`） |
| `update_conv {conv_id, title?, fields?}` | 群主和管理员改群名、自定义字段（事件 `conv.updated`） |
| `remove_member`、`leave`、`set_role`、`transfer_owner`、`dissolve` | 成员生命周期：群主和管理员管理成员；被移除或退出后看不到会话；解散后全员失去访问、内容删除，只保留审计记录 |
| `block`、`unblock`、`list_blocks`、`find_user {name}` | 拉黑（双方都不能单聊、不能拉对方进群、不能发仅某人可见的消息）；按准确用户名找人 |
| `send {conv_id, client_msg_id, text, kind?, payload?, reply_to?, causation_id?, on_behalf_of?, to_user?, to?, topics?, intent?, refs?}` | 发消息；`kind` 为自定义类型时 `text` 是降级文本；`to_user` 表示仅某人可见；`to` / `topics` / `intent` / `refs` 是给 Agent 路由用的信封（[03 §6](03-agents.md)）；审批模式下返回 `draft_id` |
| `signal {conv_id, kind, data?}` | 正在输入等临时信号，只推给在线成员，不落库 |
| `edit {msg_id, text, payload?}`、`recall` | 修订、撤回 |
| `sync {limit?}`、`ack {acks}` | 同步：服务端按这台设备的位置分批下发，客户端存好后确认（[08](08-sync-and-client.md)）；`pull`、`pull_side` 对客户端停用 |
| `unread`、`set_mute {conv_id, mode, until?}`、`set_prefs`、`observe {conv_id, agent_id}` | 未读和 @ 数；免打扰；"一台设备已读其他不提醒"；所有者代看自己的 Agent |
| `heads {conv_ids}` | 位置校验：所在会话的最新序号（最多 200 个，不是成员的不返回）；客户端发现比自己记录的新就同步，用来补上最后一条丢失的推送（11 §6.4）；Agent SDK 每 30 秒做一次 |
| `read`、`focus` | 已读游标；前台会话（接收流式增量） |
| `stream_start / stream_append / stream_end / stream_cancel` | 流式 |
| `whisper`、`approve`、`reject`、`takeover`、`release`、`set_agent_policy {conv_id, agent_id, approval?, trigger?, topics?}`、`reset_guard` | 所有者的介入操作；`trigger` 是 Agent 的接收方式（all、mention、addressed、topics、observe、coordinated） |
| `history {conv_id, after_seq?, before_seq?, limit?}`、`context {conv_id, max_tokens?}`、`search {query, conv_id?, limit?, 过滤…}`、`put_summary {conv_id, from_seq, to_seq, text}` | Agent 的历史服务（[03 §7.1](03-agents.md)）：只能读自己可见的部分，人返回 `bad_request` |
| `state_get {key, version?}`、`state_put {key, value, version}`、`state_list {prefix?, after?, limit?}`、`state_delete {key, version}` | Agent 的检查点（[03 §7.2](03-agents.md)）：写入时比较版本 |
| `report {target_kind, target_id, category, text?}` | 举报消息、用户或会话（[04 §4.2](04-security-compliance.md)）。删除账号和导出只由开发者后端调开放 API |
| `stop_agent {agent_id, reason?}`、`resume_agent {agent_id}`、`destroy_agent {agent_id, confirm}` | 负责人急停、恢复、销毁自己的 Agent（[03 §4.3](03-agents.md)） |
| `handoff {conv_id, to?, note}`、`handback {conv_id, agent_id, note?}`、`respond {msg_id, block_id, action? \| values?}`、`progress {conv_id, msg_id?, kind, text, data?}`、`feedback {msg_id, rating, reason?}`、`list_feedback {agent_id, limit?}`；`send` 的 `kind: agentim.card` 和 `sources` | AI 消息体验（[03 §3](03-agents.md)）：转人工、卡片、进度、来源、反馈 |
| `update_task {conv_id, state?, assignee?, note?}`、`claim {msg_id}`、`release_claim {msg_id}`、`floor_grant {conv_id, agent_id, ttl_secs?}`、`floor_release {conv_id}` | 任务频道（`create_conv {kind: "task", assignee?}`）、抢单、发言权（[03 §8](03-agents.md)） |
| `list_drafts` | 待审批草稿 |
| `list_devices`、`logout_device {device_id}` | 自己的设备（App 连接时用 `device=` 选定）；下线一台设备并立即断开它的连接，这台设备上已签发的令牌作废（只限人） |
| `create_agent {name}`、`list_agents`、`agent_key {agent_id, revoke_others?}`、`revoke_agent_key {agent_id, device_id}` | 自己的 Agent 和它们的密钥（[03 §2.1](03-agents.md)）；Agent 也可以通过 `POST /mcp` 接入 |
| `request_human`、`decide`、`cancel_request`、`get_request {request_id, wait_secs?}`、`inbox` | 请人决定和待办（[03 §4.2](03-agents.md)）：Agent 请人批准、回答或选择，负责人或被指定的人决定，只有一个决定生效 |

服务端推送：`user.updated`（开发者改了这个人在客户端的权限，带算好的 `permissions`）、`resync`（推送接不上，需要再 `sync`）、`mute`（自己在其他设备上设置的免打扰）、`read`（自己在其他设备上的已读）、`device.added`（新设备登录）、`event`（发给 Agent 时附带 `trust` 和 `flags`）、`side`、`delta`、`stream_cancelled`。外部 Agent 的接入示例见 `server/examples/agent.mjs`。

### 7.2 当前性能

三种数据库的单机完整数据见根目录 [README](../README.md#single-node-performance)，用 `server/bench/single-node.sh` 生成，用户可以在自己的机器上重跑。要点：单库写入约 1,000–1,300 条/秒（瓶颈是每条 SQL 语句的固定开销，不是 fsync，见 [02 §4.8](02-architecture.md)）；1 万连接时端到端 p99 在 11–21ms；每个连接约 13.5KB 服务端内存；`kill -9` 后 130–240ms 恢复就绪。

### 7.3 已知限制

`--demo` 的演示登录不需要密码，只监听本机地址（正式部署用开发者签名的令牌）；审批草稿没有过期时间；接管锁不会超时自动交还；在线迁移还没有管理接口。撤回会清空数据库中的内容，但 SQLite 的 WAL 文件在下次检查点之前可能还留着旧页面，是否在撤回后主动做检查点待定。建大群时，创建者会收到每个成员的加入事件（2000 人群就是 2000 条），超过推送队列的部分会被丢弃并改发 resync，数据不丢，但更合理的做法是合并成一条事件（放在大群模式里做）。

## 8. 开发者控制台

见 [12 §4](12-developer-experience.md)（P4）。控制台内嵌在 `agentim` 程序里（打包进二进制的单页应用，不是单独的程序），调用管理 API `/admin/v1`；所有修改都经过服务端的业务逻辑，并写审计，**控制台不直接读写数据库**。
