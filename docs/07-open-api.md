# 07 开放 API（服务端 API）

> 版本 v0.1（2026-10-10），方案已确认（D22–D25），M3 实现。开放 API 是给**开发者的后端**调用、用来操作 IM 的接口：以某个用户或系统的身份发消息、撤回、建群、拉人、导入用户、签发登录令牌等。它和管理 API 是两回事，见 §1。

## 1. 四类接口，各管各的

| 接口 | 谁在用 | 做什么 | 身份 | 位置 |
|---|---|---|---|---|
| **客户端协议** | 最终用户的设备（App、网页、Windows 端、Agent） | 收发自己的消息、同步、在线推送 | 用户或 Agent 的令牌，每台设备一个 | WebSocket `/ws`（[05 §7.1](05-operations.md)） |
| **开放 API**（本文） | 开发者的后端服务 | 以用户或系统的身份操作 IM，批量和导入 | 应用的 API Key | HTTPS `/v1/...`，对公网 |
| **管理 API** | 部署方的运维和管理员（管理系统，[05 §8](05-operations.md)） | 整个部署的运维：数据库与组织单元、迁移、管理员账号、全站审计、加密密钥、系统健康 | 管理员账号 + 角色 | `/admin/v1/...`，默认只在内网 |
| **Webhook / MCP** | 开发者的后端、Agent 框架 | 接收事件、发送前拦截（[02 §2.6](02-architecture.md)）；Agent 通过 MCP 使用 IM（[03 §9.5](03-ai-native.md)） | 签名回调；Agent 凭据 | 由服务端主动调用 / MCP 端点 |

一句话区分：**开放 API 操作的是"IM 里的数据和行为"（某个应用里的用户、会话、消息），管理 API 操作的是"这套 IM 系统本身"。** 开放 API 的 Key 不能做任何管理 API 的事，反之亦然。

## 2. 业内做法

| 产品 | 鉴权 | 以用户身份操作 | 批量与全员 | 其他 |
|---|---|---|---|---|
| 腾讯云 IM | 应用管理员账号 + 管理员的 UserSig 签名，带 `sdkappid`、随机数 | 请求里写 `From_Account`，收到的人看到的发送者就是这个用户，并可选择是否同步到该用户的其他设备 | 一对多批量发送；按账号列表推送（每次 1–500 人，默认 30 次/秒）；全员推送只在高级版本提供，默认每天 100 次，可设"只发给在线用户" | 群消息接口默认 200 次/秒；按地域使用不同域名 |
| Stream | 服务端用应用密钥（API Secret）认证；客户端令牌只能由服务端用密钥签发 | 服务端可以以任何用户的身份操作 | 有 | 有发送前 Webhook、AI 流式消息的服务端方案 |

## 3. 方案

### 3.1 应用与凭据

- **应用（App）**：一个部署里可以有多个应用，每个应用的用户、会话、消息完全隔离（数据模型里已有 `tenant_id`，即应用 ID）。单独部署的用户默认只有一个应用。
- **API Key**：`key_id` + 密钥，一个应用可以有多个 Key，用于轮换（新旧两个同时有效）。每个 Key 有**权限范围**（见下表）、可选的 **IP 允许列表**、过期时间，可以随时吊销。数据库里只存密钥的哈希。
- **两种认证方式**（D24）：
  - 默认：`Authorization: Bearer <key>`，强制 HTTPS（只有本机地址允许明文，方便开发）。和 Stream、Sendbird 一样简单。
  - 可选的请求签名：`HMAC-SHA256(密钥, 时间戳 + 随机数 + 方法 + 路径 + 请求体哈希)`，5 分钟内有效，随机数防重放。适合不信任中间网络、或者合规要求签名的企业。比国内常见的 SHA1 方案更安全。

| 权限范围 | 允许 |
|---|---|
| `tokens:issue` | 给用户签发、吊销客户端登录令牌 |
| `users:write` / `users:read` | 创建、导入、修改、停用、删除用户；读取用户资料 |
| `conversations:write` / `conversations:read` | 建会话、改资料、管理成员和角色、解散；读取会话和成员 |
| `messages:write` | 以用户或系统身份发消息、编辑、撤回、标记已读 |
| `messages:read` | 读取消息历史（**单独的权限**，因为它能读到私聊内容；每次读取写审计） |
| `moderation` | 拉黑、封禁、禁言、处理举报 |
| `compliance` | 导出、删除用户数据（GDPR） |
| `agents:write` | 注册 Agent、管理凭据和策略（[03 §9](03-ai-native.md)） |

### 3.2 以谁的身份操作（D25）

| 方式 | 写法 | 规则 |
|---|---|---|
| **以用户身份** | 请求体里 `"as": "<user_id>"` | **完全遵守这个用户的业务规则**：必须是会话成员、受拉黑和单聊规则约束、去重按这个用户算。结果和用户在客户端上操作一模一样（会同步到这个用户的所有设备） |
| **以系统身份** | `"as": "system"` | 每个应用有一个系统身份。可以：建会话、管理成员和角色、发系统通知（消息上标明来自系统）、撤回任何消息、解散会话。**不能**冒充用户说话，也不受"必须是成员"的限制 |

不提供"以任意用户身份、绕过规则"的超级模式：服务端调用一旦能绕过规则，就会破坏"业务正确"这条核心保证，也让审计失去意义。每次调用都写审计：用了哪个 Key、以谁的身份、做了什么。

### 3.3 用户 ID 由开发者决定（D23）

开发者已经有自己的用户系统，最方便的是**直接用他们自己的用户 ID**（例如 `user_12345`）。`PUT /v1/users/{id}` 按开发者给的 ID 创建或更新（幂等，适合同步和导入）。ID 规则：1–64 个字符，字母、数字和 `_-.@:`，应用内唯一。服务端内部 ID 照旧，两者一一对应。

### 3.4 接口一览（v1）

| 资源 | 接口 | 说明 |
|---|---|---|
| 登录令牌 | `POST /v1/users/{id}/tokens` | **开发者后端给用户签发客户端令牌**（可设有效期、设备名、权限）。这就是 D21 里"用开发者自己的用户体系登录"的落地 |
| | `DELETE /v1/users/{id}/tokens` | 吊销这个用户的全部令牌（例如改密码、封号后） |
| 用户 | `PUT /v1/users/{id}`、`GET`、`PATCH` | 创建或更新、读取、修改资料（昵称、头像、自定义字段） |
| | `POST /v1/users:batch` | 一次最多 100 个，逐个返回结果 |
| | `POST /v1/users/{id}:deactivate`、`:reactivate` | 停用后不能登录，已有的消息保留 |
| | `DELETE /v1/users/{id}` | GDPR 删除，异步任务（§3.6） |
| 会话 | `POST /v1/conversations` | 建群或单聊；可以指定开发者自己的会话 ID；单聊每对用户只有一个 |
| | `GET`、`PATCH`、`DELETE /v1/conversations/{id}` | 读取、修改资料、解散 |
| | `POST /v1/conversations/{id}/members`、`DELETE …/members/{user}`、`PATCH …/members/{user}` | 批量拉人、移除、改角色；转让群主 |
| | `GET /v1/users/{id}/conversations` | 某个用户的会话列表 |
| 消息 | `POST /v1/conversations/{id}/messages` | 在会话里发消息（以用户或系统身份）；可带路由信封 `to`、`topics`、`intent`、`refs` 和来源 `sources`（[09 §10.1](09-agent-communication.md)、[03 §9.6.1.1](03-ai-native.md)） |
| | `POST /v1/users/{id}/messages` | **"给某人发消息"**：没有单聊就自动建一个 |
| | `POST /v1/messages:batch-send` | 同一个发送者发给多人（一次最多 500 人），逐人返回结果 |
| | `PATCH /v1/messages/{id}`、`POST /v1/messages/{id}:recall` | 编辑、撤回 |
| | `GET /v1/conversations/{id}/messages` | 历史消息，按 seq 分页（需要 `messages:read`） |
| | `POST /v1/conversations/{id}/read` | 替某个用户标记已读 |
| 全员通知 | `POST /v1/broadcasts` | 发给全部用户或某个单元，异步任务；可选"只发给在线用户"；单独限流 |
| 导入 | `POST /v1/conversations/{id}/messages:import` | 迁移历史消息：保留原时间和发送者，不推送、不算未读 |
| 审核 | 拉黑、封禁、会话内禁言、举报队列 | 随合规阶段（M10） |
| 异步任务 | `GET /v1/jobs/{id}` | 导出、删除、全员通知、导入的进度和结果 |

### 3.5 通用约定

| 方面 | 约定 |
|---|---|
| 版本 | 路径带主版本 `/v1`，规则和协议版本管理一致（[02 §2.5](02-architecture.md)）：主版本内只做向后兼容的新增 |
| 接口描述 | **OpenAPI 3.1**，由服务端代码生成（Rust 的 utoipa），保证文档和实现一致；服务端 SDK（Node、Python、Go、Java、PHP）从它生成 |
| 防重复 | 所有 `POST` 支持 `Idempotency-Key` 请求头，保留 24 小时：同一个 Key 重试返回第一次的结果；同一个 Key 配不同的请求体返回 `422`。发消息还可以用 `client_msg_id`，和客户端的去重一致 |
| 错误 | RFC 9457 `application/problem+json`，带一个稳定的 `code` 字段，**和 WebSocket 协议的错误码完全相同**（`forbidden`、`not_found`、`conflict`、`bad_request`、`blocked`、`rate_limited`……），HTTP 状态码按含义对应（403、404、409、400、429……） |
| 批量 | 逐项返回结果（`{"results": [{"ok": true, …}, {"ok": false, "code": "blocked"}]}`），一项失败不影响其他项，和组提交里"一条失败不影响同批"的保证一致 |
| 分页 | 游标分页（`cursor` + `limit`，最大 200）；消息历史的游标就是 seq |
| 限流 | 按 Key 和接口分别限流；响应带 `RateLimit-Policy` / `RateLimit` 头（IETF 草案）；超出返回 `429` 和 `Retry-After` |
| 时间与 ID | 时间用毫秒时间戳；ID 都是字符串 |

### 3.6 和核心保证的关系

- **同一条写入路径**：开放 API 的写入和客户端一样经过单写者和组提交，fsync 之后才返回成功，所以同样不丢、有序、去重。
- **同样的推送**：通过开放 API 发的消息，会话成员和客户端发的一样实时收到；以用户身份发的消息会同步到这个用户的所有设备。
- **同样的业务规则**：以用户身份调用时，规则和客户端完全一致（§3.2）。
- **端到端加密的会话**：服务端没有密钥，无法替用户发加密消息，所以开放 API 向这类会话发消息返回 `bad_request`；成员管理照常可用。
- **异步任务**：导出、删除、全员通知、导入在后台分批执行，可以重试、可以查询进度；全员通知按批写入，不会挤占在线用户的实时消息（单独的队列和限流）。

### 3.7 安全与合规

- Key 只存哈希；日志里不出现密钥和消息内容；每次调用写审计（Key、身份、操作、目标、结果）。
- `messages:read` 和 `compliance` 是单独的权限，默认不给；读取历史消息写审计，满足"谁看过谁的消息"的追溯要求。
- GDPR 的导出和删除走 `compliance` 权限的异步任务，并且和保留策略、法律保全（企业版）联动。

### 3.8 测试计划（按 [CLAUDE.md](../CLAUDE.md) 的测试规则）

| 范围 | 覆盖 |
|---|---|
| 每个接口 | 正常路径；每种权限范围缺失时返回 403；以用户身份时用户的每条业务规则（非成员、拉黑、单聊、被移除）；以系统身份时允许和不允许的操作；未知 ID、超限、非法参数 |
| 一致性 | 开放 API 发的消息与客户端发的在日志、推送、未读、去重上完全一致；以用户身份发的消息同步到该用户的所有设备 |
| 防重复 | 同一个 `Idempotency-Key` 并发重试只执行一次；同 Key 不同请求体返回 422 |
| 批量 | 部分失败逐项返回；500 人批量发送和客户端发送同时进行时 seq 连续、无丢失 |
| 鉴权 | 吊销、过期、IP 不在允许列表；签名错误、时间过期、随机数重放 |
| 限流 | 超出返回 429，其他 Key 不受影响 |
| 故障 | 批量发送中途 `kill -9`：已确认的项全部存在，未确认的项重试后不重复 |
| 跨平台与数据库 | 三种数据库；Linux 和 Windows |

## 5. 实现细节（M3）

| 方面 | 做法 |
|---|---|
| 应用 | MVP 1 每个部署一个应用（`default`，即数据模型里的 `tenant_id`）。多应用之间的完全隔离和管理界面放 MVP 2 |
| API Key | 格式 `ak_<key_id>_<secret>`，数据库只存整个 Key 的 SHA-256。用命令行管理：`agentim api-key create --scopes …`（只在创建时显示一次）、`api-key list`、`api-key revoke <key_id>`。可选过期时间和 IP 允许列表。服务端运行时用命令行新建的 Key 立即可用；吊销在 10 秒内生效（每 10 秒重新读取，未知的 Key 最多每秒查一次库） |
| 明文 HTTP | 只有来自本机地址的请求允许；部署在 TLS 反向代理之后时设 `open_api.allow_http = true` |
| 客户端令牌 | 格式 `atk_<43 位 base64url>`（256 位随机数），只存 SHA-256；每个令牌就是一台设备（`device_id`、名称、平台、签发时间、过期时间、最近使用时间）。老数据库里的明文令牌在升级时改为哈希 |
| 设备 | 客户端协议加 `list_devices`、`logout_device {device_id}`（吊销并立即断开那台设备的连接）；开放 API 吊销用户的全部令牌时也立即断开。新设备登录时，这个用户已在线的设备收到 `device.added`；已读在其他设备上同步（`read` 推送） |
| 以系统身份 | 内置的系统用户（`kind = system`，名字 `system` 保留）。可以发系统通知（`sender_type = system`，不需要是成员）、拉人、移除非群主的成员（群主要先转让）、改角色、转让群主、撤回任何消息、解散会话、读取任何会话的历史。建会话必须指定 `owner`，按这个用户的身份建，拉黑等规则照常检查 |
| 以用户身份 | 内部用一个不登记在线状态的会话执行和客户端完全相同的操作，所以规则、去重、推送、审计一致 |
| 审计 | 每个写操作和每次读取历史都写审计：`api.<操作>`，带 Key ID 和身份 |
| 防重复 | `Idempotency-Key`（1–255 个可见字符）保存 24 小时：同 Key 同请求体返回第一次的结果（响应头 `Idempotent-Replayed: true`）；不同请求体 `422`；第一次还在执行时 `409` |
| 限流 | 每个 Key 一个令牌桶，默认每秒 100 次、突发 200 次（`open_api.rate_per_second`、`open_api.burst`）；响应头 `RateLimit-Policy`、`RateLimit`；超出 `429` + `Retry-After` |
| 错误 | `application/problem+json`：`type`（`https://agentim.dev/errors/<code>`）、`title`、`status`、`detail`、`code`；状态码：`bad_request` 400、未认证 401、`forbidden` / 缺权限 403、`not_found` 404、`conflict` 409、`idempotency_mismatch` 422、`rate_limited` 429、`blocked` 403、`policy_blocked` 403、`overloaded` / `storage_unavailable` 503 |
| OpenAPI | 手写的 OpenAPI 3.1 文档放在 `server/openapi.json`，`GET /v1/openapi.json` 返回它；测试保证文档里的每个路径和方法都存在于路由里，反之亦然。（原计划用 utoipa 在代码上标注，改为手写加测试，少一个宏依赖，效果一样） |
| 服务端 SDK | Node（TypeScript）、Python、Go 三个轻量客户端，手写，覆盖全部接口，带重试（同一个 `Idempotency-Key`）和错误类型；CI 里各跑一遍对真实服务端的冒烟测试 |
