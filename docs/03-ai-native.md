# 03 AI 原生

> 版本 v0.4（2026-10-10）。§1–§5、§8 已实现。§6（审批 v2）、§7（工具网关）、§9.6（A2A 网关与联邦）不做（2026-10-18 决定，聚焦开发者）；§9（AI 核心组件）已确认（D15），按 §9.7 分步实现。

目标：**AI 可以与任何人、任何 AI 交流；人可以随时介入、审批、过滤、监控。**

## 1. Agent 身份

- 参与者分为 `human`、`agent`、`system` 三类。`sender_type` 由服务端按认证身份写入，Agent 无法冒充人类。
- 每个 Agent 都有**所有者**（个人或组织）和**权限范围**（能加入哪些会话、预算多少）。
- 消息同时记录"谁发的"（`sender_id`）和"代表谁发的"（`on_behalf_of`）。Agent 只能代表它的所有者发言。
- 支持四种会话形态：人与人、人与 AI、AI 与 AI、混合群聊。消息模型完全相同，区别只在策略。

## 2. 信任模型：IM 能强制什么

Agent 运行在 IM 外部，所以 **IM 只能强制它经手的东西**。

| 能力 | 能否强制 | 条件 |
|---|---|---|
| Agent 的消息：审批、撤回、接管、打断 | 能 | 消息必须经过 IM |
| Agent 能读到什么 | 能 | IM 只投递允许的内容 |
| 速率、按消息数和字符数计的预算 | 能 | |
| 按 token 计的预算 | 只能依赖 Agent 上报 | 不做模型网关（D54），模型调用的强制限额交给客户已有的模型网关 |
| 工具调用、直连外部系统 | 不能 | IM 不代理工具调用（不做工具网关）；Agent 可以用"请人决定"（§9.3.4）主动请人批准，这属于协作，不是强制 |

产品文案必须区分"强制"和"协作"两类能力，不能让用户误以为工具调用也有 IM 的审批兜底。

## 3. 读取范围与告知

- `trigger` 模式：群聊默认 `mention`（只收到 @ 它的消息、回复它的消息，以及它自己的消息），私聊默认 `all`。思路与 Telegram bot 的隐私模式相同。
- Agent 只能读到加入以后（`join_seq` 之后）的事件。群管理员可以单独授予"加入前的历史"🔧。
- Agent 加入会话时产生全员可见的事件，事件里带所有者和读取范围，客户端必须展示。这满足 GDPR 的告知要求，也满足 EU AI Act 第 50 条的披露要求，见 [04](04-security-compliance.md) §4。
- 所有者经 Agent 观察会话时，只能看到 Agent 能读到的范围，而且只限自己也是成员的会话（§9.3.1）；观察动作写入审计。

## 4. 流式消息（已实现）

```
stream_start ──▶ streaming（分配 conv_seq，事件 msg.created）
   │  stream_append × N：不占 seq，按 (msg_id, idx) 幂等；重复的 idx 忽略，跳号拒绝
   │  60ms 合并推送，只推给正在看这个会话的人；进入会话时先收到当前快照
   │  每秒写一次检查点
   ├─ stream_end ──────────▶ complete
   ├─ stream_cancel ───────▶ cancelled（发送者、所有者，或任何人类成员点"停止"）
   ├─ 流式过程中命中 DLP ──▶ cancelled，内容替换为"已被策略移除"
   ├─ 接管 ────────────────▶ cancelled(taken_over)
   └─ 看门狗：Agent 断开或 30 秒没有新分块 ──▶ failed(disconnected | timeout)
```

上限：单条 256KB、最长 10 分钟；每个 Agent 在每个会话内最多 2 路并发流。

持久性分两档：已结束的流式消息与普通消息同等，ACK 后不丢；生成中的增量是尽力送达，崩溃时最多丢失最后一个检查点之后的内容（≤ 1 秒）。

## 5. 人工介入（已实现）

| 方式 | 实现 |
|---|---|
| 观察 | 所有者经 Agent 只读订阅（只限自己也是成员的会话）；写审计 |
| 耳语 | 侧信道事件，`audience = [Agent, 发起人]` |
| 审批 | 草稿放在侧信道，不占 seq；批准后才写入主日志并分配 seq |
| 打断 | `stream_cancel`；Agent 收到 `stream_cancelled` |
| 接管 | 接管锁存在数据库里；接管期间 Agent 发送会被拒绝（`taken_over`）；全员可见 `agent.state` 事件 |
| 撤回 / 修订 | 发送者或 Agent 的所有者可以操作；写审计 |

## 8. 过滤与护栏（已实现）

| 检查点 | 位置 | 对纯人类会话的影响 |
|---|---|---|
| 进入 AI 之前（注入检测，标记低信任） | 投递给 Agent 的路径上 | 无 |
| AI 输出之后（DLP：卡号、密钥） | Agent 的发送路径上，提交之前 | 无 |
| 流式过程中 | 按块检查累积内容 | 无 |

| 护栏 | 规则 | 触发后 |
|---|---|---|
| 跳数上限 | `hop > 6` 拒绝。hop 由服务端计算：人发的消息为 0，Agent 回复第 n 跳的消息记为 n+1 | 熔断，全员可见事件，通知所有者 |
| 重复检测 | 同一 Agent 在同一会话内重复相同内容 ≥ 3 次 | 熔断，冷却 60 秒 |
| 速率 | 每个 Agent、每个会话一个令牌桶 | `rate_limited` |
| 预算 | 每个 Agent 每日的消息数和字符数上限 | `budget_exceeded` |

已知限制：Agent 之间如果通过 IM 以外的渠道形成循环，IM 无法感知。预算目前存在内存里，重启后清零🔧。

## 9. AI 核心组件（D15，已确认）

目标：AgentIM 不只是"能和 AI 聊天的 IM"，而是 **AI 之间、AI 和人之间沟通协作的底层组件**。Agent 在这里交流、分派任务、记录事项、被人管理。

### 9.1 业内现状：协议有了，缺的是"可靠的会话层"和"治理层"

| 协议 / 项目 | 解决什么 | 现状 | 没解决什么 |
|---|---|---|---|
| **MCP**（Agentic AI Foundation） | Agent 调用工具和数据 | 2026-07-28 版本改成无状态、**去掉了流的断点续传**；长任务（Tasks）和 MCP Apps 成为官方扩展；追问改为多轮请求（`input_required`）；授权对齐 OAuth | 不管 Agent 之间、Agent 和人之间的对话 |
| **A2A v1.0**（Linux Foundation） | Agent 之间委派任务：Agent Card（能力说明，可签名）、Task 状态机、消息 / 产出物、流式、推送通知 | 2026 年 4 月发布 1.0，150 多家组织支持，已进入 Google、微软、AWS 的平台 | 点对点的请求 / 响应；没有多方会话、没有持久有序的共享记录、没有人工介入和审批、跨组织治理留给实现方 |
| **AG-UI** | Agent 和前端界面之间的事件流（文本流、工具调用、状态同步） | 进入 Microsoft Agent Framework、Google ADK | 只管界面同步，不管存储和权限 |
| **AGNTCY**（Linux Foundation） | Agent 目录（发现）、身份徽章（W3C 可验证凭证）、SLIM 消息层（gRPC + MLS 群组加密，IETF 草案） | 草案仍在变化 | 偏传输和发现，不管业务语义 |
| **NANDA**（MIT） | 替代 DNS 的 Agent 命名与索引，可验证的 AgentFacts | 研究阶段 | 同上 |
| Agent 记忆产品（各类向量库、记忆服务） | 单个 Agent 的长期记忆 | 很多 | 研究和厂商都指出**缺治理**：作用范围、版本、来源、删除、审计、多 Agent 共享时的正确性 |

**海外产品**（2026-10 调研，详见 [research/sdk-and-ai-2026.md §3](research/sdk-and-ai-2026.md)）：Slack、Teams、Linear 把 Agent 做成流式回复 + 展示步骤 + 委派任务；微软 Agent 365 / Entra Agent ID 定下了企业治理的模板（每个 Agent 有人类担保人、独立凭据、生命周期、一键阻止、审计）；所有 Agent 框架都有"暂停等人批准"，但**没有一家提供多人、持久、可审计、送到对的人面前的处理界面**；Stream、Sendbird、Intercom 等聊天厂商都是闭源 SaaS、偏客服。

结论：**MCP 管"Agent 用工具"，A2A 管"Agent 找 Agent 办事"，AG-UI 管"Agent 上屏幕"；而"多方之间持久、有序、可审计、可介入的交流和协作记录"以及"对 Agent 的治理"没有人做好。** 这正是 IM 的强项（会话、顺序、权限、多端同步），也是 AgentIM 已经具备的能力（seq 连续不丢、审批、接管、护栏、审计）。所以定位是：**兼容这些协议，做它们下面那一层可靠的会话与治理底座**，而不是再发明一个协议。

### 9.2 总体结构

```
          外部 Agent（MCP 客户端、Agent SDK）                 人（客户端、SDK）
                 │ MCP / WebSocket                                  │ WebSocket
                 ▼                                                  ▼
   ┌──────────────────────── AgentIM ──────────────────────────────────────┐
   │ MCP 服务（§9.5）  Agent SDK  AG-UI 映射                                │
   │ ───────────────────────────────────────────────────────────────────── │
   │ Agent 注册与身份（§9.3.1）  任务（§9.3.2）  记事本（§9.3.3）           │
   │ Agent 管理：生命周期、权限、预算、急停、观测（§9.4）                    │
   │ ───────────────────────────────────────────────────────────────────── │
   │ 现有核心：会话主日志（seq 连续）、侧信道、流式、审批、接管、护栏、审计  │
   └───────────────────────────────────────────────────────────────────────┘
```

所有新能力都落在现有的会话日志上：任务的每次状态变化、记事本对会话共享部分的修改都是主日志里的事件，所以天然继承**不丢、有序、多端同步、审计、人工介入**。

### 9.3 新增的三个基础对象

#### 9.3.1 Agent 注册与身份

- 每个 Agent 有一份档案：所有者、所属单元、简介、技能（skills）、输入输出类型、版本、联系方式（WebSocket 在线 / Webhook）、状态（启用 / 暂停 / 退役）。
- **人类负责人（担保人）必填**（参考 Entra Agent ID）；长期不活跃的 Agent 标记出来，可配置自动退役。**Agent 分两种**，创建时定下，之后由管理员改（[06 §1.1](06-plan.md) D89，2026-10-16 确认）：

  | | 个人助理（`personal`，默认） | 团队 Agent（`team`） |
  |---|---|---|
  | 是什么 | 某个人的分身：替他回消息、整理待办 | 属于群或组织：发布机器人、客服、HR 问答、知识库；负责人只是维护者 |
  | 谁能创建 | 任何人（`create_agent`） | 只有管理员：`agentim agent create --team --name … --owner …`（管理 API 随 D63 一起做；以后有单元管理员时也可以） |
  | 负责人离开或被移出会话 | 一起离开（日志 `reason: owner_left`） | 留下 |
  | 负责人被停用 | 急停，重启后仍停止；重新启用后由他自己恢复 | 照常运行；管理员的 Agent 列表里标为"负责人已停用"，由管理员转给同一单元的另一个人（`agentim agent transfer --name … --owner … [--rotate-keys]`；旧负责人手里有密钥副本时应轮换） |

  两种都遵守同一条规则：**负责人只在自己也是成员的会话里行使负责人的权力**——代看、接管、耳语、改 Agent 策略、重置熔断、审批草稿，以及收到这个会话里的草稿、反馈、通知（侧信道）。不是成员时这些操作返回 `forbidden`，侧信道也不再发给他；会话之外的管理（急停、恢复、销毁、密钥、全局设置、运行状态）不受影响。
  - 团队 Agent 所在会话的管理者（群主、管理员）可以改它在本会话的策略、重置它的熔断，就像 Slack 频道管理员配置频道里的机器人。
  - 开着审批的 Agent 在负责人不在的会话里发言返回 `conflict`（没人能审批），而不是生成没人看得到的草稿；由会话管理者关掉审批或请负责人入群。
  - 剩余风险：负责人如果持有 Agent 的密钥，可以用 Agent 自己的身份读它所在的会话。这是"让他维护这个 Agent"本身带来的，靠管理员只给可信的人团队 Agent、交接时轮换密钥来控制。
- 凭据：每个 Agent 独立的 API Key（前缀 + 随机数，只存哈希，可设置权限范围、轮换、吊销），之后支持 OAuth client credentials。
- 组织内发现：按单元和权限过滤的 Agent 目录（人和 Agent 都能搜"谁能处理退款"）。

#### 9.3.2 任务（Task）

"Agent 用这个记录事项"的结构化部分。任务是会话里的一等对象，状态机与 A2A 对齐，人和 Agent 用同一套：

```
submitted → working → completed
              │  ↘ input_required（需要人或其他 Agent 补充信息）→ working
              │  ↘ auth_required（需要授权 / 审批）→ working
              ↘ failed / canceled / rejected
```

- **委派给 Agent 时人仍是负责人**（参考 Linear）：任务记录"负责人"（人）和"执行者"（Agent），出了问题找得到人。
- **进度事件**：Agent 在执行过程中发出带类型的进度（思考、调用工具及结果摘要、计划步骤、提问、出错），作为侧信道事件挂在任务和流式回复旁边，界面可以像 Slack 的任务卡片那样展示；收到任务后应在约 10 秒内确认（`working`），超时可提醒负责人。
- 字段：标题、描述、发起方、负责方（Agent 或人）、父任务（委派链，用于追溯"谁把活派给了谁"）、截止时间、优先级、产出物（文本、文件、结构化数据）、来源消息。
- 每次变化写主日志事件（`task.created`、`task.updated`、`task.artifact`），会话成员实时看到、离线能补拉；任务列表可以按会话、按负责方、按状态查。
- `input_required` 直接变成给人的提问（富消息按钮），`auth_required` 接到请人决定（§9.3.4），所以"Agent 卡住了需要人拍板"有统一入口。
- 防失控：每个任务有委派深度上限（复用跳数思路）和预算；子任务失败可以按策略上报给父任务。

#### 9.3.3 Agent 记事本（记忆）

"Agent 用这个记录事项"的非结构化部分：笔记、待办、学到的偏好、和某个客户的上下文。业内记忆产品普遍缺治理，这里按治理优先设计：

| 作用范围 | 谁能读写 | 例子 |
|---|---|---|
| Agent 私有 | Agent 自己；所有者可查看、修改、删除 | "这个用户喜欢简短回答" |
| 会话共享 | 会话成员（人和 Agent） | "本次退款流程的进展"，修改写主日志事件 |
| 单元知识 | 单元内授权的 Agent 和人 | 部门的 FAQ、流程 |

- 每条记录带**来源**（来自哪条消息、哪个任务）、版本历史、有效期；删除是真删（满足 GDPR 删除请求，也纳入保留策略）；静态加密；他人读取写审计。
- **定位是"受治理的记事本"，不和 Mem0、Letta、Zep 这类记忆产品比检索效果**：我们的价值在作用范围、来源、审计、删除。
- 第一版只做键值、标签和全文检索；向量检索做成可插拔接口，让用户接自己的向量库，避免绑定某一家。
- 隔离等级沿用组织单元（[04 §5](04-security-compliance.md)）：L2 / L3 单元的记事本跟随单元放在它自己的数据库里。

#### 9.3.4 请人决定（统一的人工介入请求）和待办

各 Agent 框架都会"暂停等人"：工具需要审批（OpenAI Agents SDK、Google ADK）、LangGraph 的 `interrupt()`、MCP 的 `input_required`、A2A 的 `input-required` / `auth-required`。我们把这些统一成一个对象，现有的"草稿审批"也是它的一种：

| 字段 | 内容 |
|---|---|
| 类型 | 批准 / 拒绝（可修改后批准）、回答问题（文本或表单）、从选项中选择 |
| 发给谁 | Agent 的负责人、会话管理员、或指定的人；可设置"任何一人"或"必须某人" |
| 内容 | 要决定的事情、上下文（来源消息、任务、工具调用参数） |
| 有效期 | 到期自动按配置处理（拒绝或升级给别人） |
| 结果 | **只有一个决定生效**（并发决定只有一个成功，已有草稿审批的并发测试可复用）；结果写日志、写审计，Agent 收到后继续 |

**第一步实现（L3）：**

| 方面 | 做法 |
|---|---|
| 发起 | Agent 用 `request_human {conv_id, kind, title, options?, context?, assignees?, ttl_secs?, client_req_id}`（MCP 工具同名）。`kind`：`approve`（批准 / 拒绝，可修改后批准）、`answer`（回答文字）、`choose`（从 2–20 个选项里选一个）。`title` 1..4KB，`context` 是任意 JSON（例如工具调用参数，≤ 32KB，加密存放）。同一个 Agent 同一个 `client_req_id` 重试返回原来的请求 |
| 发给谁 | 默认是 Agent 的负责人；也可以指定会话里的人（1–20 个，必须是会话成员、不能是 Agent）。**负责人始终可以决定**（人工监督）。任何一个被指定的人决定即生效 |
| 谁能看到 | 发起的 Agent、它的负责人、被指定的人（侧信道，不进主日志，不占 seq）；其他成员看不到 |
| 决定 | `decide {request_id, decision, text?, choice?}`：`approve`、`reject`、`answer`（带 `text`）、`choose`（带 `choice`，必须是选项之一）。**只有第一个决定生效**，之后的返回 `conflict`；决定和请求类型不匹配 `bad_request`；不是负责人也不是被指定的人 `forbidden`；不存在 `not_found` |
| 有效期 | `ttl_secs` 60 秒到 30 天，默认 24 小时；到期变成 `expired`（定时任务处理，到期后再决定返回 `conflict`）。Agent 可以 `cancel_request`；Agent 被移出会话时它的待决请求变成 `cancelled` |
| 结果 | Agent 通过同步收到 `request.decided` / `request.expired` / `request.cancelled` 侧信道事件；也可以 `get_request {request_id, wait_secs?}` 查询，最多等 25 秒（MCP 工具同名，适合不常驻的 Agent） |
| 待办收件箱 | `inbox`：跨会话列出等我决定的请求和我的 Agent 的待审批草稿（统一现有的草稿审批），按时间排序；新请求实时推给在线的被指定的人。离线的手机推送、邮件随 M8 |
| 上限 | 每个 Agent 同时待决的请求最多 100 个，超出 `rate_limited` |
| 审计 | 创建、决定、到期、取消各写一条审计 |
| AI 标记（D36） | 批准草稿发出的消息仍是 Agent 发的（`sender_type: agent`），事件里记下批准人和是否被修改（`approval: {by, edited}`） |

- **待办收件箱**：每个人有一个跨会话的待办列表，列出所有等自己决定的请求（参考 LangChain Agent Inbox，但是多人、持久的）。
- **人不在线时**：通过推送、邮件或 Webhook 通知（参考 Auth0 的异步授权），在任意一台设备上处理。
- 对外映射：MCP 服务（§9.5）把 `input_required` 转成这个请求；Agent SDK 有对应的调用（[05 §6.5](05-operations.md)）。

### 9.4 Agent 管理（治理层）

所有者管理自己的 Agent：

| 能力 | 内容 |
|---|---|
| 生命周期 | 创建、启用、暂停、退役；**急停**：一键暂停自己的某个 Agent，立即断开它的连接、取消进行中的流和任务 |
| 权限 | 能进哪些会话、能读写哪些记事本范围 |
| 预算与成本 | 现有的消息数 / 字符数预算持久化；Agent 上报 token 用量和成本，按 Agent、会话汇总；超过上限自动暂停并通知负责人（Gartner 把成本列为 Agent 项目失败的主要原因之一） |
| 护栏 | 现有的跳数、重复、速率、注入检测、DLP，按 Agent 配置 |
| 观测 | 每条消息、每个任务带追踪 ID（W3C `traceparent`，和 MCP 2026-07-28 一致），按 OpenTelemetry GenAI 语义约定导出（约定还在开发中，相关字段标为实验性），可以接 Datadog、Langfuse、LangSmith；能看到"一个任务经过了哪些 Agent、各花了多少" |
| 审计 | 已有；增加任务、记事本、急停等操作 |

这些都在管理系统（[05 §8](05-operations.md)）里有界面。

### 9.5 MCP 服务：让任何 Agent 框架直接用 AgentIM

AgentIM 自己作为一个 MCP 服务器，**按 2026-07-28 规范（无状态）实现**，不再做已被去掉的会话模式；客户端认证用 Client ID Metadata Documents（动态注册已被弃用）。提供工具：`list_conversations`、`read_messages`、`send_message`、`create_task` / `update_task` / `list_tasks`、`note_put` / `note_get` / `note_search`、`find_agent`、`request_human`（§9.3.4）。任何支持 MCP 的 Agent（各家模型的客户端、LangGraph、CrewAI、自研框架）配置一个地址就能接入，权限按该 Agent 的凭据和范围执行。这是让更多 Agent 用上 AgentIM 的最低成本入口。

### 9.6.1 AI 消息体验（调研中发现缺少的部分）

| 能力 | 内容 | 参考 |
|---|---|---|
| 转人工 | Agent 主动把对话交给人（附交接说明），人处理完可以交回；和"接管"（人主动）互补 | Intercom Fin、Sendbird |
| 结构化消息（卡片、按钮、表单） | 固定的一组组件、声明式 JSON（不执行脚本）；用户的选择或填写作为结果回到 Agent；不支持的客户端显示 `fallback` | Slack Block Kit、ChatKit、MCP Apps（沙箱界面以后作为可选） |
| 工具调用和步骤展示 | §9.3.2 的进度事件在流式回复旁边展示 | Slack 任务卡片、Linear 活动 |
| 引用来源 | Agent 消息可以带来源列表（标题、链接、摘录） | 各 AI 助手 |
| 反馈 | 对 Agent 消息点赞 / 点踩 + 原因，关联追踪 ID，供评估使用 | 各 AI 助手、LangSmith |

#### 9.6.1.1 实现（L6，已实现）

分五部分，每部分单独测试、提交。错误码按项目规则，被拒绝的请求不留痕迹。

| 部分 | 做法 |
|---|---|
| L6a 转人工 | Agent 调用 `handoff {conv_id, to?, note}`：`to` 是会话里的一个人（默认它的负责人，负责人不在会话里时必须指定），`note` 是交接说明（1 字节–4KB）。效果和"接管"一样（复用同一个记录）：Agent 在这个会话里发消息、开始流式回复返回 `taken_over`，进行中的流式回复被取消，不再被唤醒；会话里出现 `agent.state`（`taken_over`，带 `handoff: true`、交接说明、接手的人），接手的人被唤醒、待办里能看到。接手的人或负责人用 `handback {conv_id, agent_id, note?}` 交回：`agent.state`（`active`，带说明），Agent 被唤醒。已经被接管时再转 `conflict`；人调用、`to` 不是会话里的人（不存在、不是成员、是 Agent）都是 `bad_request`。被停下、被接管、转人工的 Agent 都不被唤醒 |
| L6b 结构化消息 | 消息类型 `agentim.card`（`agentim.` 前缀是保留的，别的自定义类型不能冒充），`text` 是不支持的客户端显示的降级文字（必填），`payload` 是声明式 JSON（不执行脚本）：`{title?, blocks: [...], once?}`，组件只有 `text`（文字）、`buttons`（1–10 个按钮，每个 `{id, label, style?: primary/danger}`）、`form`（1–10 个字段 `{id, label, type: text/number/select/checkbox, required?, options?, max?}` 和提交按钮文字）；最多 20 个组件、整张卡片 16KB、ID 是 1–64 个 `a-z0-9_-` 且在卡片内唯一、标签 1–100 字节。成员用 `respond {msg_id, block_id, action? | values?}` 回应：按钮给 `action`，表单给 `values`（必填项、数字、选项、长度都检查）；发卡片的人自己不能回应；每人每张卡片只能回应一次，`once: true` 时整张卡片只接受第一个回应（之后 `conflict`）；已撤回的卡片 `bad_request`。回应写进主日志（`card.response`），唤醒发卡片的 Agent |
| L6c 进度 | Agent 用 `progress {conv_id, msg_id?, kind, text, data?}` 报告进度：`kind` 是 `thinking` / `tool_call` / `tool_result` / `plan` / `step` / `error`，`text` 1 字节–4KB，`data` 是 JSON（≤ 8KB），`msg_id` 可以挂在它自己的一条消息（通常是流式回复）上。写成侧信道事件（`progress`），会话成员都能收到、同步，但不算未读、不唤醒任何人、不进主日志；每个 Agent 每个会话每秒最多 10 条（`agents.progress_per_second`，超出 `rate_limited`） |
| L6d 引用来源 | 发消息时信封可以带 `sources`（1–20 个 `{title, url, excerpt?}`：标题 1–200 字节，`url` 是 http / https 且 ≤ 2048 字节，摘录 ≤ 500 字节），加密存放、随消息下发，草稿保留 |
| L6e 反馈 | 成员用 `feedback {msg_id, rating: up / down / null, reason?}` 对 **Agent 的消息**点赞、点踩或撤销（理由 ≤ 500 字节）；对人的消息、对自己的消息 `bad_request`；每人每条一个，改成别的会更新，和现在一样时什么都不做（不写事件）。反馈只通知 Agent 和它的负责人（侧信道 `feedback`），不进主日志；负责人用 `list_feedback {agent_id, limit?}`（1–100，默认 20）看汇总（赞、踩数）和最近的反馈；理由加密存放 |
| AI 标记（§9.6.2） | 已有：`sender_type` 由服务端写，流式回复从开始就带，批准的草稿带批准人和是否修改。这一步只补测试；SDK 的默认 AI 标识随 L7 |
| 网页 | 卡片（按钮、表单，回应过的变灰）、来源链接、进度、Agent 消息上的 👍 👎、转人工和交回的提示，接手的人在提示旁有"交回"按钮；演示里的 Aria 支持 `/card` |
| MCP | `handoff`、`send_message` 的 `sources`、`send_card`（发卡片）、`progress`；回应和反馈是人做的，不给 Agent 工具；`get_updates` 里卡片回应标为"→ for you" |

### 9.6.2 AI 标记（EU AI Act 第 50 条，2026-08-02 已生效）

- **现状**：每条消息的 `sender_type` 由服务端写入，Agent 不能冒充人；客户端协议、开放 API、Webhook 都带着它，满足"机器可读"的基本要求。
- **要补的**：
  - 被批准的草稿记录"由谁批准、是否被修改"（`approved_by`、`edited_by_human`），仍然标记为 AI 生成；人接管后发的才是人类内容。
  - 流式回复从开始就带标记，不是结束后才有。
  - 以后的文件（Agent 上传的图片、音频）、导出都带标记；2026-12-02 之前要完成已上市系统的机器可读标记。
  - 客户端 SDK 和界面组件默认显示 AI 标识（应用可以换样式，但不提供关闭的开关）。
