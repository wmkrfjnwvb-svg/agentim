# 03 AI 原生

> 版本 v0.3（2026-10-10）。§1–§5、§8 已实现。§6（审批 v2）和 §7（工具网关）是**待确认的方案**。

目标：**AI 可以与任何人、任何 AI 交流；人可以随时介入、审批、过滤、监控。**

## 1. Agent 身份

- 参与者分为 `human`、`agent`、`system` 三类。`sender_type` 由服务端按认证身份写入，Agent 无法冒充人类。
- 每个 Agent 都有**所有者**（个人或组织）和**权限范围**（能加入哪些会话、能调用哪些工具、预算多少）。
- 消息同时记录"谁发的"（`sender_id`）和"代表谁发的"（`on_behalf_of`）。社区版规定 Agent 只能代表它的所有者发言；企业版支持委托：委托后的有效权限 = Agent 权限 ∩ 被代表用户的权限。
- 支持四种会话形态：人与人、人与 AI、AI 与 AI、混合群聊。消息模型完全相同，区别只在策略。

## 2. 信任模型：IM 能强制什么

Agent 运行在 IM 外部，所以 **IM 只能强制它经手的东西**。

| 能力 | 能否强制 | 条件 |
|---|---|---|
| Agent 的消息：审批、撤回、接管、打断 | 能 | 消息必须经过 IM |
| Agent 能读到什么 | 能 | IM 只投递允许的内容 |
| 速率、按消息数和字符数计的预算 | 能 | |
| **工具调用：授权、审批、审计** | **能**，前提是工具经过 IM 的工具网关（§7） | Agent 手里没有工具的直接凭据；凭据由 IM 保管 |
| 按 token 计的预算 | 只能依赖 Agent 上报 | 除非模型调用也经过 IM 托管的网关 |
| Agent 绕开 IM 直连外部系统 | 不能 | 企业应通过网络策略禁止，并且只把凭据交给工具网关 |

产品文案必须区分"强制"和"协作"两类能力，不能让企业误以为没经过网关的工具也有审批兜底。

## 3. 读取范围与告知

- `trigger` 模式：群聊默认 `mention`（只收到 @ 它的消息、回复它的消息，以及它自己的消息），私聊默认 `all`。思路与 Telegram bot 的隐私模式相同。
- Agent 只能读到加入以后（`join_seq` 之后）的事件。群管理员可以单独授予"加入前的历史"🔧。
- Agent 加入会话时产生全员可见的事件，事件里带所有者和读取范围，客户端必须展示。这满足 GDPR 的告知要求，也满足 EU AI Act 第 50 条的披露要求，见 [04](04-security-compliance.md) §4。
- 所有者经 Agent 观察会话时，只能看到 Agent 能读到的范围；观察动作写入审计。

## 4. 流式消息（已实现）

```
stream_start ──▶ streaming（分配 conv_seq，事件 msg.created）
   │  stream_append × N：不占 seq，按 (msg_id, idx) 幂等；重复的 idx 忽略，跳号拒绝
   │  60ms 合并推送，只推给正在看这个会话的人；进入会话时先收到当前快照
   │  每秒写一次检查点
   ├─ stream_end ──────────▶ complete
   ├─ stream_cancel ───────▶ cancelled（发送者、所有者，或任何人类成员点"停止"）
   ├─ 流式过程中命中 DLP ──▶ cancelled，内容替换为"已被策略移除"
   ├─ 接管 ────────────────▶ cancelled(taken_over)
   └─ 看门狗：Agent 断开或 30 秒没有新分块 ──▶ failed(disconnected | timeout)
```

上限：单条 256KB、最长 10 分钟；每个 Agent 在每个会话内最多 2 路并发流。

持久性分两档：已结束的流式消息与普通消息同等，ACK 后不丢；生成中的增量是尽力送达，崩溃时最多丢失最后一个检查点之后的内容（≤ 1 秒）。

## 5. 人工介入（已实现）

| 方式 | 实现 |
|---|---|
| 观察 | 所有者经 Agent 只读订阅；写审计 |
| 耳语 | 侧信道事件，`audience = [Agent, 发起人]` |
| 审批 | 草稿放在侧信道，不占 seq；批准后才写入主日志并分配 seq |
| 打断 | `stream_cancel`；Agent 收到 `stream_cancelled` |
| 接管 | 接管锁存在数据库里；接管期间 Agent 发送会被拒绝（`taken_over`）；全员可见 `agent.state` 事件 |
| 撤回 / 修订 | 发送者或 Agent 的所有者可以操作；写审计 |

## 6. 审批 v2（待确认）

v1 只支持"所有者审批全部草稿"。企业要用得顺手，至少需要下面这些能力。

### 6.1 业内参考

- Zendesk Copilot：每条 AI 回复都要人工批准，属于"辅助"模式。
- Intercom Fin：自主回答，解决不了就转人工并附上上下文。
- MCP 工具审批网关（TrueFoundry 等）：拦截匹配的工具调用，生成审批请求，通知审批人。审批的作用范围包括请求方、MCP 服务器、工具和有效期。它们公开承认的不足是：**审批没有和参数绑定**，批准之后参数还可能被改掉。
- MCP 规范建议应用始终保留"人可以拒绝工具调用"的能力，但没有规定审批流程，留给实现方。

### 6.2 方案

**(1) 按规则决定是否需要审批**，而不是全有或全无。每个 Agent 一套策略，会话级可以覆盖：

```
approval_policy:
  mode: off | all | rules
  rules:                                  # 从上到下匹配，第一条命中的生效
    - when: tool.risk == "high"           -> require(approvers: owner, sla: 15m)
    - when: dlp.hit                       -> require(approvers: owner)   # 不直接拦截，转人工
    - when: action.refund.amount > 100    -> require(approvers: group:finance)
    - when: inbound.trust == "low"        -> require
    - when: first_reply_to_new_customer   -> require
    - otherwise                           -> auto
```

Agent 可以随消息附带结构化的动作（例如 `{"action":"refund","amount":120}`），规则按结构化字段判断，而不是靠猜文本。

**(2) 审批人**：所有者，以及所有者指定的代理审批人（个人或群组）。企业版另有多级审批，按风险路由到审批组。

**(3) 审批收件箱**：一个跨会话的统一队列。每个待办都附带上下文（最近的对话内容、被标记的原因、命中的规则），审批人可以：

- 批准（可以先修改内容，修改前后的差异会保留）；
- 拒绝（必须填写原因，原因会回传给 Agent）；
- 批量批准；
- 用快捷键操作：A 批准、E 编辑、R 拒绝、J/K 切换上一条/下一条。

**(4) 生命周期**

```
pending ──▶ approved（可能已修改）──▶ 写入主日志，分配 seq
        ├─▶ rejected（附原因）
        ├─▶ expired（默认 24 小时；可配置为自动升级给下一级审批人）
        └─▶ superseded（Agent 在审批前提交了新版本）
```

- 批准操作是原子的条件更新。两个审批人同时操作时，先到的生效，后到的会看到"已被 X 处理"。
- Agent 会收到决定事件（包括修改后的内容和拒绝原因），可以据此调整后续行为。

**(5) 客户侧体验**：草稿等待审批期间，客户看到"正在处理"状态，看不到草稿内容。可以配置是否显示。

**(6) 绑定**：审批结果绑定到内容哈希（工具调用则绑定到参数哈希）。批准之后再做任何修改，都会使这次批准失效。这正好补上了上面提到的"审批没有和参数绑定"的问题。

**(7) 度量**：审批延迟、批准率、修改率、拒绝原因分布、超时率。企业可以用这些数据逐步调整规则，把低风险的场景放开为自动发送。

## 7. 工具网关（待确认）

目标：Agent 接入 IM 之后，它调用的工具也走 IM。IM 统一负责授权、审批、审计和凭据保管，这样工具权限就从"协作"变成了"强制"。

### 7.1 结构

```
Agent ──tool_call{tool, args, call_id, conv_id?, on_behalf_of?}──▶ IM 工具网关
          1. 身份：Agent API Key / OAuth client credentials（与 MCP 2025-11-25 授权规范一致）
          2. 授权：Agent 是否被授予这个工具；委托时取 Agent 权限 ∩ 用户权限
          3. 校验：参数必须符合工具的 JSON Schema
          4. 参数级规则：例如 amount ≤ 100 自动放行，超过则需要审批
          5. 审批：复用 §6，审批绑定到参数哈希
          6. 限流与预算
          7. 执行：IM 用自己保管的凭据调用工具提供方；Agent 永远拿不到凭据
          8. 记录：tool_call / tool_result 事件（按策略放主日志或侧信道）+ 审计 + 指标
       ◀──tool_result{call_id, result, trust: low}──
```

### 7.2 工具从哪里来

| 来源 | 阶段 |
|---|---|
| WebSocket 工具提供方（作为一种特殊客户端接入 IM） | v0.3 |
| HTTP Webhook 工具 | v0.3 |
| 上游 MCP 服务器（Streamable HTTP） | v0.4 |
| IM 对 Agent 暴露 MCP 服务端：Agent 用标准 MCP 客户端即可调用全部工具 | v0.4 |

### 7.3 工具注册信息

名称、描述、参数 JSON Schema、风险级别（low / medium / high）、所属提供方、需要的权限范围、是否产生外部副作用、默认审批策略。

### 7.4 安全

- 工具返回的结果统一标为低信任：OWASP LLM Top 10（2026 版）把检索文档、记忆和工具返回都列为攻击面（Hidden Context Exposure）。
- 给每个 Agent 授最小权限（least agency）。
- 所有调用写审计，包括参数哈希、审批人、耗时和结果状态。

## 8. 过滤与护栏（已实现）

| 检查点 | 位置 | 对纯人类会话的影响 |
|---|---|---|
| 进入 AI 之前（注入检测，标记低信任） | 投递给 Agent 的路径上 | 无 |
| AI 输出之后（DLP：卡号、密钥） | Agent 的发送路径上，提交之前 | 无 |
| 流式过程中 | 按块检查累积内容 | 无 |

| 护栏 | 规则 | 触发后 |
|---|---|---|
| 跳数上限 | `hop > 6` 拒绝。hop 由服务端计算：人发的消息为 0，Agent 回复第 n 跳的消息记为 n+1 | 熔断，全员可见事件，通知所有者 |
| 重复检测 | 同一 Agent 在同一会话内重复相同内容 ≥ 3 次 | 熔断，冷却 60 秒 |
| 速率 | 每个 Agent、每个会话一个令牌桶 | `rate_limited` |
| 预算 | 每个 Agent 每日的消息数和字符数上限 | `budget_exceeded` |

已知限制：Agent 之间如果通过 IM 以外的渠道形成循环，IM 无法感知。预算目前存在内存里，重启后清零🔧。
