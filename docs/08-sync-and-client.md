# 08 同步协议与客户端可靠性

> 服务端（§1–§2）已实现；客户端（§3–§5）由所有平台共用的 Rust 核心 `sdk/client-rust/core` 实现（A7，2026-10-24，[12 §2](12-developer-experience.md)），各语言封装见 12 §2.14。

目标：客户端（人和 Agent）**只同步、不随意读历史**；每条消息每台设备只下发一次；任何异常（断网、崩溃、重装、并发、伪造）下都**不丢、不重、不乱序、不越权**，也不会把服务端拉垮。按 seq 读历史只留给开放 API。

## 1. 协议和代码位置

协议：`sync {limit?}`、`ack {acks: [{conv_id, seq, side_seq}]}`、`heads {conv_ids}`（位置校验）、`unread`、`set_mute {conv_id, mode, until?}`、`set_prefs {read_silences_others?}`、`observe {conv_id, agent_id, after_seq?, limit?}`；客户端的 `pull`、`pull_side` 返回 `bad_request`。

代码：`hub/sync.rs`（协议、起点规则）、`registry.rs`（`in_order`、`sync_begin`，§2.2）、`db.rs`（`ack_cursor`、`purge_before`，§2.1、§2.5）、`logic.rs`（`add_member`、移出，§2.3–§2.4）、`hub.rs`（`user_bucket`）、`open_api.rs`（按 seq 读历史）。表 `device_cursors (device_id, conv_id, user_id, acked_seq, acked_side_seq, told_state)`；控制库表 `departures`、`past_members`。

**还没做**：会话按"最近活跃"排序下发（现在按成员关系的顺序，一次调用最多 `limit` 条，没发完的下次继续）；保留期对被举报内容的例外（随合规功能）；按组织单元覆盖同步配置。

## 2. 服务端：按设备记同步位置

### 2.1 同步位置存在服务端，客户端不能伪造

- 每台设备（人的设备由 App 连接时用 `device=` 选定，Agent 的每把密钥一台，[13 §4.2](13-roles-and-entry-points.md)）对每个会话有一条记录：`(device_id, conv_id, acked_seq, acked_side_seq)`。
- 客户端**不提交"从哪个 seq 开始"**，只说"同步"；服务端从这台设备的 `acked_seq` 往后发。
- 客户端只能**确认**（`ack`），服务端检查：
  - 不能确认还没发给它的 seq（超过本连接**送达过**的最远位置 → `bad_request`；推送队列满丢掉一条只让下一次同步重发，不会让合法的确认失败）；
  - 不能往回退（小于已确认的位置 → 忽略，确认只前进）。
- 所以伪造只能让自己少收消息，不能让服务端重复发送或发送全量。

### 2.2 一条下发通道

追赶和实时是同一条通道。设备的连接只按顺序收实时推送（seq 正好接上已下发的位置）：第一次 `sync` 之前、接不上的、以及某个会话正在被 `sync` 读取期间到达的推送都不发，改发 `resync`（立即发出，不等下一帧），由下一次 `sync` 补齐。所以同一事件不会既被推送又出现在同步结果里，也不会因推送和补拉交错而乱序。

- **分批**：每批每个会话最多 `sync.batch_size` 条（默认 200），每个会话未确认的事件不超过 `sync.max_unacked`（默认 1000），客户端确认后才发下一批。
- **限流**：`sync`、信号、人的发送都按**用户**算（所有连接合计）；Agent 的同步更严；超出返回 `rate_limited`。
- **侧信道**：耳语、草稿、仅某人可见同样按 `acked_side_seq` 下发，按页读（每次查询 500 条、每个会话每轮最多扫 5000 条），没读完 `has_more` 为真。
- **自己发的消息**：`msg.created` 只对发送者带它自己的 `client_msg_id`（推送、同步、读取都一样），客户端据此合并"发出的"和"同步回来的"。
- **先发哪些会话**（计划）：先发最近有活动的会话；会话列表（标题、未读数、最后一条摘要）先下发，界面不用等全部同步完。

**历史也走这条通道**：新设备、新成员要拿的历史，就是把起始位置往前设，然后由同一条通道按顺序下发、同样确认。只有一套顺序、确认、去重、权限逻辑；代价是新设备第一次同步要等历史下完才追上最新。

### 2.3 权限

- 只下发**当前令牌所属用户现在是成员**的会话；不能指定会话 ID 去拉别人的会话。
- 被移出、退出：这台设备同步到移出事件为止，`left` 报告到设备的位置越过移出事件为止，之后什么都不再下发；重新加入时清除。
- 解散：对每台设备只报告一次 `dissolved: true`（控制库里记下这台设备已知道）。
- 被移出又拉回、设备落在移出前：先补发移出前那段，再从新的可见起点继续，中间那段不发（D92）。
- 设备被下线（令牌吊销）：这台设备的同步位置全部删除。
- 开放 API 保留按 seq 读历史，需要 `messages:read`，写审计，受限流。

### 2.4 能看到多少历史

都在服务端配置文件里设置，不能超过服务端的保留期，也有硬上限（窗口最多 90 天）：

```toml
[sync]
batch_size = 200          # 每个会话每批最多多少条
max_unacked = 1000        # 每个会话未确认的事件上限（流量控制）
max_gap = 10000           # 落后超过这么多条就重置
device_ttl_days = 30      # 多久没确认的设备按新设备处理
window_days = 90          # 新设备只同步最近多少天，上限 90
max_messages = 30         # 新设备每个会话先同步最近多少条（窗口内，后端可改）；更早的用户往上翻时按页取（§2.8）
older_enabled = false     # 窗口内没有消息的会话是否也同步一些更早的消息
older_messages = 20       # 同步多少条（默认）
older_max = 100           # 上限
member_messages = 30      # 新成员（人）默认带最近多少条（不能超过 max_messages）
member_days = 30          # 且在最近多少天内
share_max = 200           # 拉人时最多能选带多少条
rate_per_second = 10      # 每个用户每秒 sync 次数（令牌桶），burst = 20
agent_rate_per_second = 2 # Agent 更严，agent_burst = 5

[retention]
days = 180                # 0 表示永久保留
```

| 场景 | 规则 |
|---|---|
| 设备在会话里没有位置 | 设备存在之后加入的会话从可见起点开始；否则按新设备窗口 |
| 新设备、重装、清空本地数据、本地被浏览器清掉 | 先下发会话列表（标题、未读数、@ 我、最后一条），再按最近活动先后，每个会话同步最近 `window_days` 天内的最近 `max_messages` 条（默认 30）；用户往上翻时再按页向服务端要（§2.8）；未读多于 30 条时，界面可以用 `first_unread` 直接跳到第一条未读；窗口内没有消息时，`older_enabled` 打开就同步最近 `older_messages` 条，关闭就只显示会话本身 |
| 落后太多 | 位置落后于保留期或超过 `max_gap`：重置到新设备规则，响应里带 `reset.from_seq`；比位置有效期还老的设备在某个会话没有位置、按窗口起步又跳过了事件时也报 `reset` |
| 新成员（人）加入群 | 默认带最近 `member_messages` 条（`member_days` 天内）；拉人时可以单独选（`history`，0 表示不带，不能超过 `share_max`）；创建会话时的成员从第一条开始可见 |
| Agent | 默认不带历史，见 [03 §7](03-agents.md) |

- 加入时把"可见的最早 seq"记在成员记录上：之后改设置不影响已经在群里的人；退出再加入按新设置重新算。
- 新设备只同步最近一段；更早的由客户端按页向服务端要（§2.8，D108）。
- 拉人事件里写明带了多少历史，所有成员都看得到。
- 单聊加人变成群聊时：不改原来的单聊，新建一个群，避免单聊内容被新加的人看到。

### 2.5 保留期

- 服务端的事件按 `retention.days` 保留（默认 180 天，0 表示永久）。每个会话只删日志的**前缀**（按 seq，系统时钟回拨也不会删出空洞），每轮最多 2 万条，衍生数据一起删：消息、侧信道、摘要、反馈、卡片回答、认领、已决定的草稿和请求、过期的 Webhook 发件箱。
- 设备离线超过保留期：起始位置跳到最早还保留的事件（`reset`），客户端在这里显示"更早的消息已不可同步"。
- 长期不在线的设备：一台设备在这个库里**全部**位置都超过 `device_ttl_days` 没确认才一起删除（安静的会话不会被单独删掉），下次连接按新设备处理。
- 开放 API 的历史查询同样只能查到保留期内的内容。
- 计划：被举报、正在审核（DSA）的内容延后删除；审计日志单独设置保留期。

### 2.6 已读和通知

- 事件帧带 `notify`。用户设置 `read_silences_others`（默认开）：消息仍然同步到所有设备，但如果下发时它已经被读过，**不增加未读数、不提醒**；已经弹出的通知在收到已读事件时撤掉。
- 自己发言把自己的已读推进到这条（D93）。
- 未读数：服务端按已读位置计算每个会话的未读数和 @ 我的数量。
- **免打扰**：`none / all / mentions`，可设到期时间，存在服务端，同步到用户的其他设备（`mute` 帧）。免打扰的会话照常接收、照常算未读，只是不提醒、不发手机推送。
- 推送队列满丢掉的 `read` / `mute` 帧会让这个会话欠一次 `resync`；`sync` 的会话条目带 `read_seq` 和 `mute`（只在这台设备还没确认收到过时带，确认时记在 `device_cursors.told_state`）。

### 2.7 Agent

Agent 和人走同一条同步通道，但收到什么、能不能读历史、历史和状态放在哪里都和人不同，见 [09 Agent 通信与 Agent 历史](03-agents.md)。

### 2.8 往回翻历史（D108，✅ 2026-10-21）

人（客户端）能按页读自己能看到的历史：新设备、本地被清掉、缓存被淘汰后都能往回翻、跳到某条消息。参照 Zulip（锚点 + 前后各多少条，一个接口覆盖往回翻、往后翻、跳到某条、跳到第一条未读）、Discord（前后各最多 100 条）、Matrix（可见范围在加入时定下、之后改设置不追溯；明确告诉客户端"到头了"）。

**请求** `history {conv_id, anchor?, before?, after?}`：
- `anchor`：一个 seq，或 `"newest"`（默认）、`"first_unread"`（自己的已读位置）。`before` 是 seq **不大于** `anchor` 的最多几条（含锚点那条），`after` 是**大于** `anchor` 的最多几条；各 0–`page_max`（默认 `before = 50, after = 0`），两个都是 0 是 `bad_request`。锚点可以不是某条消息的 seq（比如一个成员事件），也可以超出范围。
- 返回 `{conv_id, messages, has_before, has_after, before_end?}`：消息按 seq 升序，是**当前状态**（编辑过的是新内容和新版本号，撤回的只剩撤回标记，流式中的带已生成的部分）；`before_end` 在 `has_before` 为 false 时说明为什么前面没有了：`start`（会话开头）、`visible_from`（这个成员的可见起点）、`retention`（保留期删掉了）、`disabled`（开关关了）。
- Agent 继续用自己的形式（`after_seq` / `before_seq` / `limit`，[03 §7.1](03-agents.md)，写审计）；人用 Agent 的参数、Agent 用人的参数都是 `bad_request`。

**规则**：
- 只能读**现在是成员**的会话（否则 `forbidden`，未知会话 `not_found`），和同步同一套权限检查（§2.3）。
- 只返回 seq ≥ 成员的可见起点（§2.4，加入时定下，之后改设置不追溯）、在保留期内的；被移出又拉回时，以前那段成员期照样返回，中间那段不返回（D92）。比可见起点早的消息后来被编辑也不返回。
- 侧信道（耳语、草稿、仅某人可见）不在这里返回，仍走同步。
- 不改变设备的同步位置，不确认任何东西；客户端把它当成本地缓存的补充（[12 §2.8](12-developer-experience.md)）。
- 集群和多库：按会话路由，和其他会话操作一样；读从库时同样不越过 `confirmed_seq`（C3 的读取水位线）。
- 限流：按用户的令牌桶（所有连接合计），超出 `rate_limited` 并带 `retry_after_ms`。
- 不写审计（成员读自己的会话，业内都不记）；开放 API 的历史读取照旧写审计。拒绝的请求不留痕迹。

**配置**：

```toml
[history]
enabled = true            # 人能否向服务端往回翻；关掉时返回空页和 before_end = "disabled"（成员检查照旧）
page_max = 100            # before / after 的上限（1–1000）
rate_per_second = 5       # 每个用户（所有连接合计）
burst = 20
```

按会话类型或按会话的开关先不做（D108）。

### 2.9 连接保活和重连提示（✅ 2026-10-21）

客户端的重连和发送策略（[12 §2.4–§2.5](12-developer-experience.md)）需要服务端配合：
- **应用层心跳**：`ping {}` → `res {t}`（服务端时间，毫秒）。浏览器的脚本看不到 WebSocket 协议层的 ping，只能靠它判断连接是否还活着。被急停的 Agent 也能 `ping`。欢迎帧带 `heartbeat_ms`（25000，且不超过 `idle_ms` 的三分之一）和 `idle_ms`（服务端多久没收到任何帧就断开，`clients.idle_secs`，默认 90 秒）。
- **节点下线带等待时间**：节点要下线时（`server_restart`），先发一帧 `{"type": "goaway", "reason": "server_restart", "retry_after_ms": 0–5000 的随机值}`，再用 1012 / `server_restart` 关闭。用单独一帧而不是把时间塞进关闭原因，旧客户端照样按关闭原因处理（HTTP/2 的 GOAWAY、Discord 的 reconnect 也是先发一条通知）。`logged_out`、`client_too_old` 表示不要重连。
- **握手被拒**：令牌无效 401（客户端换令牌重试一次）；这个人被停用或已删除 403（不再重试）；限流 429、存储忙 503，都带 `Retry-After`（秒）和 `retry_after_ms`。
- **请求级的暂时性错误**：`rate_limited`（按令牌桶算出的等待时间）、`overloaded`（写队列满，500–2000 毫秒的随机值）带 `retry_after_ms`。

## 3. 客户端 SDK 的状态和接口

> 实现：Rust 核心（`sdk/client-rust/core`）。它把下面的记录写进本地库：原生平台用 SQLite（`cache.db`，队列单独放 `queue.db`），浏览器用 IndexedDB（加密）。缓存和队列的规则见 [12 §2.7–§2.9](12-developer-experience.md)。还没做：§3.2 的单独未读接口，未读数现在随会话列表给出；§4.5 的"协议操作和 SDK 函数一一对应"的 CI 检查，现在用 `call` 调任意操作。

### 3.1 本地记录

| 记录 | 作用 |
|---|---|
| 消息表 `(conv_id, seq)` | 已同步、已确认的事件，按日志重放后的状态 |
| 待发送队列 | `client_msg_id`、会话、内容、状态、重试次数、下次重试时间、创建时间 |
| 会话表 | 标题、成员、未读数、@ 数、本地已同步到的 seq、"更早的消息不可同步"标记 |
| 已读位置 | 自己的已读 seq（乐观更新，服务端确认后为准） |

### 3.2 未读接口

`unread_total()`、`unread(conv)`、`mentions(conv)`，以及变化事件 `UnreadChanged{conv, unread, mentions, total}`；`mark_read(conv, seq)` 乐观更新、服务端确认、其他设备同步。

## 4. 异常场景

原则：**先写本地、再发网络；先存好、再确认；所有重试都幂等；状态只往前走；失败要告诉用户具体原因。**

**什么时候算失败**：只有服务端按业务规则拒绝才失败；断网、服务端故障时一直按重试策略重试，不会因为时间到了失败（D113，替代 D34 的 2 分钟，[12 §2.5、§2.7](12-developer-experience.md)）。失败由用户点重试或删除。SDK 提供失败消息数（全部、按会话）和变化事件。

### 4.1 发送

| # | 场景 | 处理 |
|---|---|---|
| S1 | 点了发送，应用在写入本地队列之前崩溃 | 这条消息不存在；`send()` 在写入本地队列之后才返回，界面才显示 |
| S2 | 已写入队列，发出前断网 | 状态 `pending`，连上后自动发 |
| S3 | 发出了，服务端已提交，但确认在路上丢了 | 超时后用**同一个 `client_msg_id`** 重发，服务端去重，返回同一个 seq |
| S4 | S3 之后应用被杀，重启 | 队列在本地持久化，重启后继续自动重发。手动重试仍用原来的 `client_msg_id`：服务端去重保留 7 天，超过 7 天的失败消息重试时生成新 ID |
| S5 | 同一会话连发多条，第一条暂时失败（网络） | 同一会话**严格按顺序**：前一条没成功，后面的不发 |
| S6 | 同一会话连发多条，第一条被业务拒绝 | 第一条标记失败（不重试），后面的照常发 |
| S7 | 不同会话都有待发送 | 会话之间并行，同时进行的数量有上限 |
| S8 | 断网恢复后大量重发 | 指数退避加随机抖动 |
| S9 | `rate_limited` | 按服务端给的时间等待，不算失败次数 |
| S10 | 令牌过期 | 调用取令牌回调换新令牌后重发；换不到则保持 `pending`，连接状态显示"需要重新登录" |
| S11 | 等待发送期间被移出会话、会话被解散 | 服务端返回 `forbidden` / `not_found`，标记失败，不重试 |
| S12 | 很久都发不出去（一直断网、服务端一直故障） | 一直重试（降频），显示"等待网络"，不悄悄丢弃；用户可以取消 |
| S13 | 发送确认还没到，同步通道先把这条消息下发了 | 按 `client_msg_id` 合并成一条 |
| S14 | 用户连点两次发送 | 一次输入只生成一个 `client_msg_id` |
| S15 | 编辑、撤回一条还没发出的消息 | 编辑：直接改队列里的内容；撤回：从队列取消。已经发出、还没收到确认：等确认后再执行 |
| S16 | 退出登录时还有没发出的消息 | 先告诉应用有几条没发出，由应用决定等待还是放弃；清除数据会删掉队列 |
| S17 / S18 | 两台设备同时在同一会话发消息；设备时间不准 | 顺序只看服务端 seq，所有设备最终看到同样的顺序 |

### 4.2 接收和同步

| # | 场景 | 处理 |
|---|---|---|
| R1 | 收到一批，存进本地之前应用退出 | 没确认，下次从已确认位置重发 |
| R2 / R3 | 已存进本地，确认发出前应用退出；或确认在路上丢了 | 下次会重复收到，按 `(会话, seq)` 幂等写入 |
| R4 | 手机推送通知到了，应用还没同步就被关掉 | 推送只负责提醒；内容以同步为准，同步完成前显示为"同步中" |
| R5 | 网络切换、重连 | 同一条通道从已确认位置继续；SDK 按 seq 排好再交给应用 |
| R6 | 本地磁盘满、写入失败 | **不确认**，停止同步并报存储错误；空间恢复后继续 |
| R7 | 本地库损坏 | 删除重建；按新设备规则同步，并告诉应用本地历史已丢失。待发送队列和草稿单独保存，尽量保留 |
| R8 | 离线很久，积压很多 | 分批同步，显示进度；超过保留期的部分显示"更早的消息已不可同步" |
| R9 | 离线期间被移出会话 | 同步到移出事件为止；本地会话变为只读（保留还是删除由应用设置） |
| R10 | 离线期间别人编辑、撤回了旧消息 | 编辑、撤回是新的事件，同步后更新本地；本地没有原消息时只记一个占位 |
| R11 | 流式回复进行中断线 | 增量不落盘；重连后同步到这条消息的最新状态，继续接收增量 |
| R12 | 浏览器开了多个标签页 | 同一个浏览器是一台设备，只有一个标签页负责同步和写库，其他标签页通过广播拿数据；负责的标签页关掉后自动换一个 |
| R13 | 第二个进程（如 iOS 通知扩展）同时访问本地库 | 库内租约锁，同一时间只有一个进程写 |
| R14 | 服务端要求重新同步（`resync`、`reset`） | 按服务端给的新起始位置继续，本地已有的记录保留 |
| R15 | 另一台设备已读 | 收到已读事件：更新未读数、撤掉已弹出的通知 |

### 4.3 离线期间状态变了

连上后发送被拒绝时：**服务端返回明确的错误码和原因，SDK 转成应用能直接显示的原因，标记失败、不自动重试**；同步通道同时下发造成变化的事件（例如"你被移出群"）。

| # | 离线期间发生了什么 | 服务端返回 | SDK 给应用的失败原因 |
|---|---|---|---|
| C1 | 被群主或管理员移出群 | `forbidden` | 你已不在该群 |
| C2 | 群被解散 | `not_found` | 群已解散 |
| C3 | 自己在另一台设备上退出了群 | `forbidden` | 你已退出该群 |
| C4 | 单聊对方拉黑了你 / 你在另一台设备拉黑了对方 | `blocked` | 对方拒收 / 你已拉黑对方 |
| C5 | 单聊对方账号被停用或删除 | `not_found` / `forbidden` | 对方账号不存在或已停用 |
| C6 | 自己的账号被停用 | 连接被拒（令牌失效） | 账号已停用；队列保留，不再发送 |
| C7 | 这台设备被下线、改密码导致其他设备下线 | 连接被拒 | 需要重新登录；队列保留，重新登录后由用户决定是否继续发 |
| C8 | 回复的那条消息被撤回了 | `not_found` | 回复的消息已被撤回；可选择不带引用重发 |
| C9 | @ 的人已经不在群里 | 正常发送，@ 不生效 | 发送成功；提示"某人不在群中，未提醒到" |
| C10 | 要编辑或撤回的消息已被撤回 / 超过可编辑时间 | `not_found` / `conflict` | 消息已被撤回 / 已超过可编辑时间 |
| C11 | 自己的 Agent 被设置为需要审批 | 成功，但变成草稿 | 等待批准（不是失败） |
| C12 | 会话被接管（Agent 发送时） | `conflict` | 会话已被人工接管 |
| C13 | 触发护栏（跳数、重复、预算、熔断） | `rate_limited` / `conflict` / `policy_blocked` | 发送过于频繁 / 已达到今日额度 / 已暂停 |
| C14 | 内容被 DLP 或发送前拦截拒绝 | `policy_blocked` | 内容不符合规定（不重试） |
| C15 | 会话正在迁移到另一个库 | `conv_migrating` | 不算失败，在窗口内自动稍后重试 |
| C16 | 服务端要求更新客户端 | `client_too_old` | 需要更新应用；队列保留 |
| C17 | 被移出后又被重新拉回群 | 成功 | 正常发送（按服务端当时的状态判断） |
| C18 | 群设置改成只有管理员能发言（以后的功能） | `forbidden` | 当前只有管理员可以发言 |

错误码按业务含义统一；同一个错误码下更具体的原因（例如 `forbidden` 区分"不在群里"和"只有管理员能发言"）由服务端在错误详情里给出，SDK 不靠猜。

### 4.5 SDK 覆盖所有业务

- 服务端的每一个业务操作，SDK 都有对应的函数；每一个错误码和原因，SDK 都有对应的类型。
- 一份清单把"客户端协议的全部操作"和"SDK 函数"对应起来，**CI 检查两边一致**：服务端加了新操作而 SDK 没有，构建失败。
- 每个函数写明会返回哪些失败原因，§4.1–4.3 的场景逐个有测试。

## 5. 怎么证明 SDK 做对了

SDK 测试工具包（[05 §6.6](05-operations.md)）里做**随机故障测试**：

- 用进程内服务端，随机注入：断网、丢推送、丢确认、重复推送、打乱顺序、应用在任意一步被杀（含写库到一半）、磁盘满、令牌过期、被移出会话、并发发送。
- 每轮几千次操作后检查不变量：
  1. 每条 `send()` 返回过的消息，最终要么在服务端恰好出现一次，要么在本地标记为失败；
  2. 本地消息表按 seq 重放的结果和服务端日志（在可见范围内）完全一致；
  3. 同一会话里同一个发送者的消息顺序和发送顺序一致；
  4. 没有越权：本地不出现不属于自己的会话的内容；
  5. 服务端收到的同步请求不超过限流。
- 实现：`sdk/client-rust/core/tests/simulate.rs`，用进程内的假服务端和假存储（CI 每次 1000 个随机种子，失败时打印种子）。注入断网、丢推送、丢答复、重启和存储故障，并随机组合用户操作。检查不变量 1–3，以及"确认过的不丢、队列最终清空或明确失败"。不变量 4、5 由服务端测试保证（[05 §5](05-operations.md)）。各语言封装共用这个核心，只另外跑对着真实服务端的一致性场景（[12 §2.14](12-developer-experience.md)）。"故意改坏"验证：先确认后存储、不按顺序放事件，测试都会失败。
