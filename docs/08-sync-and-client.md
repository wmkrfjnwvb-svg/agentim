# 08 同步协议与客户端可靠性

**状态**：服务端部分（§2）已实现（L1，2026-10-11），客户端协议的按 seq 拉取已停用；客户端 SDK 部分（§3–§5）随 M7 实现。

目标：客户端（人和 Agent）**只同步、不随意读历史**；每条消息每台设备只下发一次；任何异常（断网、崩溃、重装、并发、伪造）下都**不丢、不重、不乱序、不越权**，也不会把服务端拉垮。

本文件取代 [05 §6.2](05-operations.md) 里"和服务端对齐""待发送队列"两段的旧设计（旧设计允许客户端按 seq 任意补拉）。业内做法见 §6，调研详情见 [research/sdk-and-ai-2026.md §4](research/sdk-and-ai-2026.md)。

**你已经定下的（2026-10-11）**：客户端和 Agent 都只同步、不随意读历史；开放 API 给开发者保留历史查询；服务端日志保留几个月且可设置；同步位置不能被伪造，每批条数可配置（默认几百条，多轮拉取）；任何一台设备已读，其他设备只同步、不提醒（用户可设置）；SDK 提供未读接口；新成员可看最近多少条或最近多少天（可设置）；只能拉自己所在会话；重装可以没有历史，也可以设置同步最近多少条或多少天。

## 2. 服务端：按设备记同步位置

### 2.1 同步位置存在服务端，客户端不能伪造

- 每台设备（M3 已有设备表，令牌属于某台设备）对每个会话有一条记录：`(device_id, conv_id, acked_seq, acked_side_seq)`。
- 客户端**不再提交"从哪个 seq 开始"**，只说"同步"；服务端从这台设备的 `acked_seq` 往后发。
- 客户端只能**确认**（`ack(conv, seq)`），服务端检查：
  - 不能确认还没发给它的 seq（超过本连接**送达过**的最远位置 → `bad_request`；推送队列满丢掉一条只让下一次同步重发，不会让合法的确认失败，M7）；
  - 不能往回退（小于已确认的位置 → 忽略）。
- 所以伪造只能让自己少收消息，不能让服务端重复发送或发送全量。

### 2.2 一条下发通道

连接后，服务端为这台设备按会话依次下发"已确认位置之后"的事件；追上之后，新事件直接实时下发。追赶和实时是同一条通道，不会出现"推送和补拉交错导致乱序"。

- **分批**：每批每个会话最多 `sync.batch_size` 条（默认 200，可配置），客户端确认后才发下一批（流量控制：每台设备未确认的事件不超过 `sync.max_unacked`，默认 1000）。
- **轮数限流**：每台设备每秒的批数有上限（D38），Agent 更严。
- **先发哪些会话**：先发最近有活动的会话；会话列表（标题、未读数、最后一条摘要）单独、先下发，界面不用等全部同步完。
- **耳语、草稿、仅某人可见**：侧信道同样按 `acked_side_seq` 下发。

**历史走不走单独的通道**：**只有一条通道**（已实现）。新设备、新成员要拿的历史，就是把这台设备的起始位置往前设，然后由同一条通道按顺序下发、同样确认。好处：只有一套顺序、确认、去重、权限逻辑，不会出现"历史和新消息交错导致乱序、重复或漏掉"，出了问题也好查。代价是新设备第一次同步要等历史下完才追上最新（按"最近活跃的会话先同步"缓解）。单独通道（例如分页读历史的接口）只留给开放 API。

### 2.3 权限

- 只下发**当前令牌所属用户现在是成员**的会话；不能指定会话 ID 去拉别人的会话。
- 被移出、退出、会话解散：这台设备会收到截止到移出事件为止的内容，然后这个会话的同步记录删除，之后什么都不再下发。
- 设备被下线（令牌吊销）：这台设备的同步记录全部删除。
- 开放 API（开发者后端，服务端对服务端）保留按 seq 读历史，需要 `messages:read` 权限，写审计，受限流。

### 2.4 能看到多少历史

**都在服务端配置文件里设置**（可按组织单元覆盖），不能超过服务端的保留期，也有硬上限：

```toml
[sync]
batch_size = 200          # 每个会话每批最多多少条
max_unacked = 1000        # 每台设备未确认的事件上限（流量控制）
max_gap = 10000           # 落后超过这么多条就重置
device_ttl_days = 30      # 多久没确认的设备按新设备处理
window_days = 90          # 新设备只同步最近多少天，上限 90 天（太久没有意义）
max_messages = 200        # 新设备每个会话最多同步多少条（窗口内）
# 窗口内没有任何消息的会话（很久没聊）：
older_enabled = false     # 是否也同步一些更早的消息
older_messages = 20       # 同步多少条（默认）
older_max = 100           # 上限
member_messages = 50      # 新成员（人）默认带最近多少条
member_days = 30          # 且在最近多少天内
share_max = 200           # 拉人时最多能选带多少条
rate_per_second = 10      # 每个连接每秒 sync 次数（令牌桶），burst = 20
agent_rate_per_second = 2 # Agent 更严，agent_burst = 5

[retention]
days = 180                # 0 表示永久保留
```

| 场景 | 规则 |
|---|---|
| 新设备、重装、清空本地数据 | 每个会话：最近 `window_days` 天内的消息，最多 `max_messages` 条；如果这个会话在窗口内没有消息，`older_enabled` 打开时同步最近 `older_messages` 条（例如只有几条的老会话就整个同步过来），关闭时只显示会话本身，没有消息 |
| 新成员（人）加入群 | 默认带最近 `member_messages` 条（`member_days` 天内）；拉人时可以单独选择带多少条（`history`，0 表示不带，不能超过 `share_max`；参考 Teams、WhatsApp）；创建会话时的成员从第一条开始可见 |
| Agent | 见 [09 §6](09-agent-communication.md)：默认看不到加入前的历史，会话管理员可以授权 |

- 加入时把"可见的最早 seq"记在成员记录上（Telegram、Matrix 都是这样）：之后群主改设置，不影响已经在群里的人；退出再加入按新设置重新算。
- 拉人事件里写明带了多少历史，所有成员都看得到（WhatsApp、Slack 的做法）。
- 单聊加人变成群聊时：不改原来的单聊，新建一个群（Slack 的做法），避免单聊内容被新加的人看到。

### 2.5 保留期

- 服务端的事件按 `retention.days` 保留（建议默认 180 天，可按组织单元、按会话设置；Slack、Mattermost 默认永久保留，WhatsApp、Signal 投递后即删、未投递的最多 30 天）；过期的事件定期删除（随数据库删除，已加密的内容同时失去钥匙的部分见 [04 §2.6](04-security-compliance.md)）。
- 例外：被举报、正在审核（DSA）、法律保全的内容延后删除；审计日志单独设置保留期。
- 设备离线超过保留期：起始位置跳到最早还保留的事件，客户端在这个位置显示"更早的消息已不可同步"。
- 开放 API 的历史查询同样只能查到保留期内的内容。

### 2.6 已读和通知

- 用户设置"任何一台设备已读，其他设备不再提醒"（默认开启）：消息仍然同步到所有设备（本地要有完整记录），但如果下发时它已经被读过，标记为已读，**不增加未读数、不弹通知**；已经弹出的通知在收到已读事件时撤掉（手机推送阶段同样处理）。
- 未读数：服务端按已读位置计算每个会话的未读数和 @ 我的数量，随会话列表下发、变化时推送。
- **免打扰**（你的意见）：用户可以对某个会话设置免打扰（全部不提醒 / 只提醒 @ 我的 / 正常），可设置到期时间；设置存在服务端，多台设备同步。免打扰的会话照常接收、照常算未读，只是不弹通知、手机推送不发（参考 Slack、Telegram）。SDK 的消息事件里带上"是否需要提醒"，应用不用自己判断。

### 2.7 Agent

Agent 和人走同一条同步通道，但**收到什么、能不能读历史、历史和状态放在哪里**都和人不同，单独设计，见 [09 Agent 通信与 Agent 历史](09-agent-communication.md)。

## 3. 客户端 SDK 的状态和接口

### 3.1 本地记录

| 记录 | 作用 |
|---|---|
| 消息表 `(conv_id, seq)` | 已同步、已确认的事件，按日志重放后的状态 |
| 待发送队列 | `client_msg_id`、会话、内容、状态、重试次数、下次重试时间、创建时间 |
| 会话表 | 标题、成员、未读数、@ 数、本地已同步到的 seq、"更早的消息不可同步"标记 |
| 已读位置 | 自己的已读 seq（乐观更新，服务端确认后为准） |

### 3.2 未读接口（你的第 7 点）

`unread_total()`、`unread(conv)`、`mentions(conv)`，以及变化事件 `UnreadChanged{conv, unread, mentions, total}`；`mark_read(conv, seq)` 乐观更新、服务端确认、其他设备同步。

## 4. 异常场景（你的第 11 点）

原则：**先写本地、再发网络；先存好、再确认；所有重试都幂等；状态只往前走；失败要告诉用户具体原因。**

**自动重试只在短时间内进行**（你的意见）：发送失败后 SDK 自动重试的时间窗口默认 **2 分钟**（`send.auto_retry_window`，可配置）；超过后标记失败，界面显示红色感叹号，由用户点重试。SDK 提供失败消息数（全部、按会话）和变化事件，方便应用显示红点；以后 v3 做界面组件时直接用。

### 4.1 发送

| # | 场景 | 处理 |
|---|---|---|
| S1 | 点了发送，应用在写入本地队列之前崩溃 | 这条消息不存在；`send()` 在写入本地队列之后才返回，界面才显示，所以用户看不到"显示了又消失" |
| S2 | 已写入队列，发出前断网 | 状态 `pending`，连上后自动发 |
| S3 | 发出了，服务端已提交，但确认在路上丢了 | 超时后用**同一个 `client_msg_id`** 重发，服务端去重，返回同一个 seq；不会出现两条 |
| S4 | S3 之后应用被杀，重启 | 队列在本地持久化。重启时还在 2 分钟窗口内的继续自动重发（同样去重）；已经超过的标记失败，等用户点重试。用户手动重试仍用原来的 `client_msg_id`：服务端去重保留 7 天，7 天内重试不会产生两条；超过 7 天的失败消息重试时生成新 ID（界面上就是一条新消息） |
| S5 | 同一会话连发多条，第一条暂时失败（网络） | 同一会话**严格按顺序**：前一条没成功，后面的不发，避免对方先看到第 2 条 |
| S6 | 同一会话连发多条，第一条被业务拒绝（被拉黑、没权限、内容违规） | 第一条标记失败（不重试），后面的照常发；界面显示第一条失败，由用户决定重发或删除 |
| S7 | 不同会话都有待发送 | 会话之间并行，互不阻塞；同时进行的数量有上限 |
| S8 | 断网恢复后大量重发 | 指数退避加随机抖动，避免所有客户端同时冲击服务端 |
| S9 | `rate_limited` | 按服务端给的时间等待，不算失败次数 |
| S10 | 令牌过期 | 调用取令牌回调换新令牌后重发；换不到则保持 `pending`，连接状态显示"需要重新登录" |
| S11 | 等待发送期间被移出会话、会话被解散 | 服务端返回 `forbidden` / `not_found`，标记失败，不重试 |
| S12 | 超过自动重试窗口仍未发出 | 标记 `failed(network)`，显示红色感叹号，不悄悄丢弃，由用户点重试或删除 |
| S13 | 发送确认还没到，同步通道先把这条消息下发了 | 按 `client_msg_id` 合并成一条，界面不会出现两条 |
| S14 | 用户连点两次发送 | 一次输入只生成一个 `client_msg_id` |
| S15 | 编辑、撤回一条还没发出的消息 | 编辑：直接改队列里的内容；撤回：从队列取消。已经发出、还没收到确认：等确认后再执行编辑或撤回 |
| S16 | 退出登录时还有没发出的消息 | 先告诉应用有几条没发出，由应用决定等待还是放弃；清除数据会删掉队列 |
| S17 | 两台设备同时在同一会话发消息 | 服务端定顺序，两台设备最终看到同样的顺序 |
| S18 | 设备时间不准 | 顺序只看服务端 seq，不用设备时间 |

### 4.2 接收和同步

| # | 场景 | 处理 |
|---|---|---|
| R1 | 收到一批，存进本地之前应用退出 | 没确认，下次连上服务端从已确认位置重发 |
| R2 | 已存进本地，确认发出前应用退出 | 下次会重复收到，按 `(会话, seq)` 幂等写入，不会重复显示 |
| R3 | 确认在路上丢了 | 同 R2 |
| R4 | 手机推送通知到了，应用还没同步就被关掉 | 推送只负责提醒（可带摘要）；内容以同步为准，下次打开时同步；推送里的消息在同步完成前显示为"同步中" |
| R5 | 网络切换（Wi-Fi ↔ 4G）、重连 | 同一条下发通道从已确认位置继续；SDK 内部按 seq 排好再交给应用 |
| R6 | 本地磁盘满、写入失败 | **不确认**，停止同步并报存储错误；空间恢复后继续，不丢 |
| R7 | 本地库损坏 | 删除重建；按"新设备"规则同步（可能没有历史），并告诉应用本地历史已丢失。待发送队列和草稿单独保存，尽量保留 |
| R8 | 离线很久，积压很多 | 分批同步，界面显示"同步中"和进度；超过保留期的部分显示"更早的消息已不可同步" |
| R9 | 离线期间被移出会话 | 同步到移出事件为止；本地会话变为只读（保留还是删除由应用设置） |
| R10 | 离线期间别人编辑、撤回了旧消息 | 编辑、撤回是新的事件，同步后更新本地；本地没有原消息时只记一个占位 |
| R11 | 流式回复进行中断线 | 增量不落盘；重连后同步到这条消息的最新状态（生成中或已完成），继续接收增量 |
| R12 | 浏览器开了多个标签页 | 同一个浏览器是一台设备，只有一个标签页负责同步和写库，其他标签页通过广播拿数据；负责的标签页关掉后自动换一个 |
| R13 | iOS 通知扩展等第二个进程同时访问本地库 | 库内租约锁，同一时间只有一个进程写 |
| R14 | 服务端要求重新同步（会话迁移到别的库等） | 按服务端给的新起始位置继续，本地已有的记录保留 |
| R15 | 另一台设备已读 | 收到已读事件：更新未读数、撤掉已弹出的通知 |

### 4.3 离线期间状态变了（你补充的一类）

断网时消息在队列里，这期间其他人或用户自己的其他设备改变了状态，连上后发送会被服务端拒绝。原则：**服务端返回明确的错误码和原因，SDK 转成应用能直接显示的原因，标记失败、不自动重试**；同步通道同时会把造成这个变化的事件（例如"你被移出群"）下发，界面能同时更新。

| # | 离线期间发生了什么 | 服务端返回 | SDK 给应用的失败原因 |
|---|---|---|---|
| C1 | 被群主或管理员移出群 | `forbidden` | 你已不在该群 |
| C2 | 群被解散 | `not_found` | 群已解散 |
| C3 | 自己在另一台设备上退出了群 | `forbidden` | 你已退出该群 |
| C4 | 单聊对方拉黑了你 / 你在另一台设备拉黑了对方 | `blocked` | 对方拒收 / 你已拉黑对方，解除后才能发送 |
| C5 | 单聊对方账号被停用或删除 | `not_found` / `forbidden` | 对方账号不存在或已停用 |
| C6 | 自己的账号被停用 | 连接被拒（令牌失效） | 账号已停用；队列保留，不再发送 |
| C7 | 这台设备在另一台设备上被下线、改了密码导致其他设备下线 | 连接被拒 | 需要重新登录；队列保留，重新登录后由用户决定是否继续发 |
| C8 | 回复的那条消息被撤回了 | `not_found`（引用的消息不存在） | 回复的消息已被撤回；可选择不带引用重发 |
| C9 | @ 的人已经不在群里 | 正常发送，@ 不生效 | 发送成功；SDK 提示"某人不在群中，未提醒到" |
| C10 | 要编辑或撤回的消息已被管理员撤回 / 超过可编辑时间 | `not_found` / `conflict` | 消息已被撤回 / 已超过可编辑时间 |
| C11 | 自己的 Agent 被设置为需要审批 | 成功，但变成草稿 | 已提交，等待批准（不是失败） |
| C12 | 会话被接管（Agent 发送时） | `conflict` | 会话已被人工接管 |
| C13 | 触发护栏（跳数、重复、预算、熔断） | `rate_limited` / `conflict` / `policy_blocked` | 发送过于频繁 / 已达到今日额度 / 已暂停 |
| C14 | 内容被 DLP 或发送前拦截拒绝 | `policy_blocked` | 内容不符合规定（不重试，重试结果也一样） |
| C15 | 会话正在迁移到另一个库 | `conv_migrating` | 不算失败，SDK 自动稍后重试（在窗口内） |
| C16 | 服务端升级，要求更新客户端 | 握手失败 | 需要更新应用；队列保留 |
| C17 | 被移出后又被重新拉回群 | 成功 | 正常发送（离线时排队的消息，按服务端当时的状态判断） |
| C18 | 群设置改成只有管理员能发言（以后的功能） | `forbidden` | 当前只有管理员可以发言 |

服务端的错误码按业务含义统一（项目规则），SDK 在此基础上加一个**更具体的原因字段**（例如同是 `forbidden`，区分"不在群里"和"只有管理员能发言"），由服务端在错误详情里给出，SDK 不靠猜。

### 4.4 连接

连接状态机：未连接 → 连接中 → 已连接（同步中 / 已是最新）→ 重连中（第几次、多久后）→ 暂停（应用在后台）→ 需要重新登录 / 需要升级。重连用指数退避加抖动；应用回到前台、网络恢复时立即重连。

### 4.5 SDK 要覆盖所有业务（你的意见）

- 服务端的每一个业务操作，SDK 都有对应的函数；每一个错误码和原因，SDK 都有对应的类型。
- 用一份清单把"服务端客户端协议的全部操作"和"SDK 函数"对应起来，**CI 检查两边一致**：服务端加了新操作而 SDK 没有，构建失败。
- 每个函数都写明会返回哪些失败原因，异常场景（§4.1–4.3）逐个有测试。

## 5. 怎么证明 SDK 做对了

只靠写单个场景测试不够。SDK 测试工具包（[05 §6.6](05-operations.md)）里做**随机故障测试**：

- 用进程内服务端，随机注入：断网、丢推送、丢确认、重复推送、打乱顺序、应用在任意一步被杀（含写库到一半）、磁盘满、令牌过期、被移出会话、并发发送。
- 每轮几千次操作后检查不变量：
  1. 每条 `send()` 返回过的消息，最终要么在服务端恰好出现一次，要么在本地标记为失败；
  2. 本地消息表按 seq 重放的结果和服务端日志（在可见范围内）完全一致；
  3. 同一会话里同一个发送者的消息顺序和发送顺序一致；
  4. 没有越权：本地不出现不属于自己的会话的内容；
  5. 服务端收到的拉取量不超过限流。
- 每个语言的绑定都跑同一套（它们共用 Rust 核心，绑定层另测）；"故意改坏"验证：去掉去重、先确认后存储、不按顺序发送，测试都要失败。

## 6. 业内做法（2026-10 调研）

| 问题 | 业内做法 | 我们的选择 |
|---|---|---|
| 同步位置谁来记 | 服务端发不透明的令牌（Matrix）或客户端记、服务端校验（Telegram、Discord）；端到端加密的应用（Signal、WhatsApp）服务端按设备排队、确认后删除 | 服务端按设备记，确认后前进（§2.1） |
| 一次追赶的上限 | 都有每批上限和"还有更多"标记；落后太多直接让客户端重置（Telegram `differenceTooLong`、Matrix `M_UNKNOWN_POS`、Discord Invalid Session），重置后给当前状态加最近一段，**从不补全整个缺口** | 每批默认 200 条；落后超过保留期或超过 `sync.max_gap`（默认 1 万条）就重置到"新设备"规则 |
| 长期不在线的设备 | WhatsApp、Signal：未投递的保留 30 天 | 30 天没有确认的设备，同步记录作废，下次连接按新设备处理（`sync.device_ttl`，可设置） |
| 新成员看历史 | 工作类（Slack、Discord、Mattermost）默认全部可见；加密的消费类（Signal、WhatsApp）默认看不到，WhatsApp 2026 年起拉人时可选择带最近 25–100 条；Telegram、Matrix、Zulip 可按群设置；Teams 由拉人的人选择带多少 | 按群设置 + 拉人时可单独选（§2.4） |
| 新设备 | 服务端保存的产品（Slack、Teams、Telegram）全部可看，但都是**往回翻时按需取**；端到端加密的产品只给最近一段 | 只给最近一段，不提供往回翻（你的决定） |
| Agent 读历史 | Telegram、WhatsApp：**完全不能读历史**，只能收新消息，自己存；Slack：能读，但 2025 年起非市场应用每分钟 1 次、每次 15 条，理由是防止大量导出对话；Teams、Google Chat、Discord：**默认只收 @ 它的消息**，要读全部需群主或管理员同意，历史读取单独授权、有上限；Stream 的官方示例只拿本地同步到的最近 5 条做上下文 | 见 §2.7 |
| 已读同步 | Telegram、Matrix、Stream、Sendbird：每人一个已读位置存在服务端，作为普通事件同步到所有设备，服务端算未读数；Slack 在你用电脑时不给手机推送 | §2.6 |
| 保留期 | Slack、Mattermost、Synapse 默认永久，可设置；法律保全优先于删除；审核和审计记录单独保存 | §2.5 |
